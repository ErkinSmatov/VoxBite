# VoxBite

## What This Is

Telegram-бот, который по голосовому сообщению пользователя ("что я съел")
распознаёт блюдо, раскладывает его на ингредиенты с граммовкой, находит для
каждого ингредиента реальную запись в базе USDA FoodData Central через
embedding-поиск и математически считает КБЖУ и сахар (по возможности —
не все записи FDC содержат сахар). Пользователь подтверждает или
корректирует распознанное перед сохранением в дневник. На онбординге бот
считает пользователю целевые КБЖУ под цель (набор/сброс веса не быстрее
1 кг/месяц, либо поддержание/биохакинг). В будущем — платная подписка
(месяц/год через локальный эквайер, например Kaspi Pay) с лимитом голосовых
сообщений и мотивационными напоминаниями, но это отдельные фазы после
проверки core-цикла.

## Core Value

Точность распознавания блюда и подсчёта КБЖУ — это должно работать
надёжно, даже если оплата, лимиты и напоминания на старте отсутствуют.
Если распознавание/подсчёт не заслуживают доверия — продукта нет.

## Requirements

### Validated

(None yet — ship to validate)

### Active

- [ ] Пользователь может отправить боту голосовое сообщение с описанием
      съеденного
- [ ] Голос переводится в текст (STT)
- [ ] LLM раскладывает распознанный текст на ингредиенты с оценкой
      граммовки каждого (не отдаёт общее название блюда одним пунктом)
- [ ] Каждый ингредиент сопоставляется с 3 кандидатами из USDA FDC через
      embedding-based vector search (не точное совпадение строк)
- [ ] Бот показывает пользователю разбор блюда по компонентам с
      сопоставленной FDC-записью и граммовкой
- [ ] Пользователь может подтвердить разбор как есть
- [ ] Пользователь может скорректировать разбор: выбрать другого из 3
      кандидатов FDC для компонента, изменить граммовку (±10 г или ввод
      числа), убрать компонент, добавить недостающий компонент текстом
- [ ] После подтверждения бот математически (без LLM) считает
      калории/белки/жиры/углеводы/сахар записи и сохраняет её в дневник
      пользователя
- [ ] Если для ингредиента в FDC нет данных по сахару — бот показывает
      "нет данных", а не выдуманное или нулевое значение
- [ ] Пользователь проходит онбординг: пол, возраст, рост, текущий вес,
      уровень активности, цель (набор веса / снижение веса / поддержание
      / биохакинг), при наборе/снижении — желаемый темп с потолком 1 кг/мес
- [ ] Бот рассчитывает целевые КБЖУ по формуле Миффлина-Сан Жеора + TDEE +
      ограничение темпа набора/снижения не более 1 кг/месяц (см.
      TECH_SPEC.md §6)
- [ ] Пользователь видит день (съедено vs цель) в удобном виде
- [ ] Бот явно сообщает, что не является медицинским изделием и не
      заменяет консультацию врача/диетолога

### Out of Scope

- Оплата и подписка (месяц/год, локальный эквайер, лимиты голосовых
  сообщений) — отдельная фаза после проверки core-цикла на узком круге
  пользователей; на старте бот бесплатный/с ручным доступом
- Напоминания и мотивационные уведомления (фоновый планировщик) —
  отдельная фаза после core-цикла, не блокирует ценность продукта
- Публичный запуск/маркетинг — сначала закрытая бета (владелец + друзья)
- USDA FDC Branded Foods (~2 млн записей брендов США) — на v1 достаточно
  Foundation Foods + SR Legacy (~10-13 тыс. записей), Branded — не нужен
  для точности распознавания обычных блюд и раздувает объём индексации

## Context

- Заказчик — Frontend/React-разработчик, впервые делает бэкенд-продукт
  такого масштаба (Telegram-бот + LLM + vector search + внешние API) —
  инструкции по настройке окружения и сервисов должны быть подробными
  (см. `$INSTRUCTION_FILE`/CLAUDE.md в корне репозитория).
- Подробное техническое задание уже написано и лежит в `TECH_SPEC.md` в
  корне репозитория — архитектура, формулы расчёта КБЖУ, флоу обработки
  голосового, обоснование выбора USDA FDC + pgvector, открытые риски.
  Читать вместе с этим PROJECT.md перед планированием фаз.
- Целевой рынок — Казахстан (тарифы в тенге), что определило решение по
  оплате (см. Key Decisions).
- Первые пользователи — сам владелец + несколько друзей (закрытая бета),
  не публичный запуск. Это снижает требования к нагрузке/масштабированию
  на старте, но не к точности расчётов.

## Constraints

- **Оплата**: локальный эквайер/платёжный агрегатор (например, Kaspi Pay),
  не встроенный Telegram Payments API — последний не принимает тенге без
  локального эквайера. Реализуется отдельной фазой после core-цикла.
- **Данные о нутриентах**: только официальные значения из USDA FDC,
  математически посчитанные по граммовке — LLM не участвует в арифметике
  нутриентов, только в распознавании речи и декомпозиции блюда.
- **Темп изменения веса**: цель по набору/снижению веса не может задавать
  темп быстрее 1 кг/месяц — жёстко ограничено в формуле расчёта целевых
  калорий (TECH_SPEC.md §6.3).
- **Приватность**: голосовые сообщения — чувствительные данные (голос +
  здоровье/питание); исходные аудиофайлы не хранятся дольше, чем нужно для
  транскрипции.
- **Разработчик-заказчик без бэкенд-опыта**: любые шаги настройки
  (БД, ключи API, деплой) должны сопровождаться подробными пошаговыми
  инструкциями.

| Итоговый расчёт КБЖУ — математика (граммы × нутриенты из FDC), не LLM | LLM ненадёжна в арифметике; предсказуемость и проверяемость расчёта | — Pending |
| Оплата — локальный эквайер (Kaspi Pay-подобный), не Telegram Payments | Telegram Payments не принимает тенге без локального эквайера | — Pending |
| v1 без оплаты, без напоминаний — только core-цикл + онбординг с целью | Сначала проверить самое рискованное технически (точность распознавания/поиска по FDC) на узком кругу, не тратить время на договор с эквайером и юр. вопросы до валидации ценности | — Pending |

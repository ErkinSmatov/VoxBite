<objective>
Stand up the bot process itself: the Postgres-backed session storage adapter, the
fail-closed allowlist gate, `/whoami`, and a `npm run bot` entrypoint that
survives the two failure modes the owner will actually hit first — a second
instance running with the same token (409 Conflict) and no internet.

Purpose: this is the plan that turns "a token exists" into "a bot answers", and
it is where D-03 through D-07 are implemented. Onboarding itself is deliberately
not here — after this plan, an allowlisted user who sends `/start` gets no reply
yet, and that is the expected state until Plan 06 wires the conversation.

Output: a running bot that gates access, prints Telegram IDs for the owner to
copy, answers `/whoami`, and persists session state in `bot_sessions`.
</objective>

<decisions_settled_here>
- **`/whoami` sits behind the allowlist**, not in front of it. D-05 says the gate
  runs before any handler, and 02-RESEARCH.md Pattern 3's caveat resolves the
  same way: a non-allowlisted user does not need `/whoami`, because their `/start`
  already printed `отказ: telegram_id=…` in the owner's terminal — that is D-06's
  actual discovery mechanism. `/whoami` exists for the owner's own convenience
  after they are allowlisted.
- **The webhook seam is a file boundary, not an env var.** `src/bot/bot.ts`
  registers every handler and returns an unstarted `Bot`; `src/bot/index.ts` is
  the long-polling entrypoint and contains the only `bot.start()` call. Phase 3
  adds a webhook entrypoint next to it and changes zero handler code, which is
  what D-02 asks for, without introducing a `BOT_START_MODE` variable nobody
  needs yet.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Telegram update -> bot middleware chain | Every update is attacker-controllable in content and sender |
| `BETA_ALLOWLIST` string -> access decision | The single control keeping the closed beta closed |
| grammY error objects -> terminal output | Error objects from the Bot API client can carry request metadata including the token |
| Session key -> `bot_sessions` primary key | Derived from user-controlled chat/user identifiers |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-02-11 | Elevation of Privilege (ASVS V4) | `createAllowlistMiddleware` | mitigate | Deny-by-default: `parseAllowlist` returns an empty set for empty/absent/malformed config and the middleware only calls `next()` on a positive membership test; registered as the first `bot.use()` so no handler, session read or DB write runs first; unit tests assert the empty and malformed cases explicitly |
| T-02-12 | Information Disclosure | 409/401 handling in `src/bot/index.ts` | mitigate | The 409 and 401 branches print fixed hand-written Russian strings and never pass the error object to `console.error`; an automated check in this plan fails the task if `console.error(err)` appears |
| T-02-13 | Information Disclosure | Session blob and update objects in logs | mitigate | The storage adapter never logs `value`; `bot.catch` logs `err.message` only, never the update; the allowlist logs exactly one line containing an ID and a username |
| T-02-14 | Injection | Session key reaching SQL | mitigate | The adapter uses the Drizzle query builder exclusively; an automated check rejects raw SQL strings in the adapter |
| T-02-15 | Denial of Service (self-inflicted) | Two polling processes on one token | mitigate | grammY's polling loop rethrows on 409 and the entrypoint converts it into an actionable Russian instruction plus exit code 1, instead of a crash loop the owner cannot interpret (D-03) |
</threat_model>

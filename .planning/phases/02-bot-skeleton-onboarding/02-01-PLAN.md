<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| `.env` file -> process env -> logs/git | The bot token is a bearer credential; anyone holding it fully controls the bot |
| `BETA_ALLOWLIST` config string -> access-control decision | A misparse or a misread of "empty" flips the bot from closed to open |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-02-01 | Information Disclosure | `TELEGRAM_BOT_TOKEN` in `.env`, terminal output, git | mitigate | `.env` is gitignored (asserted by `git check-ignore` in Task 3's verify); the verify script asserts token *shape* without echoing the value; `.env.example` carries only a placeholder; Task 3's copy tells the owner how to revoke a leaked token |
| T-02-02 | Elevation of Privilege | Empty/absent `BETA_ALLOWLIST` misinterpreted as "allow everyone" | mitigate | `BETA_ALLOWLIST` is kept out of `REQUIRED_ENV_KEYS` so empty is a *legal, explicit* value rather than a startup crash the next developer "fixes" by defaulting to permissive; `loadEnv()` normalises absent to `''`; the fail-closed reading of `''` is enforced and unit-tested in Plan 04 (`parseAllowlist`) |
| T-02-03 | Denial of Service (self-inflicted) | Missing token discovered only at runtime | accept -> mitigate | `TELEGRAM_BOT_TOKEN` is in `REQUIRED_ENV_KEYS`, so `loadEnv()` fails fast at startup with a Russian message naming the key and pointing at `.env.example`, instead of surfacing as an opaque 401 from Telegram |
</threat_model>

<objective>
Implement the four correction operations over a persisted draft: swap the matched candidate,
adjust grams, remove a component, add a missing one.

Purpose: these are CORRECT-03..06, the mechanics the whole phase is named after. They live in
`src/application/` as plain functions over `(db, draftId, userId, ...)` so plan 09's Telegram
handler contains dispatch only, and so every rule here is unit-testable without a bot.
Output: `corrections.ts` plus the Wave 0 `corrections.test.ts`.

ACCEPTED TRADEOFF, stated rather than glossed over (CLAUDE.md, and echoing plan 04): there is
no compare-and-swap on gram adjustments. Two fast taps on `+10 г` can both read the same base
value and land as a single +10. The user sees the number and taps again; nothing is silently
lost or duplicated. Confirm and delete DO get compare-and-swap (plan 08) because a duplicate
there creates an invisible second diary row. Adding a version column or row locking to the gram
path would be complexity out of proportion to a self-correcting nuisance — revisit only if
beta users report it.

DISCRETION EXERCISED (04-CONTEXT.md left these open): the gram step is ±10 g only, no ±50 and
no percentage step — a second step size doubles the button row for a correction the typed-grams
path already covers exactly. An added component's grams are parsed from the same message when
the user writes one (e.g. "сметана 30" / "сметана 30 г"), and default to 100 g when they write
only a name; the user can then tune it with the same gram controls as any other component.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| `callback_data` draftId + component/candidate indices → draft mutation | User-controlled integers indexing into a persisted array |
| Free-text (typed grams, added component) → parser and paid embedding call | Unbounded user input reaching cost-incurring infrastructure |
| Concurrent taps → one component array | Two updates mutating the same jsonb array |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-04-01 | Elevation of Privilege / Tampering | every exported operation | mitigate | All calls go through `readDraft(db, draftId, userId)` and `updateDraftComponents(db, draftId, userId, ...)` from plan 04, which filter on `(id, user_id)` together; a foreign draft yields `reason: 'not_found'` with no write |
| T-04-04 | Tampering (input validation) | `parseGrams`, `adjustGrams` | mitigate | One shared parser rejecting non-numeric, zero, negative, non-finite and out-of-range values; ± buttons clamp into `MIN_GRAMS..MAX_GRAMS` so grams can never reach 0 or overflow |
| T-04-28 | Tampering (input validation) | component/candidate indices | mitigate | Both indices bounds-checked against the actual persisted arrays before use; out-of-range returns `reason: 'out_of_range'` with no write |
| T-04-03 | Denial of Service (cost) | `addComponent` | mitigate | `MAX_COMPONENT_TEXT_LENGTH` refusal and the empty-text refusal both run BEFORE `embedder.embed`; asserted by a zero-embedder-calls test. Per-day spend is additionally bounded upstream by the existing `DAILY_MESSAGE_CAP` gate on the message that created the draft |
| T-04-09 | Tampering | stale draft mutated | mitigate | Every operation runs `isDraftExpired` after `readDraft` and refuses with `reason: 'expired'` |
| T-04-21 | Tampering (data integrity) | double-tapped ±10 г | accept | No compare-and-swap on the gram path; a lost tap is visible and self-correcting. Stated in the module header and this plan's objective; confirm/delete are protected in plan 08 |
| T-04-07 | Information Disclosure | error logging in `addComponent` | mitigate | Failures log the draft id and the operation name only — never the typed text or component names |

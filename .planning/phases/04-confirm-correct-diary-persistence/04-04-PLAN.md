<objective>
Turn `diary_drafts` from a write-once Phase 3 artifact into the read/mutate store the whole
correction flow runs on: user-scoped reads, component and awaiting-input writes, status
transitions, expiry, and compare-and-swap claims for the two operations where a duplicate
write is a real correctness bug.

Purpose: every correction operation (plan 07), the confirm/edit/delete operations (plan 08)
and every Telegram handler (plans 09/10) go through this module. It is where CORRECT-07's
"state is in Postgres, not memory" and the IDOR guard are actually enforced.
Output: extended `types.ts`, extended `draft-store.ts`, and the Wave 0 `draft-store.test.ts`.

ACCEPTED TRADEOFF, stated rather than glossed over (CLAUDE.md): compare-and-swap protection is
applied to `claimConfirm` and `claimAbandon` ONLY. A double-tapped `+10 г` can still apply once
instead of twice, because both taps read the same base grams before either write lands. That is
a visible, self-correcting nuisance (the user taps again), whereas a double-applied confirm
would silently create two diary rows the user cannot see or reconcile. Adding row locking or a
version column to the gram path would buy nothing proportionate. If beta users report grams
"not registering," revisit with a `version` column on `diary_drafts` — do not reach for it now.
</objective>

Extend `src/application/draft-store.ts` with the following exports. Every one takes `db: Db`
first and imports no client. Every read and every write filters on BOTH `id` and `user_id`
using `and(eq(diaryDrafts.id, draftId), eq(diaryDrafts.userId, userId))` — a `draftId` arriving
from `callback_data` is user-controlled input, never authorization (04-RESEARCH.md V4). Do not
add a "convenience" overload that omits `userId`; a later caller will use it.

- `readDraft(db, draftId, userId): Promise<PersistedDraft | null>` — scoped select of every
  column in `PersistedDraft`, `.limit(1)`, returns `null` when absent (never throws for a miss).
  Cast the `components` jsonb to `DraftComponent[]`.
- `findAwaitingDraft(db, userId): Promise<PersistedDraft | null>` — the most recent row for this
  user with `status = 'draft'` AND `awaiting_input IS NOT NULL`, ordered by `updatedAt`
  descending, `.limit(1)`. This is what plan 10's text gate calls to decide whether a typed
  message is correction input or a new paid meal (D-04).
- `updateDraftComponents(db, draftId, userId, components: DraftComponent[]): Promise<boolean>` —
  scoped UPDATE that also sets `updatedAt`, and additionally requires `status = 'draft'` OR
  `status = 'confirmed'` (editing a saved entry per D-05/CORRECT-08 mutates a confirmed draft).
  Returns whether a row was affected, via `.returning({ id })`.
- `setAwaitingInput(db, draftId, userId, awaiting: DraftAwaitingInput): Promise<boolean>` and
  `clearAwaitingInput(db, draftId, userId): Promise<boolean>` — scoped UPDATEs of
  `awaiting_input` plus `updatedAt`.
- `markDraftStatus(db, draftId, userId, status): Promise<void>` — one parameterised function,
  mirroring `markUpdateStatus`; no markAbandoned/markConfirmed variants.
- `claimConfirm(db, draftId, userId): Promise<boolean>` — the compare-and-swap:
  UPDATE ... SET status='confirmed', updatedAt=now WHERE id=$1 AND user_id=$2 AND
  status='draft' RETURNING id. `true` when exactly one row came back; `false` means a
  concurrent tap already confirmed it — the caller treats that as a no-op, never an error.
- `claimAbandon(db, draftId, userId, fromStatus: 'draft' | 'confirmed'): Promise<boolean>` — the
  same conditional shape, used both by `✕ Отменить разбор` (from 'draft', D-12) and by the
  confirmed-entry delete flow (from 'confirmed', D-08).
- `linkDiaryRow(db, draftId, userId, diaryId): Promise<void>` — sets `diary_id` after the diary
  insert (D-06's back-reference).

Module header additions: restate the two `src/application/` hard rules (no grammY, no
module-level state), and state the IDOR rule in one sentence so a future reader cannot add an
unscoped helper without deliberately contradicting the comment. Also record the accepted
tradeoff from this plan's objective: CAS on confirm/abandon only, not on gram adjustments, and
why.

Nothing in this file logs transcript or component text. If a helper logs at all, it logs only
the draft id and the operation name (the `voice-pipeline.ts` logging invariant).

<objective>
Freeze the diary day at message receipt (D-07 / DIARY-01) by carrying the Telegram message's
own timestamp and the user's timezone into the pipeline, deriving `local_date` once, and
storing it on the `diary_drafts` row.

Purpose: 04-RESEARCH.md Pitfall 4 — it is tempting to compute the day inside the confirm
operation "because that is when the diary row is written." Doing so silently reassigns a
late-night meal to the wrong day and, worse, moves an entry when the user edits it the next
day. Freezing it here means plan 08's `confirm()` only ever COPIES the value and has nothing to
get wrong.
Output: `findOnboardedUser` returns a timezone; `meal.ts` passes `receivedAt`; `processMeal`
writes `localDate`.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Telegram `message.date` (client-supplied field) → diary day | The sending client controls this timestamp |
| `users.timezone` → `Intl` derivation | A malformed zone string reaching date derivation |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-04-23 | Tampering (data integrity) | `local_date` derivation timing | mitigate | Derived once at draft-save from `args.receivedAt`; `grep` criterion enforces a single `deriveLocalDate` call site in the pipeline, and plan 08's confirm only copies the stored value |
| T-04-24 | Tampering | client-controlled `message.date` | accept | A user can only mis-file their OWN meal into an adjacent day by lying about their own client clock; there is no cross-user impact, no spend impact, and Telegram itself stamps `date` server-side for normal clients. Rejecting skewed timestamps would break legitimate offline-then-sync sends |
| T-04-15 | Tampering | unknown IANA timezone | mitigate | `deriveLocalDate` throws (plan 02); the throw lands in the pipeline's existing late-failure path, so the user gets the standard failure copy rather than a draft silently filed under the server's day |
| T-04-07 | Information Disclosure | new operator log line for a missing `message.date` | mitigate | Logs only the update id and the fact the date was missing — never the transcript, the text, or the timezone |
</threat_model>

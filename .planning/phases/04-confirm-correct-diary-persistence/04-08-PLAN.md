<objective>
Turn a confirmed draft into a durable diary row, keep an already-saved entry editable through
the same machinery, and delete one for real when the user asks twice.

Purpose: this is the plan where the product becomes trustworthy per Core Value. Every number
written here comes from `calculateTotal()` — the same function that drew the `≈` preview — and
every absent nutrient stays NULL rather than becoming a comfortable-looking 0.
Output: `confirm-meal.ts` plus the Wave 0 `confirm-meal.test.ts`.

TRADEOFFS AND DISCRETION, stated rather than glossed over:
- Compare-and-swap IS applied here (unlike the gram path, plan 07): `claimConfirm` and
  `claimAbandon` are conditional UPDATEs, because a duplicate confirm creates a second diary row
  the user cannot see and cannot reconcile, which is exactly the kind of silently-wrong number
  this phase exists to prevent.
- `diary.description` (left to the planner by 04-CONTEXT.md) is the draft's transcript, trimmed
  and bounded; when the transcript is empty it falls back to a comma-joined list of component
  names. The transcript is what the user actually said, which is the most honest label for the
  entry and the one Phase 5's day view can show without re-deriving anything.
- A pre-Phase-4 draft (`local_date IS NULL`, see plan 01) cannot be confirmed: there is no
  honest day to file it under, and inventing one would corrupt a day's totals. It is refused
  with the same copy a stale draft gets.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| `callback_data` draftId → diary row insert/update/delete | A user-controlled integer reaching irreversible writes on health data |
| Concurrent confirm/delete taps → `diary` | Duplicate or double-executed destructive writes |
| FDC nulls → persisted nutrient columns | A coalesce-to-zero anywhere here becomes a permanent false health record |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-04-01 | Elevation of Privilege / Tampering | `confirmMeal`, `recomputeSavedEntry`, `deleteSavedEntry` | mitigate | Every draft access goes through plan 04's `(id, user_id)`-scoped helpers, and every direct `diary` UPDATE/DELETE is filtered by `and(eq(diary.id, ...), eq(diary.userId, userId))`; asserted by a `grep -c "diary.userId"` criterion and a foreign-user test |
| T-04-02 | Tampering (data integrity) | double-tapped confirm | mitigate | `claimConfirm`'s conditional UPDATE runs before the INSERT; a `false` return short-circuits to `already_confirmed` with zero inserts, asserted by a unit test |
| T-04-05 | Repudiation / irreversible data loss | `deleteSavedEntry` | mitigate | Requires an explicit `confirmed: true` argument (D-08's two-step prompt made structural), and `claimAbandon` runs before the DELETE so a repeated tap cannot re-delete; asserted by two unit tests |
| T-04-29 | Tampering (data integrity) | nutrient nulls | mitigate | Values from `calculateTotal` are written through unchanged; acceptance criteria forbid any `?? 0` coalesce, and a test asserts `sugarG` is exactly `null` (CALC-02, TECH_SPEC §5.8) |
| T-04-30 | Tampering (data integrity) | `local_date` on edit | mitigate | `recomputeSavedEntry` omits `localDate` from its update payload entirely, asserted by a unit test; `confirmMeal` copies the frozen value and never calls `deriveLocalDate` (grep criterion) |
| T-04-31 | Denial of Service (stuck state) | INSERT failure after a successful claim | mitigate | Compensating `markDraftStatus(..., 'draft')` restores the retryable state instead of leaving a confirmed draft with no diary row |
| T-04-22 | Repudiation | abandoned drafts retain transcripts after a delete | accept | Deleting the diary row does not purge the draft's transcript; no scheduler exists in this phase. Recorded in code comments and in plan 04's known-debt note rather than silently ignored |
| T-04-07 | Information Disclosure | failure logging | mitigate | Logs name the operation and the draft/diary id only — never the transcript, description, or component names |
</threat_model>

GATE ORDER (write this as a numbered module-header comment and label it the handler's
correctness story — the analogue of `meal.ts`'s spend-control story):
1. `ack(ctx)` first and unconditionally. The card lives in chat history forever, so a tap a day
   later gets "query is too old"; that must never abort the flow.
2. `parseCrc(ctx.callbackQuery?.data ?? '')`. `null` → return silently. A malformed or
   hand-crafted payload is ignored, never guessed at (V5 / 04-RESEARCH.md Pattern 2).
3. Resolve identity: `ctx.from?.id` → `findOnboardedUser(db, telegramId)`. Missing → answer with
   `pipelineCopy.notOnboarded` and return.
4. `readDraft(db, cb.draftId, user.id)` — the FIRST thing done with the parsed id, and it is
   scoped. `null` → `safeEditMessageText(ctx, correctionCopy.notYours)` and strip the keyboard.
   `notYours` is byte-identical to `expired` by design (plan 03), so a tap cannot distinguish
   "does not exist" from "belongs to someone else".
5. Status/expiry gates: `status === 'abandoned'` → expired copy + strip keyboard.
   `isDraftExpired(draft.status, draft.createdAt, new Date())` → `markDraftStatus(...,
   'abandoned')`, expired copy, strip keyboard (D-11).
6. Dispatch on `cb.action`. NEVER compute the next screen from `cb` alone — the process can
   restart between rendering a keyboard and the tap arriving, so the draft read in step 4 is the
   only source of truth (04-RESEARCH.md Pattern 1).

Action mapping:
- `sel` → `setAwaitingInput` is NOT used here; record the selected component index for level 2.
  Store it on the draft's `awaiting_input`-adjacent state ONLY if plan 06's codec did not carry
  the component index on the level-2 buttons. Whichever of the two shapes plan 06 landed on, use
  it consistently and state the choice in this file's header: either (a) level-2 buttons carry
  both indices in `callback_data`, or (b) the selected component index is persisted on the draft
  row. Do not mix them. Then redraw with `buildComponentEditCard` + `buildLevel2Keyboard`.
- `cand` → `swapCandidate(...)`, then redraw level 2 (so the user sees the mark move).
- `gm` / `gp` → `adjustGrams(..., -GRAM_STEP | +GRAM_STEP)`, then redraw level 2.
- `gtype` → `setAwaitingInput(db, draftId, userId, { kind: 'typed_grams', componentIndex })`,
  then redraw level 2 with `correctionCopy.askGrams(name)` appended (D-04).
- `rm` → `removeComponent(...)`, then redraw LEVEL 1 (the component being edited no longer
  exists); if the resulting array is empty, redraw the empty state with
  `buildEmptyStateKeyboard` — no Подтвердить (D-12).
- `back` → redraw level 1 from the draft just read.
- `add` → `setAwaitingInput(db, draftId, userId, { kind: 'add_component' })`, redraw level 1
  with `correctionCopy.askComponent` appended (D-04).
- `cancel` → `claimAbandon(..., 'draft')`, then `safeEditMessageText(ctx, correctionCopy.cancelled)`
  and strip the keyboard (D-12).
- `confirm` → `confirmMeal(db, draftId, user.id)`. On `ok` → `buildConfirmedCard(components,
  localDate)` + `buildConfirmedKeyboard` (D-05). On `reason === 'blocked'` → redraw level 1 with
  `correctionCopy.blockedConfirm(blockedComponent)` appended and the level-1 keyboard intact
  (D-10 — the user must be able to fix it right there). On `'already_confirmed'` → redraw the
  confirmed card, not an error (double-tap no-op). On `'expired'`/`'no_local_date'` → expiry copy.
  On `'empty'` → the empty state.
- `edit` → redraw level 1 over the confirmed draft (CORRECT-08 reuses the same screens; the
  draft stays `confirmed` while being edited, and plan 08's `recomputeSavedEntry` re-derives the
  snapshot). After any correction action on a draft whose `status === 'confirmed'`, call
  `recomputeSavedEntry` before redrawing so the saved numbers never lag the visible ones.
- `del` → `safeEditMessageText(ctx, correctionCopy.deletePrompt)` + `buildDeleteConfirmKeyboard`
  (D-08's mandatory second step — nothing is deleted on this tap).
- `delno` → redraw the confirmed card.
- `delyes` → `deleteSavedEntry(db, draftId, user.id, true)`; on success
  `safeEditMessageText(ctx, correctionCopy.deleted)` and strip the keyboard.

Redraw discipline: EVERY edit goes through `safeEditMessageText` / `safeEditMessageReplyMarkup`
from plan 03. `← Назад` onto an unchanged screen and re-tapping the already-chosen candidate
both produce Telegram's `400: message is not modified`, which is normal here (04-RESEARCH.md
Pitfall 1). Never call `ctx.editMessageText` directly in this file.

Never send a new message. The card is the message Phase 3 already owns and edits in place
(D-13); a `ctx.reply` here would break that invariant. Prompts for typed input (`askGrams`,
`askComponent`) are appended to the redrawn card, not sent separately.

Logging: on any operation failure, log the draft id and the action token only — never the
transcript, component names, or the callback payload.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Telegram callback payload → handler dispatch | Fully user-controllable string, replayable indefinitely from chat history |
| Telegram user id → database user scope | The only identity signal available; everything downstream is scoped by it |
| Chat history → destructive actions | The delete button remains tappable weeks later |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-04-06 | Spoofing / Tampering | callback payload parsing | mitigate | `parseCrc` with the anchored `CRC_PATTERN` only; unparseable input returns silently after `ack`, asserted by a zero-db-calls test |
| T-04-01 | Elevation of Privilege | draft access from a tapped id | mitigate | `readDraft(db, cb.draftId, user.id)` is the first use of the parsed id; a foreign draft yields the neutral `notYours` copy and zero operation calls, asserted by a test |
| T-04-17 | Information Disclosure | existence oracle | mitigate | `notYours` is byte-identical to `expired` (plan 03), so a tap cannot distinguish a non-existent draft from another user's |
| T-04-09 | Tampering | stale card tapped days later | mitigate | Gate 5 runs `isDraftExpired`, marks the draft abandoned, renders the expiry copy and strips the keyboard (D-11) |
| T-04-05 | Repudiation / data loss | `del` button in old chat history | mitigate | `del` only renders the Да/Нет prompt; the DELETE happens on `delyes` and `deleteSavedEntry` additionally requires `confirmed: true` (plan 08) |
| T-04-32 | Denial of Service (self-inflicted) | no-op redraws | mitigate | All edits go through `safeEditMessageText`/`safeEditMessageReplyMarkup`; direct `ctx.editMessageText` is forbidden by an acceptance-criteria grep |
| T-04-07 | Information Disclosure | handler logging | mitigate | Failures log the draft id and the action token only — never the callback payload, transcript, or component names |
| T-04-33 | Tampering | trusting the tapped keyboard's implied state | mitigate | Gate 6 dispatches only after the fresh scoped read; the module header states the rule and no branch computes a screen from `cb` alone |
</threat_model>

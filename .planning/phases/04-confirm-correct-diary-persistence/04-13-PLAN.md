<objective>
Close the two live-confirmed defects in `04-UAT.md` Round 3 / `04-REVIEW.md` CR-01/CR-02: typing a
correction into a reopened SAVED diary entry currently leaks into the paid meal pipeline instead
of being applied, and even once routed correctly, a text-based correction never updates the saved
`diary` row's totals.

**The central routing decision (must be stated explicitly, not left to the executor): widen
`findAwaitingDraft`'s filter, do NOT flip `case 'edit'`'s status back to `'draft'`.**

Two options were on the table (see `04-13-PLAN.md`'s planning guidance):
- (a) `case 'edit'` transitions the draft's status back to `'draft'`, then something un-transitions
  it later.
- (b) `findAwaitingDraft` widens its filter to `status IN ('draft', 'confirmed')`.

**Chosen: (b).** Reasoning, grounded in what the code already does:
- `updateDraftComponents` (`draft-store.ts:130-156`) ALREADY treats `'draft'` and `'confirmed'` as
  equally editable — its own doc comment says so verbatim ("editing a saved entry ... mutates a
  confirmed draft in place"). Widening `findAwaitingDraft` to the same two-status set is not a new
  precedent, it is completing one that already exists everywhere else in this file.
- `claimConfirm` (`draft-store.ts:209-217`) is a compare-and-swap that ONLY fires from
  `status = 'draft'`, and it is called from exactly one place: the `'confirm'` callback action
  (`correction.ts` `case 'confirm'`). Text-based corrections never call `confirmMeal`/`claimConfirm`
  — they call `applyTypedGrams`/`addComponent`, which only touch `components`/`awaitingInput`. So
  widening `findAwaitingDraft` cannot cause a confirmed draft to be re-confirmed, cannot touch
  `diary_id`, and cannot trip `claimConfirm`'s CAS in either direction.
- `claimAbandon` similarly only fires on an explicit `fromStatus` the caller passes (`'draft'` for
  cancel, `'confirmed'` for delete) — untouched by this change.
- Option (a) would require `case 'edit'` to flip `status` back to `'draft'` while `diary_id` stays
  set, which immediately raises exactly the questions the planning guidance warned about (does a
  stray `'confirm'` tap on that now-`'draft'` row re-fire `claimConfirm` and try to INSERT a SECOND
  `diary` row for the same draft? `confirmMeal`'s `not_found`/`empty`/`blocked` checks all assume a
  fresh draft, not a reopened one with an existing `diaryId`). None of that is a real problem under
  (b), because (b) never changes `status` at all — it only widens what `findAwaitingDraft` is
  willing to look at. (b) is also what `04-REVIEW.md` CR-01 itself recommends as the fix.

**CR-02, the second defect:** `handleAwaitingText` (`correction.ts` ~518-570) must call
`recomputeSavedEntry` under the same condition every button handler in this file already uses —
`draft.status === 'confirmed'` — in BOTH the `typed_grams` branch (after a successful
`applyTypedGrams`) and the `add_component` branch (after a successful `addComponent`). This
condition does NOT change under decision (b) above, since `status` never flips during editing.

Purpose: the saved-entry edit path (CORRECT-08) is only genuinely usable via text if a typed
correction routes correctly AND lands in the diary row — right now it does neither.
Output: `draft-store.ts` and `correction.ts` fixed; a routing-level regression test
(`draft-store.test.ts`), a recompute-call regression test (`correction.test.ts`), and a true
seam-level regression test (`meal.test.ts`, using the REAL `findAwaitingDraft`/
`createCorrectionTextHandler`, not an injected fake) that fails against the pre-fix code and
passes after it.
</objective>

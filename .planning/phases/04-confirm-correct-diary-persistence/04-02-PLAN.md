Export `interface TotalInputItem { grams: number; kcal: number | null; proteinG: number | null;
fatG: number | null; carbsG: number | null; sugarG: number | null }` — per-100g values,

Export `function calculateTotal(items: TotalInputItem[]): NutrientTotal`.

Rules the implementation must obey:
- Per item, per nutrient key: contribution is `(grams / 100) * per100gValue`. This is the whole
  of TECH_SPEC §5.7. No LLM, no heuristic, no lookup table.
- Always sum the full array from scratch. Never accept a running total or a delta — RESEARCH
  Pitfall 5: an incremental implementation is how the preview and the saved number drift apart.
- `missingCount[key]` counts items whose value for that key is `null`. A measured `0` is data,
  not missing (this mirrors Phase 1's `isIndexable()` rule already recorded in STATE.md).
- If every item is `null` for a key, that key's total is `null`, NOT 0 and NOT the string
  "нет данных" — this function never returns Russian text. Rendering is
  `src/bot/formatting/correction-card.ts`'s job (plan 06), exactly as `isWeakMatch()` returns a
  boolean and `result-card.ts` turns it into the ⚠️ line.
- Store raw floats. Do NOT round inside this function — per 04-RESEARCH.md Open Question 2 the
  decision for this phase is: round at render time only, so Phase 5's weekly sums do not compound
  rounding error. Write that decision into the file's header comment so plan 06 and plan 08 cannot
  each invent their own convention.
- Validate defensively in the style of `calculateTargetMacros`: throw
  `Invalid nutrient total input: ...` naming the offending field and value when `grams` is not a
  finite number >= 0, or when any supplied (non-null) per-100g value is not finite.

  <action>
Create `src/application/local-date.ts` exporting
`function deriveLocalDate(instant: Date, timezone: string): string`.

Implementation: `new Intl.DateTimeFormat('en-CA', { timeZone: timezone, year: 'numeric',
month: '2-digit', day: '2-digit' }).format(instant)`. The `en-CA` locale emits `YYYY-MM-DD`
directly, which is exactly what Postgres's `date` column accepts — no manual string
reassembly, no offset table, no new npm package. Node's bundled ICU carries the IANA
database including DST and historical-offset rules.

Guard rails the implementation must include:
- Reject a non-`Date` / invalid `Date` (`Number.isNaN(instant.getTime())`) with a
  descriptive Error.
- `Intl.DateTimeFormat` throws a `RangeError` on an unknown IANA zone; let that surface but
  wrap it with a message naming the offending timezone string, so an operator reading the log
  sees which user row is misconfigured. Never fall back to the process's local timezone —
  that would silently file a meal under the server's day instead of the user's (the exact
  class of bug D-07 exists to prevent).
- The file's header comment must state WHY this lives in `src/application/` and not
  `src/domain/`: it is pure, but its callers feed it I/O-adjacent inputs (a wall-clock instant
  and a user row's timezone), per 04-RESEARCH.md's Architectural Responsibility Map. It must
  also state D-07's rule in one sentence: this value is computed once, at message receipt, and
  every later step — confirmation, editing a saved entry — copies it, never recomputes it.
- No grammY import, no DB import, no module-level state.

Create `src/application/local-date.test.ts` covering every case in `<behavior>`, including
the RESEARCH Pitfall 4 regression framing: a fixed instant late on the user's local day still
resolves to that day regardless of when the test runs (use explicit `new Date(...)` literals,
never `new Date()` — the test must not depend on the machine's clock or timezone).

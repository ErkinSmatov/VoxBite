# Phase 04.1: Telegram Mini App correction UI - Context

**Gathered:** 2026-08-24
**Status:** Ready for planning

<domain>
## Phase Boundary

Phase 4 built the confirm/correct/diary-write flow as a chat-native interface: a two-level
correction card (D-01), inline keyboards, and a text-input gate (D-04) that routes typed replies
into a correction instead of the paid pipeline. This phase replaces the presentation layer with a
Telegram Mini App — a web page (React) rendered inside Telegram's own WebView, launched from a
`web_app` button — while the application-layer logic Phase 4 built (draft-store, corrections,
confirm-meal, calculate-total) is reused unchanged.

**Trigger:** this pivot was driven by two live gap-closure rounds in Phase 4 (04-12, 04-13) that
each closed a real, production-confirmed bug in the chat text-input gate — most recently a typed
correction on a reopened saved entry silently leaking into the paid decomposition pipeline and
creating a duplicate diary row (see `.planning/phases/04-confirm-correct-diary-persistence/04-UAT.md`
rounds 3-4). A touch UI with real buttons and number inputs removes the whole class of "is this
text a correction or a new meal" routing ambiguity that a chat-based text gate cannot fully close.

**In scope:**
- A Telegram Mini App (static React frontend + a small authenticated JSON API) implementing the
  same correction surface Phase 4 built: view components, swap FDC candidate, adjust grams,
  remove/add a component, confirm, and — for an already-saved entry — edit or delete (CORRECT-01
  through CORRECT-08, CALC-01, CALC-02, DIARY-01 — same requirement IDs as Phase 4, now discharged
  through a different UI).
- The API layer that lets the Mini App call the SAME `src/application/*` functions the bot's
  callback handlers call today (`draft-store.ts`, `corrections.ts`, `confirm-meal.ts`,
  `src/domain/nutrition/calculate-total.ts`) — no duplicated business logic.
- Telegram `initData` validation (HMAC signature check against the bot token) as the API's auth
  boundary, replacing `ctx.from.id` — this is the Mini App equivalent of the allowlist +
  `findOnboardedUser` check the bot handlers do today.
- A `web_app` button attached to the message that already carries the meal analysis (the same
  message Phase 3 acks with "Секунду, разбираю" and Phase 4 currently edits into a card) —
  launching the Mini App pre-loaded with that specific draft's id.
- Removing Phase 4's chat-native correction code: `src/bot/handlers/correction.ts`,
  `src/bot/formatting/correction-card.ts`, `src/bot/keyboards/correction-keyboards.ts`, the D-04
  text-input gate in `src/bot/handlers/meal.ts`, and their tests.
- Hosting the Mini App's static assets + API on Vercel.

**Explicitly NOT in this phase:**
- The bot's own deployment (it keeps running as a local long-polling process on the owner's
  machine for now — a separate, later decision. The Mini App only needs network access to the
  same Postgres database the bot already uses, which is already cloud-hosted on Supabase).
- Diary views (DIARY-02/03 — a day/week list with totals against targets) — still Phase 5,
  unstarted. See the note under Deferred about the gap this creates for OLD saved entries.
- Payments, subscription limits, reminders — unchanged, still out of v1 scope per PROJECT.md.
- Any change to STT, dish decomposition, or FDC indexing/matching — the Mini App corrects what
  those produce, it doesn't touch how they run.

</domain>

<decisions>
## Implementation Decisions

### Hosting and entry point

- **D-01: Hosted on Vercel.** Both the Mini App's static build and its API live there. Rationale
  (owner explicitly weighed cost/complexity, not just technical fit): the free tier covers this
  scale, deployment is a `git push`, and no server to patch or restart. The bot itself is
  unaffected — it stays a local long-polling process; the Mini App only needs the Postgres
  connection string it already has via `DATABASE_URL`.

- **D-02: Each analysis message carries its own "Open" button, not a single global menu button.**
  Once decomposition finishes, the bot attaches a `web_app` button (e.g. "🔧 Открыть для
  коррекции") to the SAME message it already acks and would otherwise edit into a card — that
  button's `web_app.url` carries the draft's id as a query/start param, so the Mini App opens
  directly to the right draft. Rationale: a chat-wide menu button has no way to know which of
  several open drafts the user means; per-message addressing removes that ambiguity entirely, and
  it's the natural continuation of Phase 3's D-13 (one message, edited/extended in place).
  **Consequence the planner must handle:** this replaces the *edit-into-a-card* step, not the ack
  step — VOICE-02's immediate "Секунду, разбираю" acknowledgment is untouched by this phase.

- **D-03: The chat message is never rewritten into a result card. It stays as the ack, plus the
  Open button.** No component list, no numbers, no candidate picker ever appears as chat text
  again — all of that lives only inside the Mini App. Rationale: the owner chose this over keeping
  a redundant text summary in chat, given the Mini App is now the single source of truth for what
  was eaten. **Known consequence, explicitly accepted, not solved here:** without a text summary
  in chat and without Phase 5's diary views yet built, the ONLY way back to an already-saved entry
  is finding its original message (with its still-clickable Open button — confirmed drafts are
  D-11-exempt from the 24h expiry) by scrolling chat history. This is a real gap until Phase 5
  ships; noted under Deferred, not fixed here.

### What gets removed

- **D-04: Phase 4's chat-native correction code is deleted in this phase, not kept as a fallback.**
  `src/bot/handlers/correction.ts`, `src/bot/formatting/correction-card.ts`,
  `src/bot/keyboards/correction-keyboards.ts`, the D-04-in-Phase-4 (`awaiting_input`) text gate in
  `src/bot/handlers/meal.ts`, and their tests are removed once the Mini App's equivalent
  functionality is live and tested. Rationale: two parallel ways to correct a draft is exactly the
  "two places for the same bug" pattern Phase 4's own D-06 rejected for a different reason (draft
  vs. diary storage) — the owner chose not to repeat it here. **Consequence the planner must
  handle:** `awaiting_input` (the jsonb column that did double duty as "waiting for typed input"
  AND "which component is open at level 2," per 04-09's design) becomes dead weight once the chat
  text gate is gone — the Mini App has no equivalent need for it, since it's a stateful client, not
  a stream of disconnected Telegram messages. Decide in planning: drop the column (new migration)
  or leave it unused with a doc comment. Do NOT silently keep writing to a column nothing reads.
  **What does NOT get removed:** `src/application/draft-store.ts`, `corrections.ts`,
  `confirm-meal.ts`, `src/domain/nutrition/calculate-total.ts`, `src/application/local-date.ts` —
  these are UI-agnostic per the hexagonal rule and are exactly what the new API layer calls.

### Claude's Discretion

Not discussed — the planner's/researcher's call within the constraints above:

- **Frontend framework and build tool.** Given this is a single-purpose screen inside a WebView
  (no routing, no SEO, no server-rendering need), a lightweight Vite + React SPA is the likely
  right choice over Next.js — but confirm current best practice for Telegram Mini Apps on Vercel
  during research before locking it.
- **API shape** — REST endpoints mapping close to the existing `draft-store.ts`/`corrections.ts`/
  `confirm-meal.ts` function signatures (listed under Reusable Assets below) vs. a single typed
  RPC-style endpoint. Either is fine; match whatever keeps the API layer thin.
- **`initData` validation implementation** — the HMAC-over-bot-token check Telegram's Mini App
  docs specify. This is a hard technical requirement, not a preference; get it from official
  Telegram docs during research, not improvised.
- **Whether the API runs as Vercel serverless functions or a small standalone Node server deployed
  to Vercel** — a technical/cost/DX tradeoff, not something the owner has an opinion on.
- **Exact button copy, colors, and visual design of the Mini App.** Follow the same
  actionable-Russian house style as the rest of the bot's copy
  (`src/bot/formatting/correction-copy.ts` is the reference for tone, even though its module will
  be retired — carry the tone forward, not the file).
- **Migration for dropping/retiring `awaiting_input`** (see D-04's consequence) — standard
  Phase-1-locked workflow: `drizzle-kit generate` + `migrate`, `push` banned, owner reviews SQL.
- **Whether the Mini App needs its own session/auth token beyond `initData`,** or whether every API
  call re-validates `initData` fresh (Telegram's own recommended pattern) — research question, not
  a user decision.
- **Test strategy** — the established project pattern: application-layer functions (unchanged)
  keep their existing Vitest coverage; the new API layer gets tests against fakes the same way
  `correction.ts`'s handlers were tested; the actual Mini App UI is verified by hand (same
  owner-executable-checklist pattern Phase 4 used, since there's no way to script a real Telegram
  WebView session).

</decisions>

## Existing Code Insights

### Reusable Assets — the application-layer functions the new API calls, unchanged

`src/application/draft-store.ts`:
`saveDraft(db, row)`, `readDraft(db, draftId, userId)`, `findAwaitingDraft(db, userId)` (retired
along with the text gate — see D-04), `updateDraftComponents(...)`, `setAwaitingInput(...)` /
`clearAwaitingInput(...)` (also retired), `markDraftStatus(...)`, `claimConfirm(db, draftId,
userId)`, `claimAbandon(...)`, `linkDiaryRow(...)`. All are already user-scoped
(`(draftId, userId)` pairs) — the Mini App API's job is to resolve `userId` from a validated
`initData` and pass it through exactly like the bot handlers do from `ctx.from.id`.

`src/application/corrections.ts`:
`swapCandidate(...)`, `adjustGrams(...)`, `applyTypedGrams(...)`, `removeComponent(...)`,
`addComponent(...)`, `parseGrams(raw)`, plus `GRAM_STEP`/`MIN_GRAMS`/`MAX_GRAMS`/
`MAX_COMPONENT_TEXT_LENGTH`. `addComponent` already goes through the sanctioned
`matchIngredient()` FDC search — the Mini App's "add component" form calls this function directly,
no new matching logic.

`src/application/confirm-meal.ts`:
`findBlockingComponent(components)`, `buildDiaryDescription(draft)`, `confirmMeal(...)`,
`recomputeSavedEntry(...)`, `deleteSavedEntry(...)`.

`src/domain/nutrition/calculate-total.ts`: `calculateTotal(...)` — the one function that must
produce both the live preview and the final saved numbers, unchanged from Phase 4's D-03 rule
(now enforced by the Mini App's frontend calling the same total, not a client-side recompute).

`src/application/local-date.ts`: `deriveLocalDate(...)` — one call site today
(`voice-pipeline.ts`), untouched by this phase.

### Established Patterns

- Hexagonal: `src/domain/**` and `src/application/**` import no grammY, no DB driver directly (go
  through `Db` type), no OpenAI SDK. The Mini App's API is a new adapter that follows the same
  rule — it may import `src/application/**`, never the reverse.
- Migrations: `drizzle-kit generate` + `migrate`, `push` banned, RLS enabled, owner reviews SQL
  before `db:migrate`.
- User- and operator-facing text is Russian and actionable — carries into the Mini App's UI copy.
- `src/config/env.ts` is the only place reading `process.env`; `REQUIRED_ENV_KEYS` currently
  `DATABASE_URL`, `OPENAI_API_KEY`, `TELEGRAM_BOT_TOKEN` — the Mini App's API will need
  `TELEGRAM_BOT_TOKEN` too (for `initData` validation), which is already required, and possibly a
  new `DATABASE_URL`-reachable config for its own deploy target (Vercel env vars, not `.env`).

### Integration Points

- `users.telegramId` (bigint, unique) and `users.timezone` — how the Mini App's resolved `initData`
  user maps to the existing `users` row; same `findOnboardedUser`-style lookup the bot uses.
- The message Phase 3's voice-pipeline already sends and edits (`args.ackMessageId`) is where the
  `web_app` Open button attaches — `src/application/voice-pipeline.ts` is the file that currently
  calls `deps.cardRenderer.renderLevel1(...)` (from Phase 4's 04-12 gap closure) and will instead
  need to attach a `web_app` button via a bot-layer port, mirroring the existing
  `DraftCardRenderer` port pattern (`src/bot/telegram/draft-card-renderer.ts`) rather than
  reinventing the seam.
- Node engine is `>=22` (package.json) — relevant if the Vercel API functions need a matching
  runtime version pinned.

<specifics>
## Specific Ideas

- The owner's stated trigger for this whole phase was blunt: "не работает" (referring to the
  chat text-input gate, after two live gap-closure rounds still weren't enough to make it fully
  trustworthy). The tie-break rule for any ambiguity the planner meets: prefer removing an entire
  class of routing ambiguity over patching another edge case in the chat-based flow — that is the
  whole reason this phase exists.
- The owner chose the more radical of the two "what stays in chat" options (D-03: nothing but the
  ack + button, not even a redundant summary) — treat this as a deliberate minimalism choice, not
  an oversight, when planning the Mini App's own "what does the user see first" screen (it likely
  needs to show a compact summary itself, since chat no longer will).

</specifics>

<deferred>
## Deferred Ideas

- **Finding a past saved entry without scrolling chat history.** A direct consequence of D-03 (no
  chat summary) combined with Phase 5 (diary views) not existing yet. Not solved in this phase —
  flagged plainly to the owner during discussion, accepted as a known gap. Phase 5 should treat
  "list of past entries, each reachable from the Mini App itself" as a hard requirement, not a
  nice-to-have, once this phase ships.
- **The bot's own deployment (webhook vs. continued long-polling, where it's hosted).** Explicitly
  out of scope here — the owner only decided where the *Mini App* lives (Vercel), not where the
  bot process lives. Revisit when payments/reminders (already out of v1 scope) or reliability
  requirements force the question.
- **Extending the Mini App to also show diary progress/targets.** Naturally adjacent once a web UI
  exists at all, but that's DIARY-02/03 — Phase 5's territory, not this phase's.

</deferred>

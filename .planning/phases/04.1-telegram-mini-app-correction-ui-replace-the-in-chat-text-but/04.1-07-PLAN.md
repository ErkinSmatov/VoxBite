<interfaces>
From `src/application/confirm-meal.ts`:
- `recomputeSavedEntry(db, draftId, userId, _now?): Promise<{ ok: true; diaryId: number } | { ok: false; reason: 'not_found'|'not_saved'|'blocked'; blockedComponent?: string }>`
  Requires `status === 'confirmed'` AND `diaryId !== null`, otherwise `not_saved`. Deliberately
  never touches `localDate` (D-07) — editing yesterday's entry today must not migrate it to today.
- `deleteSavedEntry(db, draftId, userId, confirmed: boolean, _now?): Promise<{ ok: true } | { ok: false; reason: 'not_confirmed'|'not_found'|'not_saved'|'already_deleted' }>`
  `confirmed === false` returns `not_confirmed` WITHOUT deleting — the two-step contract is
  enforced at this layer, not only in the UI. A repeated call loses the `claimAbandon` race and
  short-circuits to `already_deleted`.

From `api/_lib/http.ts` (plan 03): `requireUser`, `reasonToStatus` (which maps `'not_saved'` -> 409,
`'not_confirmed'` -> 400 and THROWS on `'already_deleted'`), `sendError`, `parseDraftId`,
`logApiError`.

From `api/_lib/draft-response.ts` (plan 03): `buildDraftResponse`.

From `04.1-UI-SPEC.md` (Screen Layout item 5): the two-step delete prompt
`Удалить запись? Это навсегда.` + `Да, удалить` / `Нет` is rendered entirely client-side; the
server does not need a "show prompt" round trip, it only needs the `confirmed` flag.

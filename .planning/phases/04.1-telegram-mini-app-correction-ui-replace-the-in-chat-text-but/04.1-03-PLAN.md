<objective>
Build the shared library every `/api` endpoint in this phase depends on: the Telegram `initData`
authentication boundary, the user lookup that turns a validated Telegram id into an onboarded
`users` row, the one application-reason-to-HTTP-status mapping, and the single response envelope
that carries components plus totals.

Purpose: this is the phase's security boundary. In the bot, identity came free from `ctx.from.id`
after grammY had already verified the update came from Telegram. On the web there is no such
guarantee — the API must prove for itself, on every single request, that Telegram signed the
caller's identity. Getting this wrong is a silent authentication bypass, not a visible failure.
Output: `api/_lib/*` plus one extracted application-layer helper, all unit-tested.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| public internet -> `/api/*` | Fully untrusted; anyone can reach these URLs |
| `Authorization: tma <initData>` -> resolved `userId` | The only identity assertion in the system, replacing grammY's `ctx.from.id` |
| API response -> Telegram WebView | Health data (what a person ate) leaves the system here |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-04.1-07 | Spoofing | `api/_lib/validate-init-data.ts` | mitigate | HMAC-SHA256 signature verification via `@tma.js/init-data-node`'s `validate()`; a forged `user.id` cannot produce a valid `hash` without the bot token. Tested with an altered-hash case and a wrong-token case |
| T-04.1-08 | Spoofing / Repudiation | replayed `initData` | mitigate | `expiresIn: MAX_AUTH_AGE_SECONDS` (3600) freshness bound, with a dedicated stale-`auth_date` test and a deliberate-break check proving the test fails when the bound is removed |
| T-04.1-09 | Elevation of Privilege | client-asserted identity | mitigate | `requireUser` is the sole identity source; acceptance criteria greps for any `req.body.userId`-style read and requires zero matches |
| T-04.1-10 | Information Disclosure | error bodies and logs | mitigate | `sendError` writes only a short machine code; `logApiError` logs only operation + draft id + reason, mirroring the LOGGING RULE already enforced in `draft-store.ts`/`corrections.ts`/`confirm-meal.ts` |
| T-04.1-11 | Tampering | totals computed outside `calculateTotal` | mitigate | `summarizeDraft` is the only item builder available to the API; acceptance criteria greps for any `grams / 100` arithmetic under `api/` and requires zero matches (CALC-01) |
| T-04.1-12 | Information Disclosure | IDOR via `draftId` | mitigate | No endpoint may query by `draftId` alone; the underlying `application/*` functions all require `(draftId, userId)` and `requireUser` supplies the second half. Enforced per-endpoint in plans 04-07 |

# Phase 04.1 Plan 12: Drop the awaiting_input column Summary

**Dropped diary_drafts.awaiting_input from the live Supabase database via a drizzle-kit generate+migrate cycle the owner reviewed and approved, and added a live-schema negative assertion so the column's absence is now continuously verified.**

## Performance

- **Duration:** ~50 min
- **Tasks:** 3 (1 auto, 1 blocking human-verify checkpoint, 1 auto)
- **Files modified:** 6 (2 created, 4 edited)

## Accomplishments

- Removed the `awaitingInput` column and `DraftAwaitingInput` interface from `src/db/schema/diary-drafts.ts`, replacing them with a HISTORY comment explaining what the column was for (D-04 chat-native text-input gate) and why it was removed (04-UAT.md rounds 3-4 defects, superseded by the Mini App) — a future reader of an old migration file can now find out what the column meant.
- Generated `drizzle/0008_harsh_callisto.sql` containing exactly one `ALTER TABLE "diary_drafts" DROP COLUMN "awaiting_input";` statement, with a leading comment recording that the column held live routing-state data at drop time, that the data is intentionally discarded because the Mini App has no equivalent concept, and that no backfill is needed given the D-11 24h draft expiry.
- The owner reviewed the exact SQL at the blocking checkpoint and approved it before anything touched the real database — confirmed via the coordinator relay.
- Applied the migration with `npm run db:migrate` (never `drizzle-kit push`) against the real Supabase database. `npm run verify-schema` now reports 9 applied migrations (was 8) and `SCHEMA OK`, including a new dedicated check confirming `diary_drafts` has no `awaiting_input` column.

## Migration Review Record (Task 2)

**Generated file:** `drizzle/0008_harsh_callisto.sql`

**Full contents as presented to the owner:**
```sql
-- This column held LIVE data at drop time: any diary_drafts row that was
-- mid-correction through the old chat-native flow (D-04) could have a
-- non-null awaiting_input value. That data is intentionally discarded here
-- -- the Telegram Mini App (phase 04.1) has no equivalent concept and does
-- not read this column. No backfill is needed: per D-11, unconfirmed drafts
-- expire after 24 hours, so any pre-cutover draft still mid-correction is
-- short-lived and will already be stale well before this migration runs.
ALTER TABLE "diary_drafts" DROP COLUMN "awaiting_input";
```

**Owner's approval:** relayed by the coordinator as "approved" after review; the coordinator confirmed the owner checked the file contains exactly one `DROP COLUMN awaiting_input` statement on `diary_drafts` and nothing else.

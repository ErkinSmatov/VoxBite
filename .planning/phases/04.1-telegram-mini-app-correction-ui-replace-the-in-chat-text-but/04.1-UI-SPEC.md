# Phase 04.1 — UI Design Contract

> Visual and interaction contract for the Telegram Mini App correction screen. Generated by
> gsd-ui-researcher, verified by gsd-ui-checker. This is a single-purpose WebView screen (no
> routing, no navigation chrome) — the contract below is deliberately narrow and prescriptive.

---

## Design System

| Property | Value |
|----------|-------|
| Tool | none — see rationale below |
| Preset | not applicable |
| Component library | none — hand-rolled (`ComponentRow`, `CandidatePicker`, `GramsControl`, `SummaryFooter`, per 04.1-RESEARCH.md's project structure) |
| Icon library | none — reuse the existing emoji-as-glyph convention already established in `src/bot/formatting/correction-copy.ts` (➕ ✕ ✎ 🗑 ✅ ✓) instead of adding an icon package |
| Font | system UI stack: `-apple-system, BlinkMacSystemFont, "Segoe UI", Roboto, sans-serif` (no custom `@font-face`) |

**Rationale for declining shadcn (flagged per CLAUDE.md's "don't auto-agree" rule, as the task
brief explicitly asked to sanity-check this):** No `components.json` exists in this repo, and
this phase builds exactly 4-5 small components inside one WebView screen with no dark-mode
toggle, no routing, no multi-page design system to keep consistent over time. Telegram Mini Apps
have their own native theming contract instead: Telegram injects `--tg-theme-*` CSS custom
properties (bg, secondary-bg, text, hint, link, button, button-text, destructive-text) matching
the user's actual Telegram theme (light/dark/custom), and the idiomatic pattern is to consume
those variables directly, not re-implement a parallel light/dark token system via a component
library. Pulling in shadcn (Radix primitives, its own Tailwind token layer, a themeable variant
system) would mean **maintaining two theming systems that fight each other** — shadcn's tokens
and Telegram's `--tg-theme-*` variables — for a screen with ~5 components. If the Mini App ever
grows into a multi-screen app with diary views, forms, etc. (post Phase 5), revisit; not
justified for this phase's scope. Plain CSS (or CSS Modules) driven entirely by `--tg-theme-*`
variables with static hex fallbacks (for local dev outside a real Telegram WebView) is the
correct, lower-ceremony choice here.

## Spacing Scale

Declared values (must be multiples of 4):

| Token | Value | Usage |
|-------|-------|-------|
| xs | 4px | Icon-to-text gaps, inline padding within a stepper |
| sm | 8px | Compact spacing: candidate list items, footer line spacing |
| md | 16px | Default spacing: row padding, gap between header/list/footer |
| lg | 24px | Section padding: screen horizontal margins |
| xl | 32px | Gap between the empty-state message and its actions |
| 2xl | 48px | Not used at this screen size |
| 3xl | 64px | Not used at this screen size |

Exceptions:
- **44px minimum tap target** on every interactive control (±10 г buttons, candidate list items,
  Убрать/Добавить/Подтвердить/Удалить buttons, Да/Нет in delete confirmation) — this is the
  standard iOS/Android touch-target minimum, not the 8pt scale itself; 44 is itself a multiple of
  4 so it does not violate the scale, but it is called out explicitly because it is a *floor*,
  not a spacing token, and every tappable element in this phase must be measured against it.
- The sticky footer must additionally respect `env(safe-area-inset-bottom)` padding on top of its
  `md` (16px) padding, so the Подтвердить/Удалить buttons are never obscured by a device's home
  indicator inside the Telegram WebView.

## Typography

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Caption/hint | 13px | 400 (regular) | 1.4 |
| Body | 15px | 400 (regular) | 1.5 |
| Label/emphasis | 17px | 600 (semibold) | 1.3 |
| Heading | 20px | 600 (semibold) | 1.2 |

Exactly 4 sizes, exactly 2 weights, as required. Usage:
- **Heading (20/600/1.2):** the running-total kcal number in the sticky header/footer only.
- **Label (17/600/1.3):** section header "Проверь разбор:", component names, button labels.
- **Body (15/400/1.5):** grams values, candidate names in the picker, general copy.
- **Caption (13/400/1.4):** hint text ("нет данных", partial-total footnote, delete-confirmation
  subtext, timestamps if ever shown).

## Color

Telegram Mini Apps must consume the platform's own injected theme variables, not a fixed palette
— this is the load-bearing reason "Tool: none" is correct above. Every color below is a CSS
custom property reference with a static fallback for local dev outside a real WebView.

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `var(--tg-theme-bg-color, #ffffff)` | Screen background |
| Secondary (30%) | `var(--tg-theme-secondary-bg-color, #f0f0f0)` | Component-row cards, sticky header/footer surfaces, candidate-picker expanded panel |
| Accent (10%) | `var(--tg-theme-button-color, #2ea6ff)` | **Reserved for:** the primary CTA button fill (Подтвердить / Сохранить изменения), the chosen-candidate marker/border (✓), the focus ring on the active grams input |
| Destructive | `var(--tg-theme-destructive-text-color, #e53935)` | **Reserved for:** the ✕ Убрать (remove component) button label, the 🗑 Удалить (delete entry) button, the delete-confirmation prompt's "Да, удалить" button and its warning text |

Text colors (not in the 60/30/10 split, but declared for completeness — required by every text
node in the screen):
- Primary text: `var(--tg-theme-text-color, #000000)`
- Secondary/hint text (grams sub-labels, "нет данных", captions): `var(--tg-theme-hint-color, #999999)`
- Link-style text (if any inline "изменить"-style affordance is styled as a link rather than a
  button): `var(--tg-theme-link-color, #2ea6ff)`
- Button text on the accent-filled CTA: `var(--tg-theme-button-text-color, #ffffff)`

Accent reserved for: primary CTA fill, chosen-candidate marker, active-input focus ring — nothing
else. Do not tint icons, section headers, or the stepper buttons with the accent color; those use
primary/secondary text color so the accent stays a clear "this is the one actionable/selected
thing" signal, matching the reserved-for discipline this contract requires.

## Copywriting Contract

Tone carried forward from `src/bot/formatting/correction-copy.ts` (module retired, tone kept):
plain, direct, states the fact then states what to do, never blames the user, never leaks an
internal error string/id, no marketing language. All Mini App copy is Russian.

| Element | Copy |
|---------|------|
| Screen heading (first load) | `Проверь разбор:` — reused verbatim from `correctionCopy.headerLevel1`, since D-03 makes this screen the sole place the component list is ever shown |
| Primary CTA (new draft) | `✅ Подтвердить` — reused verbatim from `correctionCopy.btnConfirm` |
| Primary CTA (editing an already-saved entry) | `Сохранить изменения` — new string, needed because "Подтвердить" implies first-time confirmation; editing a saved entry is a distinct action per CORRECT-08 |
| Add-component action | `➕ Добавить` — reused verbatim from `correctionCopy.btnAdd` |
| Remove-component action | `✕ Убрать` — reused verbatim from `correctionCopy.btnRemove` |
| Delete-entry action | `🗑 Удалить` — reused verbatim from `correctionCopy.btnDelete` |
| Cancel-whole-draft action (empty state only) | `✕ Отменить разбор` — reused verbatim from `correctionCopy.btnCancelDraft` |
| Candidate swap affordance | `Сменить вариант` — new string (tap target that expands the inline candidate picker on a component row) |
| Grams stepper labels | `−10 г` / `+10 г` — reused verbatim from `correctionCopy.btnMinus10`/`btnPlus10` |
| Missing-nutrient placeholder | `нет данных` — reused verbatim from `correctionCopy.noData`; **never** render `0` or a guessed value (CALC-02) |
| Running-total preview prefix | `≈` — reused verbatim from `correctionCopy.previewPrefix`, kept until the entry is actually saved |
| Partial-total footnote | `≥ {known} (у {missing} из {total} нет данных)` — reused verbatim from `correctionCopy.partialTotal(...)` |
| Empty state heading | `Компонентов не осталось.` (first sentence of `correctionCopy.emptyState`) |
| Empty state body | `Добавь один заново или отмени разбор.` (second sentence of `correctionCopy.emptyState`) — always paired with the ➕ Добавить and ✕ Отменить разбор actions, never shown as text alone |
| Blocked-confirm error | `Не могу подтвердить: для «{componentName}» не нашёл подходящую запись. Убери этот компонент или опиши его иначе.` — reused verbatim from `correctionCopy.blockedConfirm(...)`, shown inline above the disabled CTA, never as a native `alert()` |
| Grams-input error | `Не понял количество. Напиши число в граммах, например 200.` — reused verbatim from `correctionCopy.gramsRejected`, shown inline under the grams field |
| Add-component too-long error | `Слишком длинное описание. Опиши компонент покороче.` — reused verbatim from `correctionCopy.componentTooLong` |
| Add-component not-found error | `Не нашёл подходящую запись для «{componentName}». Попробуй описать иначе.` — reused verbatim from `correctionCopy.addNotFound(...)` |
| Draft-expired/not-yours error (full-screen) | `Этот разбор устарел, отправь сообщение заново.` — reused verbatim from `correctionCopy.expired`/`notYours` (must stay byte-identical between the two cases per the existing IDOR-privacy rule — a user must not be able to tell "expired" from "not yours") |
| Network/API failure (full-screen, new to this phase — no chat equivalent existed) | `Не получилось загрузить. Проверь соединение и попробуй ещё раз.` (fetch failure) / `Не получилось сохранить. Проверь соединение и попробуй ещё раз.` (mutation failure) — paired with a `Обновить`/retry action, never a bare error code |
| Save-success confirmation (inline, before auto-close) | `Сохранено в дневник` — new string, short-lived (~800ms) inline confirmation shown right before the Mini App calls `Telegram.WebApp.close()`, since D-03 means no chat message will ever confirm this |
| Destructive confirmation — delete entry | `Удалить запись? Это навсегда.` — reused verbatim from `correctionCopy.deletePrompt`, paired with `Да, удалить` (destructive-colored) / `Нет` (neutral), reused verbatim from `correctionCopy.btnDeleteYes`/`btnDeleteNo` |
| Destructive confirmation — remove component | none — removing a single component from a draft is non-destructive-in-effect (reversible via ➕ Добавить), so no confirmation dialog, matching the existing bot behavior (no such dialog existed pre-Mini-App either) |

## Screen Layout & Interaction Contract

Single vertical-scroll screen, no router, no tabs. Structure top to bottom:

1. **Sticky header** (secondary-bg surface, `md` padding, respects `env(safe-area-inset-top)`):
   heading `Проверь разбор:` (Label style) + live running total (Heading style for the kcal
   number, Caption style for protein/fat/carb/sugar breakdown and the `≈`/partial-total copy).
   Rendered fresh from whatever the API returns after every mutation — **never recomputed in
   React** (Anti-Pattern already flagged in 04.1-RESEARCH.md; this UI-SPEC restates it as a hard
   visual/interaction rule, not just a backend rule).
2. **Scrollable component list**, one `ComponentRow` per component:
   - Row surface: secondary-bg card, `md` padding, `sm` gap between rows.
   - Left: component name (Label style) + matched candidate name (Body style, secondary text
     color) + a `Сменить вариант` tap affordance that expands an inline accordion panel (not a
     modal) listing up to 3 candidates; each candidate is a Body-style tappable row with the `✓`
     chosen-marker (accent color) beside the active one — tapping a different candidate collapses
     the accordion and updates the row immediately from the API response.
   - Right: `GramsControl` — `−10 г` / grams value (Body style, tap-to-edit) / `+10 г`, all ≥44px
     tap targets in a horizontal row. Tapping the grams value itself switches it to a numeric
     input (`inputmode="numeric"`); invalid input shows the grams-input error inline beneath the
     row, never a toast/alert.
   - Row footer: `✕ Убрать` (destructive color, right-aligned, Label style).
3. **Add-component control**, persistent below the list: `➕ Добавить` button; tapping reveals an
   inline text field + submit button in place (no navigation/modal); a pending submit shows a
   spinner in place of the submit button; failure renders the add-component error inline below
   the field, success appends a new `ComponentRow` and clears the field.
4. **Empty state** (all components removed): replaces the list area with the empty-state heading
   + body (Body style), and reveals `✕ Отменить разбор` as a secondary action alongside
   `➕ Добавить` — the confirm CTA in the footer becomes disabled with the blocked-confirm error
   shown above it, mirroring how `findBlockingComponent` already blocks confirmation server-side.
5. **Sticky footer** (secondary-bg surface, `md` padding + `env(safe-area-inset-bottom)`):
   - New draft: `✅ Подтвердить` as the sole action, accent-filled, full-width, disabled +
     blocked-confirm copy shown above it whenever any component has no FDC match or the list is
     empty.
   - Reopened saved entry (CORRECT-08 edit path): `Сохранить изменения` (accent-filled, primary)
     stacked above a `🗑 Удалить` (destructive text, secondary/outline style) button. Tapping
     Удалить replaces the footer's action row in place with the two-step delete confirmation
     (`Удалить запись? Это навсегда.` + `Да, удалить` / `Нет`) — never a native `confirm()`
     dialog, which is unreliable inside Telegram's WebView.

**Non-interactive states (each replaces the whole screen body, not just a section):**
- **Loading (initial fetch):** centered spinner + `Загружаю…` (Caption style) — no skeleton
  needed given the tiny payload size.
- **Full-screen error:** the draft-expired/not-yours copy (fetch returned 401/403/404/410) or the
  network-failure copy (fetch threw / 5xx), each with a single retry/return action.

**Platform integration requirements (binding on the executor):**
- Call `Telegram.WebApp.ready()` and `Telegram.WebApp.expand()` on mount, before first paint if
  possible, to avoid a visible layout jump.
- Consume `--tg-theme-*` CSS custom properties directly (Telegram injects them automatically into
  the WebView's root) — do not hardcode a light or dark palette.
- After a successful confirm/save, show the `Сохранено в дневник` inline confirmation for ~800ms,
  then call `Telegram.WebApp.close()` to hand control back to the chat — this is the Mini App's
  equivalent of Phase 4's old "card disappears, saved" moment, now that D-03 removed any chat-side
  confirmation text.
- Sugar and any other nullable nutrient must render the literal `нет данных` string wherever the
  API returns `null` — verify this at both the per-component candidate display and the running
  total footer/header, not just one of the two.

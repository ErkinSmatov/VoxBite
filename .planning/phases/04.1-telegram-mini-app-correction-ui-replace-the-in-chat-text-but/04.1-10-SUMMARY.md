## Tasks Completed

### Task 1: SummaryTotals — the running total block
- File: `mini-app/src/components/SummaryTotals.tsx`
- Renders five labelled lines from a finished `NutrientTotal` prop — `Math.round` at render time is the ONLY numeric operation in the file (verified by the plan's own automated arithmetic-ban check). Labels/units (`Калории`/ккал, `Белки`/`Жиры`/`Углеводы`/`Сахар`, all г) copied verbatim from `src/bot/formatting/correction-card.ts`'s `NUTRIENT_META`.
- `null` renders `copy.noData` ('нет данных'), never 0; a present value with `missingCount[key] > 0` renders `copy.partialTotal(...)`. No `?? 0`/`|| 0` coalescing anywhere in the file (CALC-02).
- `saved === false` prefixes the block with `copy.previewPrefix` ('≈') and appends `copy.notSavedMarker` beneath it; `saved === true` shows neither.
- kcal line uses the Heading typography role; the other four use Caption, per the UI-SPEC.
- Commit: `c71cd07`

### Task 2: AddComponent control
- File: `mini-app/src/components/AddComponent.tsx`
- Collapsed: a single `copy.btnAdd` button. Expanded (in place, no modal): a text input (placeholder `copy.askComponent`, `maxLength={100}` mirroring `src/application/corrections.ts`'s `MAX_COMPONENT_TEXT_LENGTH`, since this file cannot import from `src/`) plus a submit button that becomes a spinner while in flight.
- Submits the typed text to `POST /api/drafts/:id/add-component` exactly as typed — no `.trim()`/`.replace()`/`.split()` in this file; `addComponent` on the server owns the trailing-gram-number split and the FDC search.
- Inline errors: `text_too_long` → `copy.componentTooLong`; `match_failed`/`empty_text` → `copy.addNotFound(text)`; anything else → `onError(copy.saveFailed)`. Never a toast, never `alert()`.
- Commit: `6ada09e`

### Task 3: FooterActions + final App.tsx composition
- Files: `mini-app/src/components/FooterActions.tsx`, `mini-app/src/App.tsx`
- `FooterActions` renders one of three action rows from a single `<footer className="sticky-footer">` surface: the two-step delete prompt (`copy.deletePrompt` + `Да, удалить`/`Нет`, entirely client-side, never the browser-native confirm dialog), the saved-entry row (`Сохранить изменения` stacked above `🗑 Удалить`), or the new-draft row (`✅ Подтвердить`, plus `✕ Отменить разбор` when the list is empty).
- The primary button is disabled whenever `blockedComponent !== null` OR `componentCount === 0`, with the reason shown above it — mirrors `findBlockingComponent`'s server-side refusal so the user never taps into a blind 422. When the list is empty and nothing is blocked, shows `copy.emptyStateBody` instead of calling `blockedConfirm(null)` (which would render nonsense).
- All footer buttons disabled while any action is in flight, so a double-tap cannot fire two confirms. On a successful confirm/recompute: `onUpdated(data)` then `onSaved()`. On a successful delete/cancel: `closeApp()`.
- `App.tsx`: sticky header (`copy.headerLevel1` + `SummaryTotals`), the `ComponentRow` list or the empty state (heading + body, paired with `AddComponent` and the footer's cancel action, never text alone), a persistent `AddComponent` below the list, and `FooterActions`. `onSaved` shows `copy.savedToDiary` inline for ~800ms (via a `setTimeout` ref cleared on unmount) then calls `closeApp()`. The screen-level inline error banner from plan 09 is preserved for mutation failures.
- Commit: `8bacad6`

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 2 — missing critical functionality] `copy.ts` was missing `notSavedMarker` and `askComponent`**
- **Found during:** Task 1 (writing `SummaryTotals.tsx`, which the plan's own `<interfaces>` section says can read `copy.notSavedMarker`) and Task 2 (`AddComponent.tsx` needs `copy.askComponent`)
- **Issue:** Plan 08's `copy.ts` did not export either string, even though this plan's `<interfaces>` section documents both as already available from `mini-app/src/copy.ts (plan 08)`.
- **Fix:** Added both strings to `copy.ts`, byte-copied from `src/bot/formatting/correction-copy.ts`'s `notSavedMarker` and `askComponent` entries — matches `copy.ts`'s own header rule that reused strings must be copied verbatim, never retyped, to avoid wording drift.
- **Files modified:** `mini-app/src/copy.ts`
- **Commit:** folded into `c71cd07` (notSavedMarker, needed by Task 1) and `6ada09e` (askComponent, needed by Task 2) — added at the point each was first needed, not as a separate commit.

**2. [Rule 1 — grep-driven wording, x2] `FooterActions.tsx` doc comments matched its own acceptance greps**
- **Found during:** Task 3 acceptance-criteria verification
- **Issue:** The module header originally wrote, in prose, "never `window.confirm()`" (matched the plan's own `window.confirm|alert\(` ban grep even though the match was prose about NOT using it) and "sends `{ confirmed: true }`" (inflated the `confirmed: true` literal count to 2, when the plan requires exactly 1 — the real call site).
- **Fix:** Reworded both comments to state the same facts without the banned literal tokens.
- **Files modified:** `mini-app/src/components/FooterActions.tsx`
- **Commit:** folded into `8bacad6` (caught during acceptance-criteria verification before the commit landed).

**3. [Rule 1 — bug] `FooterActions.tsx` initially rendered two separate `<footer className="sticky-footer">` elements**
- **Found during:** Task 3 acceptance-criteria verification (`grep -c "sticky-footer"` must return exactly 1)
- **Issue:** The delete-confirming branch and the normal (saved/new-draft) branch each returned their own `<footer className="sticky-footer">`, which is correct behavior (both states are footers) but produces 2 literal matches in the file, failing the plan's grep-based acceptance check.
- **Fix:** Refactored to a single `<footer className="sticky-footer">` wrapping a `body` variable chosen by a three-way if/else (delete-confirming / saved / new-draft) — same rendered output, one literal occurrence of the class name in source.
- **Files modified:** `mini-app/src/components/FooterActions.tsx`
- **Commit:** folded into `8bacad6`.

None of the three deviations changed the plan's intended behavior — all were wording/structure adjustments to satisfy the plan's own literal-string acceptance greps, or filled a gap the plan's own interfaces section assumed was already present.

<interfaces>
Project-locked migration workflow (Phase 1 CONTEXT.md, D-decision; also recorded in STATE.md's
Decisions list as "drizzle-kit generate+migrate only (push banned)"):
- `npm run db:generate` -> writes a new numbered `.sql` file into `drizzle/` and updates
  `drizzle/meta/`. It changes NOTHING in the real database.
- The owner reviews that `.sql` file.
- `npm run db:migrate` -> applies it to the real database.
- `npx drizzle-kit push` is BANNED in this project. It skips the review step and applies a diff
  directly, which is exactly the control this workflow exists to keep.

Existing migrations for reference on formatting/numbering: `drizzle/0000_enable_pgvector.sql`
through `drizzle/0007_whole_stranger.sql`. Note from Phase 2's decisions: drizzle-kit's
auto-generated filenames (e.g. `0003_grey_anthem.sql`) are KEPT as generated, never renamed.

Target in `src/db/schema/diary-drafts.ts`:
- the `awaitingInput: jsonb('awaiting_input').$type<DraftAwaitingInput | null>(),` column entry
  and the ~8-line comment block above it;
- the `export interface DraftAwaitingInput { kind: 'add_component' | 'typed_grams'; componentIndex?: number }`
  declaration and its own comment block.

`scripts/verify-schema.ts` is the existing script that checks the live database's shape.
</interfaces>

  <what-built>
    A migration file has been generated but NOT applied. Nothing in the real database has changed
    yet.

    Background, in plain terms, because this step involves the real production database:
    - A "migration" is a file containing SQL — instructions for changing the shape of the database.
      Drizzle wrote it automatically by comparing the schema description in the code against what
      it knows the database currently looks like.
    - This one removes a column called `awaiting_input` from the `diary_drafts` table. That column
      was used by the old in-chat correction flow to remember "the user tapped ➕ Добавить, so their
      next typed message is an ingredient name, not a new meal". The Mini App does not need it —
      a web page knows what the user is doing without leaving itself a note in the database.
    - Removing a column is permanent. Any values currently in it are discarded. That is intended
      here: the only rows that could have a value are drafts that were mid-correction in the old
      chat flow, and those expire after 24 hours anyway.
    - Nothing else in the table is affected. Transcripts, components, statuses, diary links and
      dates all stay exactly as they are.
  </what-built>

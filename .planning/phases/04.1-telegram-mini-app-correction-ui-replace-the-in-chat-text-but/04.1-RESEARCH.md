## User Constraints (from CONTEXT.md)

### Locked Decisions

**D-01: Hosted on Vercel.** Both the Mini App's static build and its API live there. Rationale
(owner explicitly weighed cost/complexity, not just technical fit): the free tier covers this
scale, deployment is a `git push`, and no server to patch or restart. The bot itself is
unaffected — it stays a local long-polling process; the Mini App only needs the Postgres
connection string it already has via `DATABASE_URL`.

**D-02: Each analysis message carries its own "Open" button, not a single global menu button.**
Once decomposition finishes, the bot attaches a `web_app` button (e.g. "🔧 Открыть для
коррекции") to the SAME message it already acks and would otherwise edit into a card — that
button's `web_app.url` carries the draft's id as a query/start param, so the Mini App opens
directly to the right draft. Rationale: a chat-wide menu button has no way to know which of
several open drafts the user means; per-message addressing removes that ambiguity entirely, and
it's the natural continuation of Phase 3's D-13 (one message, edited/extended in place).
**Consequence the planner must handle:** this replaces the *edit-into-a-card* step, not the ack
step — VOICE-02's immediate "Секунду, разбираю" acknowledgment is untouched by this phase.

**D-03: The chat message is never rewritten into a result card. It stays as the ack, plus the
Open button.** No component list, no numbers, no candidate picker ever appears as chat text
again — all of that lives only inside the Mini App. Rationale: the owner chose this over keeping
a redundant text summary in chat, given the Mini App is now the single source of truth for what
was eaten. **Known consequence, explicitly accepted, not solved here:** without a text summary
in chat and without Phase 5's diary views yet built, the ONLY way back to an already-saved entry
is finding its original message (with its still-clickable Open button — confirmed drafts are
D-11-exempt from the 24h expiry) by scrolling chat history. This is a real gap until Phase 5
ships; noted under Deferred, not fixed here.

**D-04: Phase 4's chat-native correction code is deleted in this phase, not kept as a fallback.**
`src/bot/handlers/correction.ts`, `src/bot/formatting/correction-card.ts`,
`src/bot/keyboards/correction-keyboards.ts`, the D-04-in-Phase-4 (`awaiting_input`) text gate in
`src/bot/handlers/meal.ts`, and their tests are removed once the Mini App's equivalent
functionality is live and tested. Rationale: two parallel ways to correct a draft is exactly the
"two places for the same bug" pattern Phase 4's own D-06 rejected for a different reason (draft
vs. diary storage) — the owner chose not to repeat it here. **Consequence the planner must
handle:** `awaiting_input` (the jsonb column that did double duty as "waiting for typed input"
AND "which component is open at level 2," per 04-09's design) becomes dead weight once the chat
text gate is gone — the Mini App has no equivalent need for it, since it's a stateful client, not
a stream of disconnected Telegram messages. Decide in planning: drop the column (new migration)
or leave it unused with a doc comment. Do NOT silently keep writing to a column nothing reads.
**What does NOT get removed:** `src/application/draft-store.ts`, `corrections.ts`,
`confirm-meal.ts`, `src/domain/nutrition/calculate-total.ts`, `src/application/local-date.ts` —
these are UI-agnostic per the hexagonal rule and are exactly what the new API layer calls.

**This research's resolution of D-04's open decision:** drop the `awaiting_input` column via a
real migration in this phase (see Runtime State Inventory) — do not leave it unused.

## Summary

This phase adds a new adapter (a Vite + React SPA plus a handful of Vercel serverless functions under `/api`) alongside the existing Telegram-bot adapter, without touching `src/domain/**` or `src/application/**`. The three application-layer modules already built in Phase 4 (`draft-store.ts`, `corrections.ts`, `confirm-meal.ts`) and `calculate-total.ts` are called directly from the new `/api` functions — same as the bot's callback handlers call them today, just with a different caller resolving `userId`.

The one genuinely new technical requirement is **Telegram `initData` validation**: every Mini App API request carries a raw `initData` string (not a `ctx.from.id`), and the API must independently verify Telegram signed it before trusting the enclosed `user.id`. The official algorithm is HMAC-SHA256-over-bot-token, documented at `core.telegram.org/bots/webapps` and mirrored precisely by the community-maintained `@tma.js/init-data-node` package (the current name — its predecessor `@telegram-apps/init-data-node` is npm-deprecated in favor of it, confirmed live via `npm view`, see Package Legitimacy Audit). Telegram's own guidance is to validate fresh, and check `auth_date` freshness, on every request — there is no documented "exchange for a session token" pattern; re-validating `initData` per request is the recommended approach and is cheap (one HMAC computation, no DB round-trip).

**Primary recommendation:** Vite + React SPA (no router — this is a single screen) built to `dist/`, deployed as a Vercel static build; a `/api/*.ts` directory of Vercel serverless functions (`@vercel/node` runtime) forming a thin REST layer 1:1 with the existing application-layer function signatures; `@tma.js/init-data-node`'s `validate()` re-run on every request as Express-style middleware equivalent; `TELEGRAM_BOT_TOKEN` (already a required env var) reused for validation, no new secret needed. `awaiting_input` (the jsonb column) should be **dropped via a real migration**, not left as dead weight — it has exactly one write-path caller left after this phase's deletions (`corrections.ts`'s `applyTypedGrams`/`addComponent`, which are reused code and must be edited to stop calling `clearAwaitingInput`), see the Runtime State Inventory section below for the precise call-site list.

### Alternatives Considered
| Instead of | Could Use | Tradeoff |
|------------|-----------|----------|
| Vite + React SPA | Next.js (App Router) | Next.js buys SSR/routing/image-optimization this phase does not need (single-screen WebView, no SEO); it also means learning Next's server-component model on top of an already backend-inexperienced owner — not justified here |
| Vercel serverless functions (`/api/*.ts`) | A standalone Node/Express server deployed to Vercel (or elsewhere) | A standalone server would need its own hosting decision, process manager, and health checks — exactly the "server to patch or restart" the owner explicitly wanted to avoid (D-01's rationale). Serverless functions are the lower-ceremony choice and match D-01's stated reasoning directly |
| `@tma.js/init-data-node` | Hand-rolled HMAC-SHA256 | The algorithm is simple but security-critical (this is literally the auth boundary); a maintained, spec-following package removes one hand-rolled crypto surface. If the package proves unusable, the algorithm itself (see Code Examples) is short enough to hand-roll safely with tests |
| REST endpoints matching `application/*` signatures 1:1 | A single typed RPC endpoint (e.g. `/api/rpc` dispatching by an `action` field) | REST-per-operation (`POST /api/drafts/:id/swap-candidate`, etc.) keeps each Vercel function small and cold-start-cheap, and maps 1:1 to `corrections.ts` exports, which is easier for the owner (a frontend dev, not used to designing backend RPC contracts) to reason about. RPC-style is marginally less boilerplate but obscures the mapping this research recommends keeping explicit |

### Pattern 1: `initData` re-validated on every request (no session token)
**What:** Every `/api/*` call includes the raw `initData` string (e.g. `Authorization: tma <initData>` header, Telegram's own suggested scheme name), and the serverless function calls `validate(initData, botToken)` before touching the database. No login step, no JWT/session cookie is issued.
**When to use:** Always for this phase — this is Telegram's own documented recommendation and CONTEXT.md's D-15-equivalent research question resolves in favor of it (see Summary). The compute cost (one HMAC-SHA256) is negligible next to a DB round-trip.
**Why not a session token:** A session token would be a second, self-invented auth mechanism to secure and expire correctly, duplicating work `initData` already does per-request, for a single-screen app where the marginal latency of re-validating is not measurable to the user.
**Example:**
```typescript
// api/_lib/validate-init-data.ts
// Source: https://docs.telegram-mini-apps.com/packages/tma-js-init-data-node/validating
import { validate, parse } from '@tma.js/init-data-node';

const MAX_AUTH_AGE_SECONDS = 3600; // Telegram's own docs recommend an expiry check; 1h is a reasonable v1 bound

export function validateAndParse(rawInitData: string, botToken: string) {
  validate(rawInitData, botToken, { expiresIn: MAX_AUTH_AGE_SECONDS });
  return parse(rawInitData); // throws on invalid signature or stale auth_date
}
```

### Pattern 2: Thin adapter, zero duplicated business logic
**What:** Every `/api/drafts/[id]/*.ts` handler does exactly three things: (1) validate `initData` → resolve `userId`, (2) parse+validate the JSON body with Zod, (3) call the matching `src/application/*` export and translate its discriminated result into an HTTP status + JSON body. No draft-mutation logic is re-implemented.
**When to use:** Always — this is the hexagonal rule ARCHITECTURE.md already establishes (`application/` never imported the other way) applied to the new adapter.
**Example:**
```typescript
// api/drafts/[id]/swap-candidate.ts
// Source: mirrors src/bot/handlers/correction.ts's dispatch shape, adapted for HTTP
import type { VercelRequest, VercelResponse } from '@vercel/node';
import { z } from 'zod';
import { swapCandidate } from '../../../src/application/corrections.js';
import { validateAndParse } from '../../_lib/validate-init-data.js';
import { resolveUser } from '../../_lib/resolve-user.js';
import { db } from '../../_lib/db.js';

const Body = z.object({ componentIndex: z.number().int(), candidateIndex: z.number().int() });

export default async function handler(req: VercelRequest, res: VercelResponse) {
  const initData = req.headers.authorization?.replace(/^tma\s+/, '');
  if (!initData) return res.status(401).json({ error: 'missing_init_data' });

  let parsed;
  try {
    parsed = validateAndParse(initData, process.env.TELEGRAM_BOT_TOKEN!);
  } catch {
    return res.status(401).json({ error: 'invalid_init_data' });
  }

  const user = await resolveUser(db, parsed.user?.id);
  if (!user) return res.status(403).json({ error: 'not_onboarded' });

  const body = Body.safeParse(req.body);
  if (!body.success) return res.status(400).json({ error: 'invalid_body' });

  const draftId = Number(req.query.id);
  const result = await swapCandidate(db, draftId, user.id, body.data.componentIndex, body.data.candidateIndex);
  if (!result.ok) return res.status(422).json({ error: result.reason });
  return res.status(200).json({ components: result.components });
}
```

### Pattern 3: `web_app` button on a per-message keyboard needs only a plain URL — no `start_param` mechanism required
**What:** `InlineKeyboard.webApp(text, url)` in grammY (confirmed directly from grammY's source, `src/convenience/keyboard.ts`) takes `url: string | WebAppInfo` — a plain HTTPS URL. Since D-02 attaches this button to a specific message (not a persistent menu button or a `t.me?startapp=` deep link), the draft id can simply be a query parameter on that URL: `https://voxbite.vercel.app/?draftId=123`. `start_param` (the `tgWebAppStartParam` mechanism) is Telegram's way of forwarding a parameter through `t.me` deep links and the persistent menu button — it does not apply to a direct `web_app` inline button's `url`, which Telegram opens verbatim (plus its own `tgWebAppData`/`tgWebAppPlatform` etc. query params Telegram itself appends).
**When to use:** Always for this phase's per-message button — simpler than `start_param`, and it is the mechanism that actually applies to this button type.
**Example:**
```typescript
// Source: https://grammy.dev/ref/core/inlinekeyboard, verified against grammY source
import { InlineKeyboard } from 'grammy';

function buildOpenButton(draftId: number): InlineKeyboard {
  const url = `${MINI_APP_BASE_URL}/?draftId=${draftId}`;
  return new InlineKeyboard().webApp('🔧 Открыть для коррекции', url);
}
```

### Anti-Patterns to Avoid
- **Recomputing totals in the Mini App frontend:** the frontend must render whatever `kcal`/`proteinG`/etc. the API returns (which itself calls `calculateTotal()`), never sum `grams × per100g` in React. This is a direct extension of D-03/CALC-01 to the new UI layer — a client-side recompute would create exactly the "second summation" the confirm-meal.ts module header explicitly forbids.
- **Trusting `Telegram.WebApp.initDataUnsafe` for authorization:** it is a parsed, client-controlled object — Telegram's own docs state its data "should not be trusted." Only the raw `initData` string, validated server-side via HMAC, may ever determine `userId`.
- **Skipping the `auth_date` freshness check:** validating the HMAC signature alone is not sufficient — a captured, still-correctly-signed `initData` string replayed later must be rejected. `@tma.js/init-data-node`'s `validate()` supports an `expiresIn` option; use it.
- **Building the API as one big RPC dispatcher that imports every `application/*` function into a single file:** defeats Vercel's per-function cold-start isolation and makes the 1:1 mapping (recommended above) harder to audit; keep one file per operation.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| `initData` HMAC verification | A hand-rolled `crypto.createHmac('sha256', ...)` chain | `@tma.js/init-data-node`'s `validate()`/`parse()` | This is the entire auth boundary for the new API — a subtle bug (wrong key derivation order, missing the `WebAppData` intermediate key, string vs buffer secret) is a silent authentication bypass, not a visible failure. A maintained package that implements the documented algorithm removes that risk class |
| Grams/text parsing for corrections | A new parser in the Mini App API layer | `src/application/corrections.ts`'s existing `parseGrams()` | Already exists, already tested, already enforces `MIN_GRAMS`/`MAX_GRAMS`/rounding rules — the Mini App's numeric input can send a raw string to `applyTypedGrams` exactly like the bot's text-gate did, no duplicate validation logic |
| Nutrient totals | A React-side sum | `calculateTotal()` via the API response | D-03/CALC-01, restated above — this is the one function that may ever sum nutrients |

**Key insight:** every "don't hand-roll" here is either an existing, already-audited application-layer function or a security-critical parsing routine (HMAC) with an official reference implementation — the discipline for this phase is resisting the urge to write a "just this once" shortcut version of either inside the new API files.

## Common Pitfalls

### Pitfall 1: Trusting `initDataUnsafe` or skipping validation "just for now"
**What goes wrong:** A developer reads `Telegram.WebApp.initDataUnsafe.user.id` client-side and sends it as a plain field in the API request body, skipping HMAC validation because it's more convenient during development.
**Why it happens:** `initDataUnsafe` is a parsed, ready-to-use object — much less friction than validating the raw string server-side.
**How to avoid:** Never accept a client-asserted `userId`/`telegramId` field in any request body. The ONLY source of truth for who is calling is the validated `initData`'s `user.id`, resolved server-side on every request (Pattern 1).
**Warning signs:** Any API handler that reads `req.body.userId` or similar instead of deriving it from `validateAndParse(...).user.id`.

### Pitfall 2: `initData` freshness (`auth_date`) not checked, enabling replay
**What goes wrong:** HMAC validation alone confirms Telegram signed the data at SOME point — a captured, still-valid-looking `initData` string (e.g. logged accidentally, or intercepted) could be replayed indefinitely.
**Why it happens:** The HMAC check is the headline requirement in most tutorials; the `auth_date` expiry check is a secondary, easy-to-skip detail.
**How to avoid:** Always pass an `expiresIn` (or equivalent) bound to the validation call and reject stale `auth_date` values (see Pattern 1's example, `MAX_AUTH_AGE_SECONDS`).
**Warning signs:** A validation helper whose signature has no expiry parameter.

### Pitfall 3: Frontend recomputes totals, silently diverging from `calculateTotal()`
**What goes wrong:** The Mini App shows a live "≈ preview" total client-side by summing `grams/100 × nutrient` in React for responsiveness, and that number very slightly diverges from what `calculateTotal()` returns from the API (different rounding, or a component was optimistically updated locally before the API round-trip completed) — the user sees one number, the diary saves another.
**Why it happens:** Client-side instant feedback feels more responsive than waiting for a round-trip on every ±10g tap.
**How to avoid:** Either (a) always show the API's returned total after each mutation (slight latency, but D-03-safe), or (b) if instant local feedback is wanted, it must call the SAME `calculateTotal` logic — which means either shipping `domain/nutrition/calculate-total.ts` (a pure, dependency-free function) to the frontend bundle unmodified, or accepting the latency of (a). Do not write a second summation formula in the frontend.
**Warning signs:** Any arithmetic involving `grams` and a nutrient value inside a `.tsx` file.

### Pitfall 4: Vercel `/api` cold starts adding perceptible correction-loop latency
**What goes wrong:** Each serverless function is a separate cold-startable unit; a user rapid-tapping ±10g could hit cold starts on functions that haven't been invoked recently, making the touch UI feel laggier than the chat buttons it replaces.
**Why it happens:** Serverless functions scale to zero between invocations by design.
**How to avoid:** Not a v1 blocker (closed beta, low traffic per PROJECT.md) — but keep each function's dependency graph small (no heavy imports beyond what's needed) to minimize cold-start duration, and note this as a revisit trigger if beta feedback reports lag.
**Warning signs:** User reports of "button feels slow the first time, fast after."

### Pitfall 5: `Authorization` header stripped or rewritten by an intermediary
**What goes wrong:** Some setups (proxies, certain fetch configurations) can drop or alter custom/Bearer-like headers. If the `initData` transport breaks silently, every API call 401s.
**Why it happens:** Not Vercel-specific, but worth testing explicitly since this is the sole auth transport.
**How to avoid:** Test the exact header name/scheme end-to-end early (Wave 0), not assumed from documentation alone.
**Warning signs:** 401s in production that don't reproduce locally.

## Open Questions

1. **Should `mini-app/` be a separate `package.json` (own `node_modules`) or a workspace/subfolder sharing the root `package.json`?**
   - What we know: the root project has no monorepo tooling (no `workspaces` field in `package.json` today) and a Node/tsx-based bot process; the Mini App needs a browser-targeted React/Vite toolchain with a different build step entirely.
   - What's unclear: whether importing `src/application/*` types directly into `mini-app/src/types.ts` (to keep `DraftComponent` shapes in sync) is easiest via a shared root `package.json` + `tsconfig` project reference, or via manually mirroring the type (accepting drift risk) with a comment pointing at the source of truth.
   - Recommendation: keep it simple for a solo owner — a single root `package.json` (add `vite`/`react` as dependencies there, as shown in Installation above) with `mini-app/` as a plain subfolder, no npm workspaces. Only introduce workspaces if type-sharing friction proves painful in practice; premature monorepo tooling is more ceremony than this phase's one-frontend, one-API-layer shape needs.

2. **Exact env var name and required-vs-optional status for the Mini App's base URL.**
   - What we know: the bot process needs to know the Mini App's deployed URL to build the `web_app` button (`MINI_APP_BASE_URL` suggested above); `REQUIRED_ENV_KEYS` currently only covers `DATABASE_URL`, `OPENAI_API_KEY`, `TELEGRAM_BOT_TOKEN`.
   - What's unclear: whether this should be required (bot refuses to start without it, matching D-01's "Mini App is the only place correction UI appears" — no fallback UI exists) or optional with an explicit "button omitted" fallback for a dev environment where the Mini App isn't deployed yet.
   - Recommendation: make it required — per D-03, there is no chat-based fallback UI anymore, so a bot running without a working Open button cannot let a user reach correction at all; failing loudly at startup (like the existing `REQUIRED_ENV_KEYS` pattern) is safer than a silent missing button.

3. **Vercel Postgres connectivity from serverless functions vs. the bot's existing `postgres`/`Db` client setup.**
   - What we know: the bot uses `postgres` (npm package, `postgres.js`) + Drizzle via `src/db/client.ts`, connecting to Supabase over a pooled connection string (`.env.example`'s "Session pooler" guidance).
   - What's unclear: Vercel serverless functions are short-lived and can open many concurrent connections under load; Supabase's pooler mode matters here (session vs. transaction pooling) in a way it may not for the bot's single long-lived process. This was not independently verified against Supabase's serverless-specific pooling guidance in this research pass.
   - Recommendation: reuse the existing `DATABASE_URL`/pooler setup for v1 (closed beta, low concurrency) but flag this explicitly to the owner as a "if Vercel functions report connection errors under load, switch the API's connection string to Supabase's transaction-mode pooler port" contingency — not a blocking research gap for a beta of a few users.

|---------------|---------|-----------------|
| V2 Authentication | yes | `initData` HMAC-SHA256 validation (Pattern 1) replaces password/session auth entirely — Telegram is the identity provider |
| V3 Session Management | yes (in the "no session" sense) | Deliberately stateless — re-validate `initData` per request (Pattern 1) instead of issuing/managing session tokens, per Telegram's own guidance |
| V4 Access Control | yes | Same IDOR discipline `draft-store.ts`/`confirm-meal.ts` already enforce (`and(eq(id, draftId), eq(userId, userId))`) — the new API layer must resolve `userId` from validated `initData` ONLY, never trust a client-supplied id, and every application-layer call already requires both ids per the existing modules' documented IDOR rule |
| V5 Input Validation | yes | Zod schemas on every `/api/*` request body (Pattern 2), mirroring the project's existing `zod` usage for LLM structured output |
| V6 Cryptography | yes | HMAC-SHA256 via the library, never hand-rolled (Don't Hand-Roll) — no new key material, reuses `TELEGRAM_BOT_TOKEN` |

### Known Threat Patterns for this stack

| Pattern | STRIDE | Standard Mitigation |
|---------|--------|---------------------|
| Forged/tampered `initData` (attacker crafts their own `user.id`) | Spoofing | HMAC-SHA256 signature check — a forged payload cannot produce a valid `hash` without the bot token |
| Replayed captured `initData` | Spoofing / Repudiation | `auth_date` freshness check (`expiresIn`, Pitfall 2) |
| IDOR — draftId belonging to another user | Elevation of Privilege | Existing `and(eq(diaryDrafts.id, draftId), eq(diaryDrafts.userId, userId))` scoping in every `application/*` function, unchanged and reused by the new API layer (Architectural Responsibility Map) |
| CORS misconfiguration allowing a non-Telegram origin to call the API with a stolen `initData` string | Information Disclosure / Tampering | The API's real protection is `initData` HMAC validation itself (an attacker without a valid, fresh, correctly-signed `initData` gains nothing from CORS access) — but restricting the `Access-Control-Allow-Origin` to the Mini App's own deployed origin is defense-in-depth and should be set explicitly in `vercel.json`/each handler rather than left as Vercel's default (which may be permissive for a same-project static+API deployment; verify in Wave 0) |
| Health-data (nutrition/meal) leakage via verbose error responses | Information Disclosure | Mirror the existing `LOGGING RULE` from `draft-store.ts`/`corrections.ts`/`confirm-meal.ts`: API error responses and server logs must never include transcript or component text, only operation name + draft id, matching the project-wide invariant already enforced in the reused files |

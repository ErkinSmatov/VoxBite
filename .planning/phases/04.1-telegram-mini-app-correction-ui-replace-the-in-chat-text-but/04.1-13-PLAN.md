<interfaces>
From plan 01: `vercel.json` declares `buildCommand: "npm run miniapp:build"` and
`outputDirectory: "mini-app/dist"`, plus a rewrite sending non-`/api` paths to `/index.html`.
`package.json` declares `"engines": { "node": ">=22" }`.

From plan 02: the bot reads `MINI_APP_BASE_URL` from `.env` (a REQUIRED key — the bot refuses to
start without it) and builds `${MINI_APP_BASE_URL}/?draftId=<id>`.

From plan 03: every `/api` request must carry `Authorization: tma <initData>`; a request without it
receives `401 {"error":"missing_init_data"}`. That exact response is the smoke test for a healthy
deployment.

Server-side environment variables the deployed functions need (all read through
`src/config/env.ts`'s `loadEnv()`, which falls back to `process.env` when there is no `.env` file):
`DATABASE_URL`, `TELEGRAM_BOT_TOKEN` (used as the initData HMAC secret), `OPENAI_API_KEY` (used by
`api/_lib/matching.ts` for the add-component embedding), and `MINI_APP_BASE_URL`.

Open items this plan must settle, flagged in 04.1-RESEARCH.md and never yet verified against a real
deployment: assumption A3 (the root-`/api` + separate-SPA-folder layout is correct for Vercel),
Pitfall 5 (the `Authorization` header surviving end to end), the Security Domain's CORS note, and
the deployed Node major version.
</interfaces>

  <what-built>
    The project exists but has no configuration. Four values must be given to it.

    What an "environment variable" is here: a named secret or setting that lives in the hosting
    service rather than in the code, so it never ends up in Git. Your local `.env` file does the
    same job on your laptop; Vercel's Settings page does it in the cloud.

    Why each one is needed:
    - `DATABASE_URL` — where the drafts and diary live (the same Supabase database the bot already
      uses; the Mini App reads and writes the very same rows).
    - `TELEGRAM_BOT_TOKEN` — NOT for sending messages here. The Mini App's server uses it to check
      the signature Telegram attaches to every visit, which is how it knows who you are. Without
      it, every request would be rejected.
    - `OPENAI_API_KEY` — used only when you add a missing ingredient by typing its name; that runs
      the same ingredient search the bot uses, which costs a fraction of a cent per use.
    - `MINI_APP_BASE_URL` — the page's own address, which the code also reads.
  </what-built>
  <how-to-verify>
    A. Set the variables on Vercel:
    1. In the Vercel project, open "Settings" -> "Environment Variables".
    2. Add each of the four below. For each one: type the name in "Key", paste the value in

       too is fine), then click "Save".
       - `DATABASE_URL` — copy the value from the `DATABASE_URL=` line in your local `.env` file.
       - `TELEGRAM_BOT_TOKEN` — copy from the same file.

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-04.1-58 | Spoofing | the deployed API being callable by anyone | mitigate | Verified live: an unauthenticated request returns 401 `missing_init_data` and a forged one returns 401 `invalid_init_data`, both recorded as curl evidence rather than assumed from the code |
| T-04.1-59 | Tampering | the `Authorization` header stripped in transit | mitigate | Task 3 tests the header end to end over the real network (RESEARCH.md Pitfall 5) and specifies the fallback transport if it fails, rather than discovering it during manual testing |
| T-04.1-60 | Information Disclosure | secrets committed to git | mitigate | `.env` git-ignore re-verified after editing; Vercel variables are entered in the dashboard, never in a file |
| T-04.1-61 | Information Disclosure | permissive CORS | mitigate | Measured, not assumed; a restrictive `Access-Control-Allow-Origin` is added in `vercel.json` if the default is permissive. Residual risk accepted because the HMAC boundary is the real control |
| T-04.1-62 | Denial of Service | wrong Node runtime silently deployed | mitigate | Deployed Node major version read from the platform and required to be >= 22, matching `engines` |
| T-04.1-63 | Denial of Wallet | `OPENAI_API_KEY` now present in a cloud environment | accept | Same key, one more location; the only endpoint that spends is behind `requireUser` (plan 06's T-04.1-23). The existing OpenAI hard spend cap from Phase 1 remains the backstop |
</threat_model>

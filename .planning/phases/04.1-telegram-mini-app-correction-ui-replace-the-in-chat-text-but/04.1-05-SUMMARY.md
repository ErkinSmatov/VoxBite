## Decisions Made

### Single post-mutation `readDraft` for every endpoint's response + guard check

The plan explicitly allowed either a pre- or post-mutation read; this implementation reads once, after the mutation succeeds, because none of these three mutations (`swapCandidate`, `adjustGrams`, `applyTypedGrams`) change a draft's `status` — a post-mutation read gets both the up-to-date `components` for the response envelope and the correct `status` for the recompute-guard check in one round trip, and doubles as the source of `localDate`/`diaryId` that `buildDraftResponse` needs.

### `blockedComponent` surfaces structurally, not via a special branch

`buildDraftResponse` calls `findBlockingComponent(draft.components)` unconditionally on every response. This means the plan's requirement — "recompute reporting `blocked` still returns 200, but with a non-null `blockedComponent`" — is satisfied without the endpoint code needing to special-case the recompute result's `blockedComponent` field into the response; it falls out of the shared envelope builder for free, and was verified with a dedicated test.

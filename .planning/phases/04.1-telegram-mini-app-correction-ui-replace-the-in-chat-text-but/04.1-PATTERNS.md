# Phase 04.1: Telegram Mini App correction UI - Pattern Map

**Mapped:** 2026-08-24
**Files analyzed:** 22 (new) + 6 (modified) + 5 (deleted)
**Analogs found:** 20 / 22 new files have a strong in-repo analog; 2 (React components, `vite.config.ts`/`vercel.json`) have no in-repo analog — use RESEARCH.md's Code Examples/Recommended Project Structure instead.

This phase is a **new adapter alongside the existing Telegram-bot adapter** (per
ARCHITECTURE.md's hexagonal rule) — nothing in `src/domain/**` or `src/application/**` changes
its business logic, only its callers change. Every `api/**` handler's job is to reproduce the
*shape* of `src/bot/handlers/correction.ts`'s dispatch discipline (ack → parse → resolve identity
→ scoped read → expiry gate → dispatch → translate result) using HTTP status codes instead of
`editMessageText` redraws.

## Pattern Assignments

### `api/_lib/resolve-user.ts` (service, CRUD-read)

**Analog:** `src/application/limits.ts` (`findOnboardedUser`)

**Core pattern** (`src/application/limits.ts:91-108`):
```typescript
export async function findOnboardedUser(
  db: Db,
  telegramId: number,
): Promise<{ id: number; timezone: string } | null> {
  const rows = await db
    .select({ id: users.id, onboardedAt: users.onboardedAt, timezone: users.timezone })
    .from(users)
    .where(eq(users.telegramId, telegramId))
    .limit(1);

  const user = rows[0];
  if (user === undefined || user.onboardedAt === null) {
    return null;
  }
  // users.timezone is NOT NULL with a default -- no fallback literal here.
  ...
}
```
**What to copy:** `resolve-user.ts` should call this SAME function (import it, don't reimplement
it) — `findOnboardedUser(db, parsed.user.id)` where `parsed` is `validateAndParse(...)`'s output.
Do not write a second `users` lookup query. This satisfies both DRY and the "resolve `userId` from
validated `initData` only" security rule (Pitfall 1 in RESEARCH.md).

### `api/_lib/validate-init-data.ts` (middleware, request-response)

**Analog:** RESEARCH.md Pattern 1 (no in-repo HMAC precedent exists — this is genuinely new
ground) + the auth-gate STRUCTURE of `src/bot/middleware/allowlist.ts` (fail-closed, one
responsibility, called before any business logic).

**Pattern to copy (structure, not literal auth mechanism)** — every `api/drafts/[id]/*.ts` handler
must run this FIRST, exactly like `correction.ts`'s step 1-3 gate order:
```typescript
// RESEARCH.md Pattern 1, already vetted against official Telegram docs
import { validate, parse } from '@tma.js/init-data-node';

const MAX_AUTH_AGE_SECONDS = 3600;

export function validateAndParse(rawInitData: string, botToken: string) {
  validate(rawInitData, botToken, { expiresIn: MAX_AUTH_AGE_SECONDS });
  return parse(rawInitData); // throws on invalid signature or stale auth_date
}
```
**Error handling pattern:** mirror `correction.ts`'s "never guess, return early" discipline —
missing/invalid `initData` → `401`, unknown user → `403` (`not_onboarded`), never a `500` for an
expected auth failure.

### `api/drafts/[id]/swap-candidate.ts` (controller, CRUD-update) — reference for ALL mutation endpoints

**Analog:** `src/application/corrections.ts`'s `swapCandidate` (business logic, unchanged) +
`src/bot/handlers/correction.ts`'s `case 'cand'` (dispatch shape, translated to HTTP)

**Imports pattern** (RESEARCH.md, already the exact target file):
```typescript
import type { VercelRequest, VercelResponse } from '@vercel/node';
import { z } from 'zod';
import { swapCandidate } from '../../../src/application/corrections.js';
import { validateAndParse } from '../../_lib/validate-init-data.js';
import { resolveUser } from '../../_lib/resolve-user.js';
import { db } from '../../_lib/db.js';
```

**Auth + validation + dispatch pattern** (full worked example, RESEARCH.md Pattern 2 — this is the
template every other `api/drafts/[id]/*.ts` file should copy verbatim, swapping only the Zod
schema and the `application/*` call):
```typescript
const Body = z.object({ componentIndex: z.number().int(), candidateIndex: z.number().int() });

export default async function handler(req: VercelRequest, res: VercelResponse) {
  const initData = req.headers.authorization?.replace(/^tma\s+/, '');
  if (!initData) return res.status(401).json({ error: 'missing_init_data' });

  let parsed;
  try {
    parsed = validateAndParse(initData, process.env.TELEGRAM_BOT_TOKEN!);
  } catch {
    return res.status(401).json({ error: 'invalid_init_data' });
  }

  const user = await resolveUser(db, parsed.user?.id);
  if (!user) return res.status(403).json({ error: 'not_onboarded' });

  const body = Body.safeParse(req.body);
  if (!body.success) return res.status(400).json({ error: 'invalid_body' });

  const draftId = Number(req.query.id);
  const result = await swapCandidate(db, draftId, user.id, body.data.componentIndex, body.data.candidateIndex);
  if (!result.ok) return res.status(422).json({ error: result.reason });
  return res.status(200).json({ components: result.components });
}
```

**CORRECT-08 recompute guard — copy from `correction.ts`'s `case 'cand'`/`case 'gm'`/`case 'rm'`**
(`src/bot/handlers/correction.ts:257-260, 278-281, 310-312`): every mutation endpoint whose
underlying draft may already be `status === 'confirmed'` must call `recomputeSavedEntry` after a
successful mutation, exactly like the bot handler does:
```typescript
if (draft.status === 'confirmed') {
  await recomputeSavedEntry(d.db, cb.draftId, user.id);
}
```
This means each mutation endpoint (`swap-candidate.ts`, `adjust-grams.ts`, `typed-grams.ts`,
`remove-component.ts`, `add-component.ts`) needs a scoped `readDraft` (or the result of its own
mutation call, which already reports `ok`) to check `status` before or after mutating, and call
`recomputeSavedEntry` when true — this was the exact bug (04-UAT rounds 3-4 / CR-02) that
triggered this whole phase; do not drop this guard when porting to HTTP.

### `api/drafts/[id].ts` (GET, controller, CRUD-read)

**Analog:** `src/application/draft-store.ts`'s `readDraft` + `correction.ts`'s steps 3-5 (identity
→ scoped read → status/expiry gate)

**Core pattern** (`src/bot/handlers/correction.ts:181-203`, translate the `editText(...)` calls to
HTTP status codes instead):
```typescript
const user = await findOnboardedUser(d.db, telegramId);
if (!user) { /* -> 403 not_onboarded, was pipelineCopy.notOnboarded */ }

const draft = await readDraft(d.db, cb.draftId, user.id);
if (!draft) { /* -> 404, was correctionCopy.notYours (byte-identical text to expired — IDOR rule) */ }

if (draft.status === 'abandoned') { /* -> 410, was correctionCopy.expired */ }
if (isDraftExpired(draft.status, draft.createdAt, now())) {
  await markDraftStatus(d.db, cb.draftId, user.id, 'abandoned');
  /* -> 410, was correctionCopy.expired */
}
```
**IDOR rule to preserve exactly (from `draft-store.ts`'s module header):** the 404 for "belongs to
another user" and the 404/410 for "expired" must be indistinguishable to the client — this is
already true because `readDraft` returns `null` for both "doesn't exist" and "belongs to someone
else", and UI-SPEC.md's copy table explicitly requires the expired/not-yours strings to stay
byte-identical. Do not add a different HTTP status or error body that leaks which case occurred.

## Shared Patterns

### Auth boundary — re-validate `initData` on every request, never trust client-asserted identity
**Source:** RESEARCH.md Pattern 1 + `src/bot/middleware/allowlist.ts`'s fail-closed structural
precedent (bot equivalent: `ctx.from.id` + allowlist check happens before any handler logic runs)
**Apply to:** every file under `api/drafts/[id]/*.ts` and `api/drafts/[id].ts` — no exceptions,
no endpoint skips this because "it's just a read."
```typescript
const initData = req.headers.authorization?.replace(/^tma\s+/, '');
if (!initData) return res.status(401).json({ error: 'missing_init_data' });
const parsed = validateAndParse(initData, process.env.TELEGRAM_BOT_TOKEN!); // throws -> 401
const user = await resolveUser(db, parsed.user?.id); // null -> 403
```

### IDOR scoping — every draft read/write is `(draftId, userId)`, never `draftId` alone
**Source:** `src/application/draft-store.ts` module header + every exported function's
`and(eq(diaryDrafts.id, draftId), eq(diaryDrafts.userId, userId))` where-clause
**Apply to:** every `api/drafts/[id]/*.ts` handler — `userId` MUST come from `resolveUser(...)`'s
result (itself derived from validated `initData`), never from `req.query`/`req.body`. This is
already enforced by the underlying `application/*` functions' signatures — the API layer's job is
simply to never bypass them with a raw query.

### Result-discriminated-union → HTTP status mapping
**Source:** every `application/*` function already returns `{ ok: true, ... } | { ok: false,
reason: ... }` (see `corrections.ts`'s `CorrectionResult`, `confirm-meal.ts`'s `ConfirmMealResult`/
`RecomputeSavedEntryResult`/`DeleteSavedEntryResult`)
**Apply to:** every controller file — translate `ok: false` reasons to HTTP status per this table
(planner should lock this exact mapping so it's consistent across all 8 endpoints):

| `reason` | HTTP status |
|---|---|
| `not_found` | 404 |
| `expired` / `no_local_date` | 410 |
| `blocked` / `empty` / `out_of_range` / `invalid_grams` / `text_too_long` / `empty_text` / `match_failed` | 422 |
| `already_confirmed` / `already_deleted` | 200 (idempotent no-op, re-read current state) |
| `write_failed` | 500 |

### CORRECT-08 recompute-on-mutation guard
**Source:** `src/bot/handlers/correction.ts` — every mutation case (`'cand'`, `'gm'/'gp'`, `'rm'`)
checks `if (draft.status === 'confirmed') { await recomputeSavedEntry(...); }` after a successful
write; `handleAwaitingText`'s `typed_grams` and `add_component` branches repeat the same guard
(gap-closure CR-02, `correction.ts:539-544, 572-577`).
**Apply to:** `swap-candidate.ts`, `adjust-grams.ts`, `typed-grams.ts`, `remove-component.ts`,
`add-component.ts` — every one of these MUST re-check the draft's status and call
`recomputeSavedEntry` when the draft being mutated is already saved. This is the exact defect
class (04-UAT rounds 3-4) that motivated this entire phase's existence — do not regress it while
porting to HTTP.

### Logging discipline — never log transcript/component text
**Source:** module headers in `draft-store.ts`, `corrections.ts`, `confirm-meal.ts` (all: "logs
only the draft id and the operation name, never transcript/component text — health data")
**Apply to:** every `api/**` file's `catch`/error-log lines — mirror exactly:
```typescript
console.error(`swap-candidate: failed for draft ${draftId} (${result.reason})`);
```
never interpolate `req.body`, component names, or transcript into a log line.

### Test fakes / dependency injection shape
**Source:** `src/bot/handlers/correction.test.ts` (`makeDeps`, injectable overrides on
`CorrectionHandlerDeps`, `makeCtx`/`makeTextCtx` fake builders) and
`src/application/limits.test.ts` (pure fakes for `Db`-shaped params)
**Apply to:** every `api/**/__tests__/*.test.ts` — each `application/*` function should be
injectable/mockable the same way `correction.ts`'s handlers accept
`swapCandidate?: typeof swapCandidateReal` overrides; build a small local
`VercelRequest`/`VercelResponse` fake (per RESEARCH.md's Wave 0 gap list) instead of a real Vercel
dev server, mirroring how `correction.test.ts`'s `makeCtx` avoids a real grammY `Context`.

## Decisions Made

### No `swap-candidate.ts` template existed at execution time

The plan's Task 1 `<read_first>` and `<action>` instructed copying `api/drafts/[id]/swap-candidate.ts` (plan 05's structural template) "exactly." That file does not exist in this worktree — plan 05 is a sibling wave-3 plan running concurrently in a separate worktree and had not merged into `main` as of this plan's execution. `remove-component.ts` was instead built directly from the already-merged plan 03 shared library (`api/_lib/http.ts`, `api/_lib/draft-response.ts`) and `src/application/corrections.ts`/`src/bot/handlers/correction.ts`'s `case 'rm'`, reproducing the same factory shape (`createXHandler(deps)` + default export), the same zod `safeParse` 400 path, and the same `status === 'confirmed' -> recomputeSavedEntry` guard the plan's acceptance criteria require. `add-component.ts` (Task 3) was then built from `remove-component.ts`'s own just-written structure, as the plan's Task 3 `<read_first>` originally intended relative to Task 1's output. This is not a Rule 4 architectural deviation — the plan's acceptance criteria, `<behavior>` bullets, and `<interfaces>` section fully specify the required shape independent of the missing template file, and every acceptance criterion passes.

### `readDraft` injected as a fourth handler dependency

`CorrectionResult` (`src/application/corrections.ts`'s shared discriminated-union return type for `removeComponent`/`addComponent`) carries only `{ ok: true; components: DraftComponent[] }` on success — no `status`/`localDate`/`diaryId`. Both endpoints need those three fields to (a) build the `DraftResponse` envelope's `status`/`localDate`/`saved` and (b) decide whether to call `recomputeSavedEntry`. Rather than widen `CorrectionResult` (a `src/application/` shared type touching plan 04/05/07's endpoints too — out of this plan's file scope) both endpoints call `readDraft(db, draftId, user.id)` a second time, AFTER a successful mutation, exactly mirroring how `src/bot/handlers/correction.ts`'s callback handler already reads the draft once up front and reuses `draft.status` for its own recompute guard. `readDraft` is exposed as an optional injectable dependency (`readDraft?: typeof readDraftReal`) on both handlers' deps interfaces, defaulting to the real `draft-store.ts` implementation, so tests can supply a fake without touching Postgres — consistent with how `src/bot/handlers/correction.ts`'s `CorrectionHandlerDeps` already injects `readDraft` alongside its other overridable collaborators.

## Decisions Made

### `@tma.js/init-data-node@2.0.8`'s real exported API (RESEARCH.md's [ASSUMED] flag resolved)

Confirmed directly from the installed package's own `.d.ts` files
(`node_modules/@tma.js/init-data-node/dist/entries/node.d.ts`,
`dist/validation.d.ts`, `dist/parsing.d.ts`), not from memory or the research
document's guess:

- `validate(value: string | URLSearchParams, token: string, options?: { expiresIn?: number; tokenHashed?: boolean }): void` —
  throws one of `SignatureMissingError | SignatureInvalidError |
  AuthDateInvalidError | ExpiredError` (all ordinary `Error` subclasses from
  the `error-kid` package) on any failure; never returns a partial object.
  `expiresIn` **defaults to 86400 seconds (1 day) when omitted** — this
  project passes `MAX_AUTH_AGE_SECONDS = 3600` explicitly, confirmed
  load-bearing by a deliberate-break test (see Acceptance Criteria below).
- `parse(value: string | URLSearchParams)` — returns the parsed object
  (`{ user?: { id: number; first_name: string; ... }, auth_date, hash,
  ... }`); called only after `validate()` in `validateAndParse`.
- `sign(data: SignableData, key: Text, authDate: Date, options?: SignOptions): string` —
  exported directly from the package's own node entrypoint; used by this
  plan's own test suite (`validate-init-data.test.ts`) to build a genuinely
  valid signed `initData` string, in place of hand-rolling `node:crypto`
  HMAC or trusting a manually-constructed fixture.

This was verified live with a throwaway script run against the real
installed package (deleted before commit, never part of the repo): a
correctly signed fresh `initData` validates; an altered `hash` throws
`SignatureInvalidError`; a wrong bot token throws `SignatureInvalidError`; a
stale `auth_date` throws `ExpiredError`; an empty string throws
`SignatureMissingError`.

### `@vercel/node`'s body-parsing behavior (RESEARCH.md's open question resolved)

`@vercel/node@10.0.0`'s `VercelRequest` type
(`node_modules/@vercel/node/dist/index.d.ts`) declares `body:
VercelRequestBody` as an explicit field added on top of Node's
`IncomingMessage` (which has no `body` field of its own — it is a raw
stream). This confirms Vercel's Node.js Serverless Function runtime
pre-parses the request body based on `Content-Type` before a handler ever
sees `req`, matching Vercel's own documented behavior. **No
`readJsonBody(req)` helper was written** — endpoints in plans 04-07 read
`req.body` directly.

### The exact `DraftResponse` interface (plans 04-08's source of truth)

```typescript
export interface DraftResponse {
  draftId: number;
  status: 'draft' | 'confirmed' | 'abandoned';
  saved: boolean;
  localDate: string | null;
  components: DraftComponent[];
  total: NutrientTotal;
  contributingCount: number;
  blockedComponent: string | null;
}
```

`mini-app/src/types.ts` (plan 08) must mirror this by hand — this file
(`api/_lib/draft-response.ts`) is the source of truth for that mirror.

### `fakes.ts`'s `FakeRes.statusCode` sentinel

Node's `ServerResponse.statusCode` type is `number` (not `number | null`),
which `VercelResponse` inherits. The original draft of `FakeRes` declared
`statusCode: number | null` to represent "no response written yet," which
`npx tsc --noEmit` correctly rejected as an incompatible override. Fixed by
initializing `statusCode` to `0` — never a valid HTTP status — as the "not
yet set" sentinel, and updated the one test asserting on it
(`requireUser`'s "valid initData for an onboarded user" case) to check
`toBe(0)` instead of `toBeNull()`.

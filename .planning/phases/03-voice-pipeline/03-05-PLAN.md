  <action>
Create `src/application/idempotency.ts` implementing 03-RESEARCH.md Pattern 4.

`claimUpdate` inserts one `processedUpdates` row with `status: 'processing'`
and the caller-supplied `telegramId`, `chatId` and `kind`, using
`.onConflictDoNothing({ target: processedUpdates.updateId }).returning({ updateId: processedUpdates.updateId })`,
and returns `rows.length > 0`. The module doc comment must spell out the
ordering rule this function exists to enforce, because it is the phase's main
spend control: the claim is written BEFORE the audio download and before every
paid API call, so a Telegram redelivery of the same `update_id` (which happens
on network hiccups and on restart) loses the race at the database level and
returns silently instead of buying a second transcription. It must also record
why an in-memory `Set` was rejected (D-10): it dies with the process, i.e. in
exactly the crash-restart case it would exist to protect against.

`markUpdateStatus(db, updateId, status)` updates `status` and `updatedAt` where
`updateId` matches. Take the status as a `ProcessedUpdateStatus` parameter
rather than writing four near-identical functions.

`findInterruptedUpdates(db)` selects `updateId`, `chatId` and `telegramId` from
rows where `status = 'processing'`. This is the D-11 startup sweep's query: a
row still in `processing` when the process starts means a previous run died
mid-pipeline. Document explicitly that the caller notifies the user and then
calls `markInterrupted` — there is deliberately no resume, because the audio is
gone by design (D-05) and a half-resume is not worth the complexity in a closed
beta.

`markInterrupted(db, updateIds)` sets `status = 'interrupted'` for the given
ids using `inArray`, and returns immediately without issuing a query when the
array is empty (an `inArray` with an empty list is a footgun in SQL).

Nothing in this module may import `grammy`, and nothing may hold module-level
state.

Write `src/application/idempotency.test.ts` covering every behaviour bullet
using a hand-built fake `db` object in the style of
`pg-storage-adapter.test.ts` — a structural stub whose `insert`/`update`/`select`
chains record what was called and return canned rows. Assert call counts, not
just return values: "returns false" and "returns false without issuing another
query" are different guarantees, and only the second one protects spend.

Create `src/application/limits.ts`.

`countRecentUpdates(db, telegramId, windowHours = 24)` counts `processedUpdates`
rows for that `telegramId` whose `createdAt` is within the trailing window,
using Drizzle's `count()` with a `gte` on a timestamp computed in JavaScript
(`new Date(Date.now() - windowHours * 3600_000)`) rather than SQL date
arithmetic — the query then matches the `(telegram_id, created_at)` index shape
from plan 03-02 exactly. Use a rolling window, not a calendar day, and document
why: a calendar day needs the user's timezone, which is a Phase 4/diary
concern, and D-15 is a runaway guard where "roughly a day" is precise enough.

`isDailyCapReached(db, telegramId)` returns `count >= DAILY_MESSAGE_CAP`. Wrap
the count in a try/catch that logs one short Russian operator line naming the
failure kind only (no telegram id, no message content) and returns `false` —
document the reasoning inline: D-15 is a guard against a loop, not a paywall,
so a database hiccup in the guard must fail open toward the user rather than
silently swallowing their meal. Everything that actually costs money is still
gated by `claimUpdate` and by the 60-second duration cap.

`findOnboardedUser(db, telegramId)` selects `users.id` where
`telegramId` matches and `onboardedAt is not null`, returning `{ id }` or null.
Document why this exists: `diary_drafts.user_id` is a foreign key to `users.id`
(plan 03-02), so a user who is on the beta allowlist but has never finished
/start has no row to reference. Detecting that before the paid calls turns a
late foreign-key crash into an immediate, actionable Russian reply
(`pipelineCopy.notOnboarded`).

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Telegram update stream → paid API calls | every update is a potential spend event; this module is the gate in front of it |
| process lifetime → durable state | a crash mid-pipeline must leave a detectable record, not a silent hole |
| one user → shared OpenAI budget | one looping or confused user must not be able to drain the account |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-03-22 | Denial of Service (financial) | duplicate/retried Telegram delivery | mitigate | `claimUpdate` uses `onConflictDoNothing().returning()` on the `update_id` primary key and returns false without further queries; callers must invoke it before the download and before any paid call (asserted in plan 03-07's handler tests) |
| T-03-23 | Denial of Service (financial) | single-user runaway loop | mitigate | `isDailyCapReached` enforces `DAILY_MESSAGE_CAP = 30` over a rolling 24 h window using the `(telegram_id, created_at)` index |
| T-03-24 | Denial of Service (availability) | the limit check itself failing | mitigate | the count is wrapped in try/catch and fails open to `false`, so a database hiccup in the guard cannot lock a legitimate user out; spend remains bounded by `claimUpdate` and the 60 s duration cap |
| T-03-25 | Information Disclosure | operator logging in the limit path | mitigate | the catch logs a fixed Russian string plus the error kind only — never the telegram id, never message content, matching `error-handler.ts` |
| T-03-26 | Repudiation | crash mid-pipeline leaving no trace | mitigate | rows persist in `processing` and are surfaced by `findInterruptedUpdates` at startup, then moved to the terminal `interrupted` status by `markInterrupted` (D-11) |
| T-03-27 | Elevation of Privilege | a non-onboarded allowlisted user writing a draft | mitigate | `findOnboardedUser` requires a `users` row with `onboardedAt` set before a draft can be created, backed by the `diary_drafts.user_id` foreign key |
| T-03-28 | Denial of Service | unbounded growth of `processed_updates` | accept | one row per message in a closed beta is negligible; a retention/purge job is deferred until real user volume exists |
</threat_model>

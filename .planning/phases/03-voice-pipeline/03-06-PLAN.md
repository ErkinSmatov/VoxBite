<objective>
Build `processMeal()` — the single, Telegram-agnostic orchestrator that turns
either an audio Buffer or a typed string into a persisted draft and a rendered
card, plus the draft writer and the per-message cost line.

Purpose: this is where the phase's chain actually becomes one thing. Every
decision about ordering, failure handling and what the user sees lives here,
behind injected ports, so it is unit-testable end to end with zero network and
zero Telegram.

`src/application/cost-log.ts` with tests.

Create `src/application/voice-pipeline.ts` exporting `processMeal(deps, args)`,
the orchestrator described in 03-RESEARCH.md's system architecture diagram. It
takes every collaborator through `PipelineDeps` and constructs nothing itself
(ARCHITECTURE.md Pattern 3). It must not import `grammy` — the only way it
touches Telegram is through the injected `MessageEditor` from plan 03-03.

Order of operations, and this order is the contract:
1. Obtain the transcript. For `kind: 'voice'`, call `transcriber.transcribe(audio)`
   and keep `{ text, usage, model }`. For `kind: 'text'`, use the text directly
   and record no STT usage. This branch is the ONLY difference between the two
   input types — VOICE-04 is satisfied by everything after it being shared code,
   not by a parallel implementation.
2. Call `decomposer.decompose(transcript)`.
3. If `items` is empty, this is D-08's normal answer: edit the ack message into
   `pipelineCopy.noFood`, mark the update `done`, log the cost line, and return.
   Do not write a draft, do not retry.
4. Otherwise embed all `component_en` values in ONE `embedder.embed([...])`
   call (the port already batches; N single-text calls is 03-RESEARCH.md Pitfall
   2), then run `matchIngredient({ embedding, repo })` for each returned vector
   with `Promise.all`. Never query pgvector directly and never re-rank — the
   `matchIngredient` barrel is the only entry point, and the repository's
   `ORDER BY cosineDistance` ordering is a Phase 1 invariant that hand-written
   query code would silently regress.
5. Build `DraftComponent[]`: map `component_en` to camelCase `componentEn`,
   carry the candidates through unchanged, set `chosenFdcId` to the top
   candidate's `fdcId` (or null when there are none) and `weakMatch` via the
   shared `isWeakMatch` helper. Never drop a component for any reason (D-21).
6. `saveDraft` the row: userId, updateId, chatId, messageId = ackMessageId,
   source, transcript, components, status 'draft'.
7. `editor.editMessage(chatId, ackMessageId, buildResultCard(draft))` — D-13,
   the same message the handler already sent, edited in place, which is also
   what gives Phase 4 a stable message id for its keyboard.
8. `markUpdateStatus(db, updateId, 'done')` and one `logCost(...)` call.

Failure handling — 03-RESEARCH.md Pitfall 6 is the governing rule: this
function is invoked as a detached promise, so `bot.catch()` will never see its
errors, and an unhandled failure leaves the user staring at "Секунду, разбираю
🎧" forever. Therefore `processMeal` must never reject. Wrap the body so that
every failure path (a) edits the ack message into the right Russian copy —
`sttFailed`, `decompositionFailed` (on `DecompositionFailedError`), or
`internalError` for anything else — (b) marks the update `failed`, and (c) logs
one short operator line containing the failure kind and the update id only,
never the transcript, never the ctx, never a token (the `error-handler.ts`
invariant). If the ack edit itself fails, swallow it after logging: there is no
better recovery, and throwing would produce exactly the unhandled rejection
this design exists to prevent.

Never write the audio Buffer anywhere and never place it in a log or in the
draft (D-05). The transcript IS persisted — it is needed by Phase 4 and is the
only way to distinguish an STT error from an LLM error after the fact.

Write `src/application/voice-pipeline.test.ts` covering every behaviour bullet
with hand-built fakes for all six dependencies, in the style of
`match-ingredient.test.ts` (fake repository) and
`pg-storage-adapter.test.ts` (fake db). Assert call counts, not only outcomes:
"embed called once with two names" and "transcribe never called for text input"
are the two assertions that actually protect Pitfall 2 and VOICE-04.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| audio Buffer / transcript → persistence and logs | the most sensitive data in the product crosses this boundary (voice plus dietary/health information) |
| LLM output → Postgres and the user's screen | untrusted model output becomes stored state and displayed text |
| detached promise → error visibility | this function runs outside grammY's dispatch, so its errors are invisible to `bot.catch()` |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-03-29 | Information Disclosure | audio Buffer inside `processMeal` | mitigate | the Buffer is passed to `transcriber.transcribe` and never stored, never logged, never written to `diary_drafts`; grep gate in acceptance criteria and D-05 stated in the module doc comment |
| T-03-30 | Information Disclosure | transcript in error logs | mitigate | every catch logs only the failure kind and the update id; `CostInputs` structurally cannot carry user content; `pipeline-copy.ts` strings are constants that never interpolate an exception message |
| T-03-31 | Tampering (data integrity) | LLM output reaching `diary_drafts` | mitigate | only values that passed `DecompositionSchema` (plan 03-04) are mapped into `DraftComponent`; grams bounds and item count are already enforced before this function sees them |
| T-03-32 | Denial of Service (financial) | per-component embedding fan-out | mitigate | one batched `embed()` call for all components plus a schema cap of 15 items bounds the paid calls per message to a constant |
| T-03-33 | Denial of Service (availability) | unhandled rejection in a detached promise | mitigate | `processMeal` never rejects; every path edits the ack message and marks the ledger row `failed`, so a user is never left on a permanent "Секунду, разбираю" and a stuck row is never invisible |
| T-03-34 | Repudiation | a failed run leaving the ledger in `processing` | mitigate | `markUpdateStatus(..., 'failed')` on every failure path; anything that still dies (process kill) is caught by the D-11 startup sweep in plan 03-08 |
| T-03-35 | Tampering | bypassing the Phase 1 vector-search ordering invariant | mitigate | matching goes exclusively through the `src/domain/fdc-matching` barrel; grep gate forbids `cosineDistance`/pg-core imports in this file |
| T-03-36 | Information Disclosure | transcript stored in Postgres | accept | required by Phase 4 and by post-hoc STT-vs-LLM error diagnosis (D-05 explicitly persists it); protected by RLS from plan 03-02 rather than by not storing it |
</threat_model>

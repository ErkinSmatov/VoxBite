`createVoiceHandler` performs, in this exact order:
1. `claimUpdate({ db, updateId: ctx.update.update_id, telegramId, chatId, kind: 'voice' })`.
   If it returns false, `return` immediately — no reply, no cost. This is
   D-10's whole purpose, and it must be the first statement that can have an
   effect, so a Telegram redelivery cannot buy a second transcription.
2. `findOnboardedUser` — if null, reply `pipelineCopy.notOnboarded`, mark the
   update `done`, return. Checked before spending because the draft's foreign
   key would fail later anyway.
3. `isDailyCapReached` — if true, reply `pipelineCopy.dailyCapReached`, mark
   `done`, return (D-15).
4. `downloadVoice(ctx, token)` inside try/catch. `VoiceTooLongError` → reply
   `pipelineCopy.tooLong`, mark `failed`, return (D-14). Any other error →
   reply `pipelineCopy.internalError`, mark `failed`, return.
5. `const ack = await ctx.reply(pipelineCopy.ack)` — VOICE-02/D-13, one message
   whose `message_id` the pipeline later edits in place.
6. Fire `processMeal(...)` WITHOUT awaiting it: `void processMeal(...).catch(...)`.
   The comment above it must state why, because it looks like a bug otherwise:
   grammY awaits handlers in its dispatch loop, so awaiting the whole pipeline
   here would serialise every user behind one slow analysis and break D-12
   ("three voice messages in a row are all processed"). The local `.catch` is
   mandatory — `bot.catch()` cannot see a promise that outlives the handler
   (03-RESEARCH.md Pitfall 6) — and it logs only the update id and the error
   kind, never the ctx and never the transcript.

`createUnsupportedHandler` replies `pipelineCopy.unsupportedMessage` and does

nothing). Plan 03-08 registers it for `message:audio`, `message:video_note`,
`message:photo`, `message:document`, `message:sticker` and `message:video`.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Telegram update → this process | fully untrusted input: message type, duration, text content, and delivery count are all outside our control |
| this process → Telegram file CDN | the request URL carries the bot token in its path |
| handler → paid pipeline | every statement after the claim can cost money |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-03-37 | Denial of Service (financial) | held-microphone / very long voice | mitigate | `downloadVoice` rejects on `duration > MAX_VOICE_SECONDS` before `getFile()` is called, asserted by a test that `getFile` was never invoked (D-14) |
| T-03-38 | Denial of Service (financial) | duplicate Telegram delivery | mitigate | `claimUpdate` is the first effectful statement in both handlers; a false result returns with no reply and no download, asserted by a call-order test (D-10) |
| T-03-39 | Denial of Service (financial) | unbounded pasted text reaching the LLM | mitigate | `MAX_TEXT_LENGTH = 1000` bounds the text branch, mirroring the duration cap on the voice branch |
| T-03-40 | Denial of Service (financial) | unsupported message types triggering work | mitigate | `createUnsupportedHandler` replies and returns without claiming, downloading or invoking the pipeline (D-06) |
| T-03-41 | Information Disclosure | bot token in the file-download URL | mitigate | the URL is constructed locally and never logged, never embedded in an error message; asserted by a test that no thrown message contains the token |
| T-03-42 | Information Disclosure | message text (health data) in logs | mitigate | the detached `.catch` logs only the update id and error kind; grep gate forbids logging `ctx` or a stringified update, extending `error-handler.ts`'s invariant |
| T-03-43 | Denial of Service (availability) | one slow analysis blocking all users | mitigate | the pipeline promise is deliberately not awaited inside the handler, asserted by the never-resolving-fake test; satisfies D-12 |
| T-03-44 | Elevation of Privilege | a non-allowlisted user reaching a paid path | mitigate | these handlers are registered after the existing allowlist middleware; enforced and asserted in plan 03-08's wiring test rather than here |
| T-03-45 | Spoofing | forged `update_id` collisions | accept | updates arrive only over the authenticated Telegram long-polling connection using the bot token; there is no inbound HTTP surface in this phase (D-09) |
</threat_model>

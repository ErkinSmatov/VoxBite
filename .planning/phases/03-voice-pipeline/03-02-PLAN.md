Add the two Postgres tables the voice pipeline needs — `processed_updates`
(the idempotency ledger, D-10/D-11) and `diary_drafts` (the persisted draft,

schema-level guarantees, not application conventions.

  <action>
Create `src/db/schema/processed-updates.ts`, one table per file, mirroring
`bot-sessions.ts`'s structure exactly.

Table `processed_updates` columns:
- `updateId` → `bigint('update_id', { mode: 'number' }).primaryKey()` — the
  Telegram `update_id` is the natural key; making it the primary key means the
  database itself rejects a duplicate delivery, which is the whole point of
  D-10. No surrogate id.
- `telegramId` → `bigint('telegram_id', { mode: 'number' }).notNull()` — needed
  by the D-11 startup sweep (which user do we apologise to) and by the D-15
  daily cap (how many did this user send).
- `chatId` → `bigint('chat_id', { mode: 'number' }).notNull()` — the sweep
  sends its message to a chat, not a user id.
- `kind` → `text('kind').notNull().$type<'voice' | 'text'>()`.
- `status` → `text('status').notNull().$type<'processing' | 'done' | 'interrupted' | 'failed'>()`.
- `createdAt`, `updatedAt` → `timestamp(..., { withTimezone: true }).defaultNow().notNull()`.

Table-level extras, using the array-returning second argument shape already
used in `users.ts`:
- `check('processed_updates_status_check', sql\`... in ('processing','done','interrupted','failed')\`)`
- `check('processed_updates_kind_check', sql\`... in ('voice','text')\`)`
- `index('processed_updates_user_day_idx').on(table.telegramId, table.createdAt)`
  — the D-15 daily cap counts rows per user per rolling day; without this index
  that count is a sequential scan that grows forever.

Export `ProcessedUpdateRow`/`NewProcessedUpdate` inferred types and a
`ProcessedUpdateStatus` string-union type alias (imported by plan 03-05).

The doc comment must explain, in the same WHY-first voice as `bot-sessions.ts`:
that this table is the idempotency ledger (D-10), that a row is inserted BEFORE
any paid API call so a retried Telegram delivery can never buy a second
transcription, that `status` exists so a crash mid-pipeline is detectable at
next startup (D-11), and that RLS is enabled with zero policies for the same
reason as `bot_sessions` — Supabase publishes every `public` table through
PostgREST to anyone holding the anon key.

Create `src/db/schema/diary-drafts.ts` for table `diary_drafts`:
- `id` → `integer('id').primaryKey().generatedAlwaysAsIdentity()` (matches `users`).
- `userId` → `integer('user_id').notNull().references(() => users.id, { onDelete: 'cascade' })`.
- `updateId` → `bigint('update_id', { mode: 'number' }).notNull()` — links the draft back to the ledger row that authorised it, so a duplicated update cannot produce two drafts.
- `chatId` → `bigint('chat_id', { mode: 'number' }).notNull()`.
- `messageId` → `bigint('message_id', { mode: 'number' }).notNull()` — the ack message the bot edits in place (D-13) and the anchor Phase 4 hangs its inline keyboard on.
- `source` → `text('source').notNull().$type<'voice' | 'text'>()`.
- `transcript` → `text('transcript').notNull()` — persisted per D-05 (the audio is not; the transcript is the only way to tell an STT error from an LLM error afterwards).
- `components` → `jsonb('components').notNull()` — the array of `{ component, componentEn, grams, candidates, chosenFdcId, weakMatch }`. jsonb, not normalised rows: D-19 gives Phase 4 ownership of any further schema evolution, and normalising now would force Phase 4 to migrate a shape it has not designed yet.
- `status` → `text('status').notNull().default('draft').$type<'draft' | 'confirmed' | 'abandoned'>()`.
- `createdAt`, `updatedAt` → timestamps as above.
- `check('diary_drafts_status_check', ...)`, `check('diary_drafts_source_check', ...)`, `unique('diary_drafts_update_id_key').on(table.updateId)`, and `index('diary_drafts_user_idx').on(table.userId, table.createdAt)`.

Append `export * from './processed-updates';` and `export * from './diary-drafts';`
to `src/db/schema/index.ts` so `createDb()`'s schema object includes them.

Do not write any SQL by hand in this task — the table-creation SQL is
generated in Task 2.

Then hand-write `drizzle/0006_voice_pipeline_rls.sql` by copying
`drizzle/0004_bot_sessions_rls.sql` verbatim twice, substituting the table
names `processed_updates` and `diary_drafts`. Each block does two things:
`ALTER TABLE "<name>" ENABLE ROW LEVEL SECURITY;` and, inside the
`IF EXISTS (SELECT 1 FROM pg_roles WHERE rolname = 'anon')` guard,
`REVOKE ALL ON TABLE "<name>" FROM anon, authenticated;`.

Plain-language note for the owner (put this as a SQL comment at the top of the
file and repeat it in the SUMMARY): Row Level Security is a Postgres switch
that makes a table return zero rows to anyone who has not been explicitly
granted a policy. Supabase automatically exposes every table in the `public`
schema over a public web API, so any table without RLS is readable by anyone
who finds the project's anon key. `diary_drafts` holds what people ate and
`processed_updates` holds Telegram user ids — both need the switch on. The bot
itself connects with the database owner role, which bypasses RLS, so the bot
keeps working normally.

Register `0006_voice_pipeline_rls.sql` in `drizzle/meta/_journal.json` exactly
the way `0004_bot_sessions_rls.sql` was registered (same entry shape, next
index, `breakpoints` flag matching its siblings) — read the existing entry for
0004 and copy its structure. Do not run the migration in this task.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Supabase PostgREST → public internet | every table in the `public` schema is exposed by Supabase's auto-generated API to any holder of the anon key unless RLS is on |
| migration file → live database | applying SQL is irreversible against real data |
| Telegram update stream → `processed_updates` | `update_id` is attacker-influenceable only in the sense that a retried/duplicated delivery must not double-charge |

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-03-06 | Information Disclosure | `diary_drafts` (transcripts = health/diet data) | mitigate | `drizzle/0006_voice_pipeline_rls.sql` enables RLS with zero policies and revokes `anon`/`authenticated`, verified live via the `pg_class.relrowsecurity` query in Task 3 |

# Деплой Mini App на Vercel — что развёрнуто, где и как это менять

> Этот документ — для тебя, если ты никогда раньше не разворачивал (не
> "деплоил") веб-приложение. Термины по ходу: "деплой"/"развернуть" — процесс,
> при котором код из Git-репозитория собирается и выкладывается на публичный
> адрес в интернете; "серверная функция" (serverless function) — маленькая
> программа, которая запускается только когда приходит запрос (например,
> нажатие кнопки в Mini App), а не работает постоянно, как бот; "переменная
> окружения" (environment variable) — секрет или настройка, которая хранится
> не в коде, а в настройках хостинга, поэтому никогда не попадает в Git;
> "редеплой" — повторный запуск сборки и выкладки того же кода (нужен после
> смены переменных окружения).

## Что развёрнуто и где

Vercel — сервис, который берёт код из GitHub-репозитория, собирает его и
выкладывает по публичному https-адресу, повторяя это автоматически при каждом
`git push` в ветку `main`. Устанавливать и обслуживать сервер самому не нужно
— в этом весь смысл выбора Vercel.

- **Проект на Vercel:** `vox-bite`
- **Публичный адрес (production URL):** `https://vox-bite.vercel.app`
- **Что именно там крутится:**
  - Страница Mini App (собирается из папки `mini-app/` командой
    `npm run miniapp:build`, результат кладётся в `mini-app/dist`) —
    отдаётся по любому адресу, кроме `/api/...`.
  - Серверные функции коррекции блюда — файлы из папки `api/` (например,
    `api/drafts/[id].ts`) — отвечают на запросы вида `/api/drafts/123`.
- **GitHub-репозиторий, из которого Vercel берёт код:**
  `https://github.com/ErkinSmatov/VoxBite.git`, ветка `main`.

## Автодеплой — ничего руками делать не нужно

Vercel подключён к GitHub через официальную интеграцию: **каждый `git push`
в ветку `main` автоматически запускает новую сборку и выкладку**. Отдельного
шага "нажать кнопку Deploy" не требуется — если код запушен в `main`, через
1-2 минуты изменения уже на `https://vox-bite.vercel.app`.

## Четыре переменные окружения на Vercel и откуда брать их значения

Настройка находится в: **Vercel → проект `vox-bite` → Settings → Environment
Variables**. Каждая переменная выставлена для окружения "Production".

| Переменная | Откуда берётся |
|---|---|
| `DATABASE_URL` | Та же строка подключения к Supabase, что бот использует локально (см. `DATABASE_URL=` в твоём локальном файле `.env`). Mini App читает и пишет в ту же самую базу данных, что и бот. |
| `TELEGRAM_BOT_TOKEN` | Тот же токен из `@BotFather`, что в локальном `.env`. Используется НЕ для отправки сообщений, а чтобы проверить подпись, которую Telegram прикладывает к каждому открытию Mini App — так сервер понимает, кто именно открыл страницу. |
| `OPENAI_API_KEY` | Тот же ключ, что в локальном `.env`. Нужен только когда в Mini App добавляют недостающий ингредиент вручную (текстом) — это запускает тот же поиск по базе USDA, что использует бот. |
| `MINI_APP_BASE_URL` | Собственный адрес страницы — `https://vox-bite.vercel.app`, без завершающего слэша. |

Если когда-нибудь понадобится изменить одно из этих значений (например,
перевыпустить токен бота) — меняешь его в ДВУХ местах: здесь, на Vercel, И в
локальном файле `.env`. После смены в `.env` бота на своём компьютере нужно
перезапустить (`Ctrl+C`, затем снова `npm run bot`) — иначе он продолжит
работать со старым значением, которое уже загружено в память процесса.

## Если адрес приложения (`MINI_APP_BASE_URL`) когда-нибудь изменится

1. Обнови значение `MINI_APP_BASE_URL` на Vercel (Settings → Environment
   Variables) на новый адрес, без завершающего слэша.
2. Обнови ту же переменную в локальном `.env`.
3. Перезапусти бота на своём компьютере, чтобы он подхватил новое значение.
4. Сделай Redeploy на Vercel (Deployments → на нужной сборке → "..." →
   Redeploy), чтобы серверные функции тоже увидели новое значение — иначе
   старое значение останется закешированным в уже запущенной функции до
   следующего обычного деплоя.
5. Если у бота уже есть открытая кнопка "Open" с ссылкой на старый адрес —
   она обновится сама после следующего сообщения бота (кнопка строится
   заново на каждое сообщение), никакого отдельного шага в Telegram не
   требуется. Домен в @BotFather менять не нужно, если новый адрес — это
   тот же проект Vercel (`vox-bite.vercel.app`); если ты создашь СОВСЕМ
   новый проект Vercel с другим адресом — тогда нужно заново зарегистрировать
   новый домен через @BotFather (шаг "Menu Button → Configure Menu Button",
   как при первом деплое).

## Как найти лог сборки, если что-то сломалось

1. Открой проект `vox-bite` на vercel.com.
2. Вкладка **Deployments** — список всех сборок, самая свежая сверху.
3. Если статус сборки — "Error", кликни на неё и открой **"Build Logs"** —
   там будет текст ошибки. Скопируй последние ~20 строк и покажи их
   разработчику/ассистенту — по этому логу почти всегда сразу понятно, что
   не так.
4. Если сборка завершилась статусом "Ready", но сама страница или кнопки
   в Mini App работают не так, как ожидалось — открой ту же сборку и
   вкладку **"Functions"** → выбери нужную функцию (например,
   `api/drafts/[id]`) → **"Logs"** (иногда подписано "Runtime Logs"). Там
   видно, что происходит уже ПОСЛЕ успешной сборки, когда кто-то реально
   открывает Mini App или нажимает кнопку — именно так на этой фазе была
   найдена и исправлена реальная причина ошибки 500 (см. раздел ниже).

## Контингент: если Mini App начнёт сообщать об ошибках подключения к базе при нагрузке

Serverless-функции Vercel — короткоживущие, и при одновременном использовании
многими людьми могут открывать много параллельных подключений к базе данных.
Если появятся ошибки вида "too many connections" именно у Mini App (не у
бота) — решение: переключить `DATABASE_URL` **только для Vercel-проекта**
на порт transaction-mode pooler Supabase (порт 6543 вместо 5432, вкладка
Supabase Dashboard → Connect → Transaction pooler).

**Важно:** это НЕ относится к `DATABASE_URL` самого бота — бот должен
оставаться на session pooler (порт 5432), потому что миграциям
(`npm run db:migrate`) и части других запросов бота нужны prepared
statements, которые transaction-mode pooler не поддерживает. Значит после
этой фазы у бота и у Mini App впервые могут оказаться РАЗНЫЕ значения
`DATABASE_URL` — это ожидаемо и нормально, если до этого дойдёт.

На момент написания этого документа (после реального теста через `curl`,
раздел ниже) переключать пока не потребовалось — это чисто предупредительная
инструкция на будущее.

## Что реально пошло не так при первом деплое (для истории)

Первый деплой этой фазы столкнулся с двумя настоящими проблемами, обе
исправлены и проверены "живым" запросом к развёрнутому адресу:

1. **GitHub был на 342 коммита позади локального кода** — вся фаза 04.1
   (включая `vercel.json`, папку `api/`, папку `mini-app/`) существовала
   только на компьютере разработчика и никогда не была отправлена (`git
   push`) в GitHub. Vercel честно развернул то, что реально было на
   GitHub — старый код без Mini App вообще, отсюда `404` на любой адрес.
   Исправление: `git push origin main` (обычный fast-forward, без
   конфликтов).
2. **Относительные импорты внутри `api/` и `src/` были без расширения
   `.js`** (например, `from '../_lib/db'` вместо `from '../_lib/db.js'`).
   Локально (тесты, typecheck) это работало нормально, но реальный
   серверный движок Vercel запускает собранный код напрямую через
   встроенный в Node.js загрузчик модулей `ESM`, который — в отличие от
   локальных инструментов сборки — требует явное расширение `.js` у
   каждого относительного импорта. Без этого КАЖДАЯ серверная функция
   падала с ошибкой вида:
   ```
   Error [ERR_MODULE_NOT_FOUND]: Cannot find module '/var/task/api/_lib/db'
   imported from /var/task/api/drafts/[id].js
   ```
   Исправление заняло два прохода: сначала расширения добавили только в
   `api/**`, но та же проблема тут же всплыла в файлах `src/**`, которые
   `api/**` тоже использует (например, `src/db/schema/index.ts`) — поэтому
   вторым проходом расширения `.js` добавили ко ВСЕМ относительным импортам
   и в `src/**`, и в `api/**`, одним разом, чтобы не гоняться за одной
   ошибкой за раз через несколько циклов "деплой → лог → фикс".

Обе проблемы находятся в самом коде, а не в настройках Vercel — они уже
исправлены в репозитории, повторно настраивать ничего не нужно.

## Проверка, что всё развёрнуто правильно (для истории, автоматические тесты)

- `GET https://vox-bite.vercel.app/` → `200`, HTML-страница со ссылкой на
  `telegram-web-app.js` (страница Mini App открывается).
- `GET https://vox-bite.vercel.app/api/drafts/1` без заголовка авторизации
  → `401 {"error":"missing_init_data"}` (сервер отказывает без подписи
  Telegram — граница защиты работает).
- `GET https://vox-bite.vercel.app/api/drafts/1` с поддельным заголовком
  `Authorization: tma garbage` → `401 {"error":"invalid_init_data"}`
  (поддельная подпись тоже отклоняется, а не пропускается по ошибке).
- `GET https://vox-bite.vercel.app/api/drafts/abc` (нечисловой id) без
  авторизации → `401` (проверка личности выполняется раньше разбора id, а
  не наоборот — значит на нечисловой id нет отдельной "дыры").

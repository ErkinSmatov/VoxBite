# Ручная проверка Phase 4.1 — коррекция блюда в Telegram Mini App

> Этот документ — для тебя, если ты никогда раньше не открывал Mini App внутри
> Telegram и не работал с задеплоенным веб-приложением.
>
> Термины по ходу:
> - **Mini App** — маленькое веб-приложение, которое открывается ВНУТРИ
>   Telegram (поверх чата с ботом), а не в отдельном браузере. Именно там
>   теперь происходит вся коррекция блюда — раньше это было прямо в чате
>   текстом и кнопками, теперь это отдельный экран с обычным тач-интерфейсом
>   (кнопки, поля ввода, как в любом мобильном приложении).
> - **WebView** — тот самый экран Mini App внутри Telegram: по сути браузер,
>   встроенный в приложение Telegram, но со своими особенностями (например,
>   он умеет узнавать, кто именно его открыл, без отдельного логина). Всё
>   ниже нужно проверять именно в НАСТОЯЩЕМ Telegram на телефоне — Telegram
>   Desktop и Telegram Web показывают WebView иначе и для этой проверки не
>   подходят.
> - **initData** — подпись, которую Telegram прикладывает при открытии Mini
>   App, чтобы сервер знал, какой именно пользователь его открыл, без пароля
>   или отдельного входа. Если открыть адрес Mini App в обычном браузере
>   (не через кнопку в Telegram) — этой подписи не будет, и сервер честно
>   откажет вместо того, чтобы притвориться, что кто-то залогинен.
> - **деплой** — процесс, при котором код из GitHub собирается и выкладывается
>   на публичный адрес в интернете (см. `docs/phase-04.1-deploy.md` — там
>   расписано, что именно развёрнуто и как это менять).
> - **serverless-функция** — маленькая программа, которая запускается только
>   когда приходит запрос (например, когда Mini App о��ращается за данными
>   черновика), а не работает постоянно, как бот. Живёт в папке `api/` этого
>   проекта и выложена на Vercel вместе со страницей Mini App.
> - **черновик** (`draft`) — незавершённый разбор блюда, который хранится в
>   таблице `diary_drafts`, пока ты его не подтвердил внутри Mini App.
> - **запись в дневнике** — уже сохранённое, подтверждённое блюдо в таблице
>   `diary`.
> - **Drizzle Studio** — браузерная программа для просмотра (и, если очень
>   нужно, редактирования) строк базы данных без написания SQL-запросов.
>
> Каждый шаг говорит: что сделать, что ты должен увидеть (дословно, если это
> текст от бота или из Mini App), и что это значит, если ты видишь что-то
> другое.

Эта фаза целиком заменила старую механику коррекции (кнопки и текст прямо в
чате, `docs/phase-04-manual-checklist.md`) на Mini App — старый чек-лист
больше не актуален для сценариев коррекции, но его Раздел 0 (preflight) и
общий стиль остаются образцом.

Каждый сценарий ниже проверяет конкретное требование или решение фазы 4.1
(см. `.planning/phases/04.1-.../04.1-CONTEXT.md`,
`.planning/phases/04.1-.../04.1-UI-SPEC.md` и `.planning/REQUIREMENTS.md`) —
номер требования указан в заголовке сценария.

## Раздел 0 — Подготовка (Preflight, обязательно пройти первым)

Все команды ниже вводи в терминале, открытом в корне проекта:
```
/Users/smatov/GitLab/VoxBite
```

- [ ] **Шаг 1.** Введи:
      ```
      npm test
      ```
      Ожидаемый результат: все тесты зелёные (в конце строка вида
      `Test Files  N passed` и `Tests  N passed`, без `failed`). Если хотя бы
      один тест красный — **останови проверку здесь**: значит в коде уже
      есть поломка, которую бессмысленно проверять руками.

- [ ] **Шаг 2.** Введи:
      ```
      npm run typecheck
      ```
      Ожидаемый результат: команда завершается без вывода ошибок (выход с
      кодом 0 — терминал просто возвращает тебя к следующей строке
      приглашения, без текста про `error TS...`). Если видишь ошибки типов —
      останови проверку здесь по той же причине, что и в шаге 1.

- [ ] **Шаг 3.** Введи:
      ```
      npm run check-setup
      ```
      Ожидаемый результат: команда печатает `SETUP OK`. Если видишь что-то
      другое (например, жалобу на отсутствующую переменную окружения) —
      останови проверку здесь и сначала разберись с настройкой окружения,
      прежде чем идти дальше.

- [ ] **Шаг 4.** Открой в обычном браузере на компьютере (НЕ в Telegram)
      адрес:
      ```
      https://vox-bite.vercel.app
      ```
      Ожидаемый результат: страница открывается (не `404`, не пустой белый
      экран) и показывает дословно текст **«Этот разбор устарел, отправь
      сообщение заново.»**. Это ожидаемо и правильно — вне Telegram у
      страницы нет подписи (`initData`), которая говорит, кто её открыл, и
      сервер намеренно показывает то же самое сообщение, что показывает и
      для реально устаревшего/чужого черновика, чтобы не выдавать
      постороннему, в чём именно причина отказа. Если вместо этого видишь
      `404` или совсем пустую страницу — деплой не работает, смотри
      `docs/phase-04.1-deploy.md`, раздел «Как найти лог сборки».

- [ ] **Шаг 5.** Открой на vercel.com проект `vox-bite`, вкладку
      **Deployments**. Ожидаемый результат: у самой свежей сборки статус
      **Ready**. Если статус `Error` или `Building` — останови проверку
      здесь, смотри `docs/phase-04.1-deploy.md`.

- [ ] **Шаг 6.** Введи в терминале:
      ```
      npm run bot
      ```
      Ожидаемый результат: та же строка запуска, что ты видел в предыдущих
      фазах (`Бот запущен: @<имя_твоего_бота>...`), без ошибки про
      отсутствующую переменную окружения. Если видишь ошибку, называющую
      `MINI_APP_BASE_URL` — значит эта переменная не задана в твоём
      локальном файле `.env`; посмотри `docs/phase-04.1-deploy.md`, там
      написано, откуда брать её значение. **Не закрывай этот терминал** —
      бот работает, только пока эта команда выполняется в нём.

      Открой Telegram на телефоне, найди своего бота — дальше проверка идёт
      там.

Если что-то в Разделе 0 не сработало — не переходи к сценариям ниже, это
означает, что окружение не готово, а не что в коде фазы 4.1 есть баг.

## Раздел 1 — Сценарии

### Сценарий 1 (CORRECT-01 / D-02 / D-03): чат больше не показывает разбор — только кнопка

Отправь боту голосовое сообщение, описывающее блюдо из нескольких
компонентов (например: «я съел бешбармак с мясом и картошкой»).

- [ ] Сразу приходит короткое сообщение-подтверждение получения (как раньше,
      «Секунду, разбираю» или похожее).
- [ ] То же сообщение через некоторое время меняется на готовый разбор — но
      **без списка компонентов, без граммовки, без цифр КБЖУ и без названий
      кандидатов из базы USDA**. Внимательно проверь текст сообщения целиком:
      там не должно быть НИ ОДНОГО числа и НИ ОДНОГО названия ингредиента.
      Это намеренное изменение (решение D-03 фазы 4.1) — вся эта информация
      теперь показывается только внутри Mini App, а не в чате. Если ты
      видишь список компонентов, граммы или калории прямо в тексте сообщения
      — это баг, зафиксируй дословный текст сообщения.
- [ ] Под сообщением есть кнопка **`🔧 Открыть для коррекции`**.
- [ ] Нажми на кнопку. Ожидаемый результат: открывается Mini App **внутри
      Telegram** (страница появляется поверх чата, без выхода в отдельный
      браузер или Safari/Chrome). Если вместо этого открылся внешний браузер
      — это баг.
- [ ] Внутри Mini App виден список всех компонентов блюда, у каждого — его
      граммовка и название сопоставленной записи из базы USDA (FDC).

### Сценарий 2 (CORRECT-03): смена кандидата меняет итог

Внутри Mini App, на любом компоненте, нажми **`Сменить вариант`**.

- [ ] Разворачивается список до трёх кандидатов из базы USDA — каждый
      кандидат виден полностью, текстом (не сокращённо).
- [ ] У текущего выбранного кандидата стоит отметка `✓`.
- [ ] Нажми на другого кандидата. Ожидаемый результат: отметка `✓`
      переместилась на новый выбор, строка компонента обновилась, и итоговые
      цифры в шапке (общие КБЖУ) тоже изменились.

### Сценарий 3 (CORRECT-04): изменение граммовки — кнопками и вручную

На любом компоненте внутри Mini App:

- [ ] Нажми `+10 г` дважды. Граммовка и итоговые цифры в шапке обновляются
      после каждого нажатия.
- [ ] Нажми `−10 г` один раз. Граммовка уменьшилась на 10 относительно
      предыдущего значения.
- [ ] Нажми на само число граммов. Ожидаемый результат: оно превращается в
      поле для ввода числа.
- [ ] Введи `250` и подтверди (например, кнопкой «Готово» на клавиатуре
      телефона или как предусмотрено экраном). Граммовка стала `250`, итог в
      шапке обновился.
- [ ] Снова нажми на число, введи бессмыслицу `abc`. Ожидаемый результат:
      прямо под полем появляется дословно **«Не понял количество. Напиши
      число в граммах, например 200.»**, а значение граммовки НЕ изменилось.

### Сценарий 4 (CORRECT-05): удаление компонента и полностью пустой разбор

- [ ] Убери один компонент кнопкой удаления на его строке. Список и итоговые
      цифры в шапке обновились без этого компонента.
- [ ] Убери оставшиеся компоненты по одному, пока не останется ни одного.
      Ожидаемый результат — появляется экран пустого состояния с текстом
      дословно:
      **«Компонентов не осталось.»**
      **«Добавь один заново или отмени разбор.»**
- [ ] На этом экране видны обе кнопки: **`➕ Добавить`** и
      **`✕ Отменить разбор`**.
- [ ] Кнопка подтверждения (`✅ Подтвердить`) недоступна для нажатия
      (задизейблена) — пустой разбор нельзя сохранить в дневник.

### Сценарий 5 (CORRECT-06): добавление компонента текстом

Из пустого состояния (сценарий 4) нажми `➕ Добавить`.

- [ ] Появляется поле для ввода текста прямо на этом же экране (без перехода
      на другую страницу).
- [ ] Введи название ингредиента с граммовкой, например `сметана 30`, и
      отправь.
- [ ] Ожидаемый результат: компонент появляется в списке с собственными
      кандидатами из базы USDA, как будто он был там с самого начала.
- [ ] Проверь свой расход в аккаунте OpenAI (platform.openai.com → Usage) —
      этот шаг должен был стоить один embedding-запрос (маленькая сумма,
      доли цента), а не полноценную транскрипцию голоса и разбор блюда
      языковой моделью (это была бы заметно бо́льшая сумма). Если сумма
      скачка расхода выглядит как за целое голосовое сообщение — это баг.

### Сценарий 6 (CALC-02): честное «нет данных» вместо нуля

Это проверка, которую нельзя выполнить автотестами против настоящих данных
USDA.

- [ ] Открой `npm run db:studio` (в новом терминале, не закрывая тот, где
      работает бот) — откроется страница в браузере. Найди таблицу
      **`fdc_foods`** и строку, у которой колонка **`sugar_g`** пустая
      (`null`). Запомни `description` этой строки.
- [ ] В Mini App подбери или скорректируй блюдо так, чтобы один из
      компонентов был сопоставлен именно с этой записью (через `Сменить
      вариант`, если нужно выбрать конкретного кандидата).
- [ ] Ожидаемый результат: в разделе про сахар — и в строке этого конкретного
      компонента (если она показана отдельно), и в общем итоге в шапке —
      значение сахара показано дословно как **«нет данных»**. **Никогда не
      `0`** — это критично: `0` здесь означает, что бот соврал, будто знает,
      что сахара нет, хотя на самом деле данных просто нет.
- [ ] Если у блюда есть и другие компоненты с известным сахаром, итог в
      шапке должен читаться как нижняя граница с явным числом недостающих —
      например `≥ 12 г (у 1 из 5 нет данных)`, а не как обычная сумма и не
      как общее «нет данных» для всей строки.

### Сценарий 7 (CALC-01): сохранённые цифры — это математика, не выдумка LLM

- [ ] На экране Mini App перед подтверждением запиши текущие итоговые цифры
      (калории, белки, жиры, углеводы) из шапки.
- [ ] Подтверди разбор (см. сценарий 8 ниже про сам процесс подтверждения).
- [ ] Открой `npm run db:studio` → таблицу **`diary`** → найди только что
      сохранённую строку. Сравни её `kcal`, `protein_g`, `fat_g`, `carbs_g`
      с цифрами, которые ты записал перед подтверждением. Ожидаемый
      результат: числа совпадают (кроме, возможно, округления на десятые).
      Это подтверждает, что итог — результат арифметики (граммы × нутриенты
      из FDC на 100 г), а не что-то досочинённое языковой моделью на лету.

### Сценарий 8 (CORRECT-02 / DIARY-01): подтверждение и день записи

Возьми исправный разбор (без компонентов без совпадений) и нажми
`✅ Подтвердить` внутри Mini App.

- [ ] Ненадолго (примерно на секунду) появляется надпись дословно
      **«Сохранено в дневник»** прямо внутри Mini App.
- [ ] После этого Mini App закрывается **сам** — тебя не просят закрыть
      руками, экран возвращается в чат с ботом автоматически.
- [ ] Открой `npm run db:studio` → таблицу **`diary`** и убедись, что для
      этого блюда есть **ровно одна** строка. Колонка `local_date` должна
      равняться дню, когда ты **надиктовал** сообщение (а не дню, когда ты
      нажал «Подтвердить», если это разные дни — например, если диктовал
      поздно вечером, а подтвердил уже после полуночи).

### Сценарий 9 (CORRECT-08): правка и удаление уже сохранённой записи

Найди в истории чата то самое сообщение, из которого ты открывал Mini App
для блюда, сохранённого в сценарии 8 (это единственный способ вернуться к
уже сохранённой записи на этом этапе — см. примечание в конце документа).
Нажми на его кнопку ещё раз.

- [ ] Mini App открывается заново, но в футере (нижней части экрана) теперь
      не `✅ Подтвердить`, а две кнопки: **`Сохранить изменения`** и
      **`🗑 Удалить`**.
- [ ] Измени граммовку любого компонента и нажми `Сохранить изменения`.
- [ ] Открой Drizzle Studio → таблицу `diary` → ту же самую строку.
      Ожидаемый результат: числа (`kcal`, `protein_g`, `fat_g`, `carbs_g`,
      возможно `sugar_g`) изменились, а `local_date` остался **тем же**, что
      и раньше. И самое важное — **не появилось второй строки** для этого
      же блюда.
- [ ] Открой Mini App для этой же записи ещё раз (та же кнопка в чате),
      нажми `🗑 Удалить`. Ожидаемый результат: на месте кнопок появляется
      подтверждение дословно **«Удалить запись? Это навсегда.»** с двумя
      кнопками — `Да, удалить` и `Нет`.
- [ ] Сначала нажми `Нет`. Ожидаемый результат: ничего не удалилось, запись
      осталась как была (проверь в Drizzle Studio, если хочешь убедиться).
- [ ] Открой Mini App и нажми `🗑 Удалить` ещё раз, на этот раз нажми
      `Да, удалить`.
- [ ] Открой Drizzle Studio → таблицу `diary` — строка должна **полностью
      исчезнуть** (настоящее удаление строки, не пометка «удалено»).

### Сценарий 10 (CORRECT-07): черновик переживает перезапуск бота

Это единственная проверка (кроме сценария 6), которую нельзя автоматизировать
— она требует реально убить и снова запустить процесс бота.

- [ ] Начни новый разбор (отправь голосовое сообщение) и открой Mini App.
- [ ] Измени граммовку одного компонента (кнопкой `+10 г` или вводом числа).
- [ ] **Не подтверждай.** Переключись в терминал, где выполняется
      `npm run bot`, и нажми `Ctrl+C`. Дождись, что процесс завершился
      (терминал вернул строку приглашения).
- [ ] Запусти бота заново той же командой:
      ```
      npm run bot
      ```
- [ ] Пока бот был выключен, попробуй в самой Mini App (не закрывая её)
      изменить что-то ещё, например нажать `+10 г` ещё раз. Ожидаемый
      результат: это сработало, несмотря на то что бот выключен. Это
      нормально и ожидаемо — Mini App обращается напрямую к базе данных
      через свои собственные серверные функции на Vercel, а не через
      запущенный процесс бота.
- [ ] Закрой Mini App и снова открой её из того же сообщения в чате (уже
      после перезапуска бота). Ожидаемый результат: изменённая граммовка
      всё ещё там, как будто ничего не происходило.
- [ ] Открой Drizzle Studio → таблицу `diary_drafts` → найди свою строку
      (самую свежую). Черновик существует и хранит актуальные изменённые
      компоненты — это доказательство того, что состояние черновика хранится
      в базе данных, а не в памяти процесса бота, и поэтому пережило
      перезапуск.

### D-04 removal check (CORRECT-07 / причина, по которой существует эта фаза)

С открытым и НЕ подтверждённым черновиком (можно использовать черновик из
предыдущего сценария, если он ещё не подтверждён) — не трогая Mini App,
вернись в чат с ботом и отправь обычное текстовое сообщение, например
`200`.

- [ ] Ожидаемый результат: это сообщение обрабатывается как **новый,
      отдельный** разбор блюда — приходит своё собственное
      сообщение-подтверждение и, если распознавание пройдёт успешно, своя
      собственная кнопка `🔧 Открыть для коррекции`. Оно НЕ применяется как
      правка к уже открытому черновику.
- [ ] Открытый ранее черновик (в Mini App) остался нетронутым — изменённая
      в прошлом сценарии граммовка всё ещё на месте, если ты откроешь его
      снова.

Раньше (до этой фазы, см. `04-UAT.md`, раунды 3-4) подобное текстовое
сообщение иногда незаметно перехватывалось открытым черновиком коррекции и
могло дойти до платного пайплайна распознавания, создавая задвоенную запись
в дневнике. Теперь, когда вся коррекция происходит только внутри Mini App,
а не текстом в чате, у бота больше нет механизма, который бы мог перепутать
текстовое сообщение с правкой черновика — весь класс этой ошибки исчез
вместе с самим текстовым гейтом. Если ты видишь любое поведение, похожее на
старое (сообщение пропадает без своего отдельного разбора, или граммовка в
открытом черновике меняется сама) — это серьёзный баг, сообщи дословный
текст, который увидел.

### Проверка темы (light/dark)

- [ ] Открой Mini App. Переключи тему Telegram (Настройки → Оформление) на
      светлую, если сейчас тёмная, или наоборот.
- [ ] Открой Mini App заново. Ожидаемый результат: цвета экрана (фон, кнопки,
      текст) поменялись вслед за темой Telegram — Mini App не осталась
      "залипшей" на одной цветовой схеме.
- [ ] Пройдись пальцем по всем кнопкам (`+10 г`, `−10 г`, `Сменить вариант`,
      `✕ Убрать`, `➕ Добавить`, `✅ Подтвердить`/`Сохранить изменения`,
      `🗑 Удалить`, `Да, удалить`/`Нет`). Каждая должна нажиматься с первого

## Раздел 2 — Что делать, если что-то пошло не так

- Остановись на том шаге, где увидел расхождение. Не пытайся продолжать
  дальше по списку, если предыдущий шаг дал не тот результат, который здесь
  описан, — следующие шаги почти наверняка тоже «соврут», раз предыдущее
  состояние уже неверное.
- Скопируй **дословно** русский текст, который тебе показал бот или Mini App
  (или сделай скриншот), и номер сценария (например: «Сценарий 6, шаг 3:
  увидел `0` вместо «нет данных»»).
- **Не редактируй строки в Drizzle Studio вручную**, пытаясь «починить»
  данные и продолжить проверку. Вручную изменённая строка сделает следующие
  шаги проверки лживыми — они будут проверять твою ручную правку, а не код.
- Если сборка на Vercel выглядит подозрительно (страница не открывается,
  Mini App не грузится) — сначала загляни в `docs/phase-04.1-deploy.md`,
  раздел «Как найти лог сборки, если что-то сломалось»: там пошагово
  расписано, где смотреть Build Logs и Runtime Logs.
- Если сломался именно бот (не Mini App) — смотри терминал, где выполняется
  `npm run bot`: любая ошибка печатается прямо туда.
- Сообщи о расхождении (дословный текст + номер сценария) для разбора и
  фикса отдельным планом — эта проверка сама по себе кода не чинит.

## Известный принятый пробел (не баг)

Единственный способ вернуться к уже сохранённой записи сейчас — пролистать
историю чата до её исходного сообщения и нажать на всё ещё рабочую кнопку
`🔧 Открыть для коррекции` под ним. Отдельного экрана «мой дневник» со
списком всех записей пока нет — это появится в Фазе 5. Это ожидаемое,
сознательно принятое ограничение текущей фазы, а не то, что нужно сообщать
как баг.

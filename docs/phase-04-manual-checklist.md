# Ручная проверка Phase 4 — подтверждение, коррекция и сохранение в дневник

> Этот документ — для тебя, если ты никогда раньше не запускал backend-процесс
> и не открывал базу данных напрямую.
>
> Термины по ходу: "терминал" — программа для ввода текстовых команд (на Mac —
> Terminal или iTerm); "процесс" — запущенная программа, работающая, пока её
> не остановишь (`Ctrl+C`) или не закроешь терминал; "миграция" — файл с SQL,
> который меняет структуру базы данных (уже применён, здесь не встречается);
> "черновик" (`draft`) — незавершённый разбор блюда, который бот хранит в
> таблице `diary_drafts`, пока ты его не подтвердил; "запись в дневнике" —
> уже сохранённое, подтверждённое блюдо в таблице `diary`; "Drizzle Studio" —
> браузерная программа для просмотра и — если очень нужно — редактирования
> строк базы данных без написания SQL-запросов; "строка" (`row`) — одна
> запись в таблице базы данных, как одна строка в Excel-таблице.
>
> Каждый шаг говорит: что сделать, что ты должен увидеть (дословно, если это
> текст от бота), и что это значит, если ты видишь что-то другое.

Каждый сценарий ниже проверяет конкретное решение или требование фазы 4
(см. `.planning/phases/04-confirm-correct-diary-persistence/04-CONTEXT.md` и
`.planning/REQUIREMENTS.md`) — номер требования/решения указан в заголовке
сценария.

## Раздел 0 — Подготовка (Preflight, обязательно пройти первым)

Все команды ниже вводи в терминале, открытом в корне проекта:
```
/Users/smatov/GitLab/VoxBite
```

- [ ] **Шаг 1.** Введи:
      ```
      npm test
      ```
      Ожидаемый результат: все тесты зелёные (в конце строка вида
      `Test Files  N passed` и `Tests  N passed`, без `failed`). Если хотя бы
      один тест красный — **останови проверку здесь** и сообщи об этом,
      прежде чем переходить к живым шагам ниже: значит в коде уже есть
      поломка, которую бессмысленно проверять руками.

- [ ] **Шаг 2.** Введи:
      ```
      npm run typecheck
      ```
      Ожидаемый результат: команда завершается без вывода ошибок (выход с
      кодом 0 — терминал просто возвращает тебя к следующей строке
      приглашения, без текста про `error TS...`). Если видишь ошибки типов —
      останови проверку здесь по той же причине, что и в шаге 1.

- [ ] **Шаг 3.** Введи:
      ```
      npm run verify-schema
      ```
      Ожидаемый результат: нет ошибок про отсутствующие колонки (никакого
      текста вида "missing column" или "column does not exist"). Это
      подтверждает, что база данных уже содержит все таблицы и колонки,
      которые нужны для проверки ниже (`diary_drafts.awaiting_input`,
      `diary_drafts.local_date`, `diary.sugar_g` и т.д.).

- [ ] **Шаг 4.** Введи:
      ```
      npm run bot
      ```
      Ожидаемый результат: та же строка запуска, что ты уже видел в Phase 2
      (`Бот запущен: @<имя_твоего_бота>...`). **Не закрывай этот терминал** —
      бот работает, только пока эта команда выполняется в нём. `Ctrl+C` в
      этом терминале останавливает бота — это специально используется в
      сценарии 6 ниже.

      Открой Telegram, найди своего бота (ты уже добавлен в
      `BETA_ALLOWLIST` по итогам Phase 2) — дальше проверка идёт там.

Если что-то в Разделе 0 не сработало — не переходи к сценариям ниже, это
означает, что окружение не готово, а не что в коде фазы 4 есть баг.

## Раздел 1 — Сценарии

### Сценарий 1 (CORRECT-01 / D-01 / D-02): вид карточки на телефоне

Отправь боту голосовое сообщение, описывающее блюдо из нескольких
компонентов (например: "я съел бешбармак с мясом и картошкой").

- [ ] Дождись карточки с заголовком **«Проверь разбор:»** (дословно — эта
      строка называется `headerLevel1` в коде).
- [ ] Под заголовком — список всех компонентов блюда, у каждого — граммовка и
      описание из базы USDA (FDC). Описание должно читаться полностью, без
      обрезки многоточием («…») в теле сообщения (кнопки короче — это
      нормально, важно тело сообщения).
- [ ] Под списком — строка предпросмотра КБЖУ, начинающаяся со знака `≈`, и
      рядом или ниже — пометка **«пока не сохранено»** (дословно —
      `notSavedMarker`).
- [ ] Нажми на кнопку любого компонента (например `1. Говядина 120 г`).
      Ожидаемый результат: **то же самое сообщение** превращается в экран
      этого одного компонента — новое сообщение в чат не приходит (это
      проверка того, что бот редактирует одно и то же сообщение, а не
      плодит новые).
- [ ] На этом экране — до трёх кандидатов из базы USDA, описанных текстом
      (не как текст на кнопке), и под ними — кнопки `1`, `2`, `3` (по числу
      кандидатов). Убедись, что текст каждого кандидата читается целиком —
      разница между кандидатами часто состоит в последнем слове ("сырое"
      против "приготовленное"), и его не должно быть видно только частично.

### Сценарий 2 (CORRECT-03 / D-03): смена кандидата меняет превью

На экране одного компонента (из сценария 1) нажми на кандидата номер `2`.

- [ ] Отметка (галочка `✓`, дословно `chosenMarker`) переместилась на
      кандидата 2.
- [ ] Строка предпросмотра (`≈ ...`) изменилась — запиши для себя новые
      цифры, они понадобятся для сравнения дальше по чек-листу, если решишь
      сверять итоговую сумму вручную.

### Сценарий 3 (CORRECT-04): изменение граммовки, включая ввод текстом

На том же экране компонента:

- [ ] Нажми `+10 г` дважды. Граммовка в тексте экрана и строка `≈`-превью
      меняются после каждого нажатия.
- [ ] Нажми `−10 г` один раз. Граммовка уменьшилась на 10 относительно
      предыдущего значения, превью снова обновилось.
- [ ] Нажми `⌨ Ввести граммы`. Ожидаемый результат — бот присылает вопрос
      вида **«Сколько граммов «...»? Напиши число.»** (дословно —
      `askGrams`, где вместо `...` — название компонента).
- [ ] Напиши в чат обычным текстовым сообщением `200 г`. Ожидаемый результат:
      граммовка компонента стала 200, и **новый разбор блюда не запустился**
      (то есть бот не начал распознавать это сообщение как новое голосовое
      описание еды — это была бы трата денег на новый API-вызов).
- [ ] Повтори: нажми `⌨ Ввести граммы` ещё раз и напиши бессмыслицу `abc`.
      Ожидаемый результат — бот отвечает дословно **«Не понял количество.
      Напиши число в граммах, например 200.»** (это `gramsRejected`), и ты
      можешь сразу, не нажимая кнопку заново, написать корректное число
      (например `150`) — оно должно примениться.

### Сценарий 4 (CORRECT-05 / D-12): удаление всех компонентов — пустое состояние

Вернись на экран со списком компонентов (кнопка `← Назад`, если ты внутри
экрана одного компонента) и удаляй компоненты по одному кнопкой `✕ Убрать`
на экране каждого из них, пока не останется ни одного.

- [ ] После удаления последнего компонента появляется сообщение дословно
      **«Компонентов не осталось. Добавь один заново или отмени разбор.»**
      (это `emptyState`).
- [ ] Кнопки `✅ Подтвердить` на этом экране **нет** — это принципиально:
      пустой разбор не может быть сохранён в дневник.
- [ ] Кнопка `➕ Добавить` осталась.

### Сценарий 5 (CORRECT-06): добавление компонента текстом — без повторной траты на распознавание

Из пустого состояния (сценарий 4) нажми `➕ Добавить`.

- [ ] Бот присылает вопрос дословно **«Что добавить? Напиши название
      компонента.»** (это `askComponent`).
- [ ] Напиши простой ингредиент с граммовкой, например `сметана 30`.
- [ ] Ожидаемый результат: компонент появляется в списке с кандидатами из
      USDA, как будто он был там с самого начала.
- [ ] Проверь свой расход в аккаунте OpenAI (platform.openai.com → Usage) —
      этот шаг должен был стоить **один embedding-запрос** (маленькая
      сумма, доли цента), а не полноценную транскрипцию голоса плюс разбор
      блюда языковой моделью (это была бы заметно бо́льшая сумма). Если
      сумма скачка расхода выглядит как за целое голосовое сообщение —
      это баг, сообщи о нём.

### Сценарий 6 (CORRECT-07 / D-04): черновик переживает перезапуск бота — самая важная проверка

Это единственная проверка, которую нельзя автоматизировать: она требует
реально убить и снова запустить процесс бота.

- [ ] Начни коррекцию любого компонента (открой его экран) и нажми
      `⌨ Ввести граммы` — но **пока не пиши число**.
- [ ] Переключись в терминал, где выполняется `npm run bot`, и нажми
      `Ctrl+C`. Дождись, что процесс завершился (терминал вернул тебе
      строку приглашения).
- [ ] Запусти бота заново той же командой:
      ```
      npm run bot
      ```
- [ ] Вернись в Telegram и теперь напиши число, например `180`.
      Ожидаемый результат: число применяется к **тому же самому компоненту
      в той же самой карточке**, как будто бот и не перезапускался.
- [ ] Открой Drizzle Studio командой (в новом терминале, не закрывая тот,
      где работает бот):
      ```
      npm run db:studio
      ```
      Это откроет страницу в браузере. Найди таблицу **`diary_drafts`**,
      найди свою строку (самую свежую по времени, либо отфильтруй по своему
      `user_id`), и посмотри на колонку **`awaiting_input`**. Пока ты был
      между нажатием `⌨ Ввести граммы` и отправкой числа (то есть всё время,
      пока бот был выключен) — эта колонка держала непустое значение (JSON
      вида `{"kind":"typed_grams","componentIndex":...}`). Это доказательство
      того, что состояние "жду от тебя число" пережило перезапуск процесса,
      потому что оно хранится в базе данных, а не в памяти бота.

### Сценарий 7 (CALC-02 / D-09): честное «нет данных» вместо нуля

Это второй пункт, который нельзя проверить автотестами против настоящих
данных USDA.

- [ ] В Drizzle Studio (`npm run db:studio`, если ещё не открыто) открой
      таблицу **`fdc_foods`** и найди строку, у которой колонка **`sugar_g`**
      пустая (`null`). Запомни `description` этой строки — по этому тексту
      её можно будет узнать в карточке бота.
- [ ] В Telegram подбери или скорректируй блюдо так, чтобы один из
      компонентов был сопоставлен именно с этой записью (например, через
      кандидатов на экране компонента — выбери того кандидата, чьё описание
      совпадает с найденной строкой).
- [ ] Ожидаемый результат в строке предпросмотра (`≈ ...`): значение сахара
      показано дословно как **«нет данных»** (это `noData`) — никогда `0`.
- [ ] Если в блюде есть и другие компоненты, у которых сахар известен, итог
      должен читаться как нижняя граница с явным числом недостающих —
      например `≥ 12 г (у 1 из 5 нет данных)` (это `partialTotal`), а не как
      обычная сумма и не как общее «нет данных» для всей строки.
- [ ] Подтверди блюдо (`✅ Подтвердить`, см. сценарий 9) и проверь, что то же
      самое сохраняется в итоговой карточке — открой Drizzle Studio, таблицу
      **`diary`**, найди свою строку и посмотри на колонку `sugar_g`: она
      должна быть пустой (`null`), а не `0`. Пустое `null` в базе — это то,
      что на экране бота превращается в текст «нет данных»; `0` в базе
      означало бы, что бот соврал о нуле сахара.

### Сценарий 8 (D-10): подтверждение блокируется без FDC-совпадения

- [ ] Опиши голосом или добавь текстом (`➕ Добавить`) компонент, для
      которого поиск по базе USDA заведомо ничего не найдёт (очень странное
      или бессмысленное название), либо дождись случая, когда обычное блюдо
      даёт такой результат для одного из компонентов.
- [ ] На экране этого компонента должна быть строка **«не нашёл подходящую
      запись»** (это `noMatch`) вместо списка кандидатов.
- [ ] Вернись на уровень списка и нажми `✅ Подтвердить`. Ожидаемый
      результат: бот **отказывает**, называет именно этот компонент по
      имени и предлагает ровно два выхода — убрать компонент или описать
      его иначе (формулировка начинается с «Не могу подтвердить: для
      «...» не нашёл подходящую запись.» — это `blockedConfirm`). Он не
      должен предлагать «подтвердить как есть».

### Сценарий 9 (CORRECT-02 / DIARY-01 / D-05 / D-07): подтверждение и день записи

Возьми исправный черновик (без компонентов без совпадений) и нажми
`✅ Подтвердить`.

- [ ] То же сообщение превращается в сохранённую запись: финальные цифры без
      знака `≈`, и строка вида **«Сохранено в дневник за <дата>»** (это
      `savedOn`).
- [ ] Открой `npm run db:studio` → таблицу **`diary`** и убедись, что для
      этого блюда есть **ровно одна** строка. Колонка `local_date` должна
      равняться дню, когда ты **надиктовал** сообщение (а не дню, когда ты
      нажал «Подтвердить», если это разные дни — например, если ты
      диктовал поздно вечером, а подтвердил уже после полуночи).
- [ ] Если у тебя есть более старая карточка с разбором в истории чата,
      попробуй быстро нажать `✅ Подтвердить` на ней тоже (или дважды подряд
      на текущей, если успеешь). Ожидаемый результат: вторая строка в
      таблице `diary` для того же блюда **не появляется**.

### Сценарий 10 (CORRECT-08): правка уже сохранённой записи

На сохранённой записи (см. сценарий 9) нажми `✎ Поправить`.

- [ ] Открывается тот же самый экран коррекции, что и до сохранения (тот же
      двухуровневый интерфейс из сценария 1).
- [ ] Измени граммовку любого компонента (кнопками `+10 г`/`−10 г` или
      `⌨ Ввести граммы`) и снова подтверди.
- [ ] Открой Drizzle Studio → таблицу `diary` → ту же строку. Числа (`kcal`,
      `protein_g`, `fat_g`, `carbs_g`, возможно `sugar_g`) должны были
      измениться, а колонка `local_date` — остаться **той же самой**, что
      была до правки.

### Сценарий 11 (D-08): удаление с подтверждением

На сохранённой записи нажми `🗑 Удалить`.

- [ ] Бот спрашивает дословно **«Удалить запись? Это навсегда.»** (это
      `deletePrompt`) с двумя кнопками: `Да, удалить` и `Нет`.
- [ ] Нажми `Нет`. Ожидаемый результат: ничего не удаляется, запись
      остаётся как была.
- [ ] Нажми `🗑 Удалить` ещё раз, а на этот раз — `Да, удалить`.
      Ожидаемый результат: бот отвечает дословно **«Запись удалена.»**
      (это `deleted`).
- [ ] Открой Drizzle Studio → таблицу `diary` — строка должна **полностью
      исчезнуть** (не появиться там с какой-то пометкой "удалено" — это
      настоящее удаление строки, а не скрытый флаг).
- [ ] Открой таблицу `diary_drafts` → найди связанный черновик (тот же,
      что породил эту запись) → колонка `status` должна читаться
      **`abandoned`**.

### Сценарий 12 (D-11): просроченная карточка (старше 24 часов)

- [ ] Если у тебя в истории чата есть карточка разбора старше 24 часов —
      нажми на любую её кнопку. Ожидаемый результат: бот отвечает дословно
      **«Этот разбор устарел, отправь сообщение заново.»** (это `expired`),
      и кнопки под карточкой исчезают.
- [ ] Если такой карточки у тебя нет (весь функционал был написан сегодня,
      и у тебя, скорее всего, нет карточки суточной давности) — отметь этот
      пункт как **"не проверено сегодня"**, а не пропускай молча. Это не
      баг и не повод останавливать проверку — просто честно зафиксируй,
      что этот пункт проверен не был.

## Раздел 2 — Что делать, если что-то пошло не так

- Остановись на том шаге, где увидел расхождение. Не пытайся продолжать
  дальше по списку, если предыдущий шаг дал не тот результат, который
  описан здесь, — следующие шаги почти наверняка тоже "соврут", раз
  предыдущее состояние уже неверное.
- Скопируй **дословно** русский текст, который тебе показал бот, и номер
  сценария (например: "Сценарий 7, шаг 3: увидел `0` вместо «нет данных»").
- **Не редактируй строки в Drizzle Studio вручную**, пытаясь "починить"
  данные и продолжить проверку. Вручную изменённая строка сделает
  следующие шаги проверки лживыми — они будут проверять твою ручную правку,
  а не код бота.
- Сообщи о расхождении (дословный текст + номер сценария) для разбора и
  фикса отдельным планом — эта проверка сама по себе кода не чинит.

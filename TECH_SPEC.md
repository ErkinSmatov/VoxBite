# VoxBite — Техническое задание

Версия 0.1 · 2026-08-10

## 0. Одностраничное резюме

Telegram-бот по подписке. Пользователь присылает голосовое сообщение вида
"на обед съел лазанью и выпил колу" → бот распознаёт речь → раскладывает блюдо
на ингредиенты с граммовкой → находит для каждого ингредиента реальную запись
в базе USDA FoodData Central (FDC) через семантический (embedding) поиск →
пользователь подтверждает/корректирует → бот **математически** (не через LLM)
считает калории/Б/Ж/У/сахар и сохраняет в дневник. Отдельно бот на онбординге
считает пользователю целевые КБЖУ под цель (набор/сброс веса не быстрее 1 кг
в месяц, либо биохакинг/поддержание), присылает напоминания и мотивационные
сообщения. Доступ — по платной подписке (месяц/год) с лимитом голосовых
сообщений в месяц.

---

## 1. Роли и допущения

- **Целевая платформа:** Telegram Bot (long polling или webhook).
- **Один "рынок" на старте:** судя по цене в тенге, целевая аудитория —
  Казахстан. Это важно для выбора платёжного провайдера (см. §7 и "Открытые
  риски" в §11 — **это блокирующий вопрос архитектуры**, его нужно закрыть до
  начала разработки платного функционала).
- Язык интерфейса бота: русский (можно заложить i18n-слой заранее, чтобы не
  переписывать потом — это дёшево сделать сразу и дорого добавить позже).
- Голосовые сообщения пользователь может присылать на русском/казахском —
  название блюд, скорее всего, будет не на английском, а USDA FDC — база на
  английском. Это создаёт обязательный шаг перевода перед embedding-поиском
  (см. §5.4).

## 2. Глоссарий (для не-бэкенд разработчика)

| Термин | Что это значит здесь |
|---|---|
| КБЖУ | Калории, Белки, Жиры, Углеводы |
| STT (Speech-to-Text) | Сервис, переводящий голос в текст (например, Whisper) |
| LLM | Большая языковая модель (например, Claude/GPT/Gemini) — здесь используется **только** для понимания текста (распознать блюдо, разложить на ингредиенты, оценить граммы), а не для арифметики |
| Embedding | Числовой вектор, представляющий смысл текста. Похожие по смыслу фразы получают близкие вектора. Нужен, чтобы искать "куриная грудка жареная" в англоязычной базе как "grilled chicken breast", даже если текст не совпадает дословно |
| Vector search / Vector DB | Поиск ближайших по смыслу embedding-векторов. Как обычный поиск по ключевым словам, но по смыслу, а не по буквам |
| USDA FDC | FoodData Central — открытая база нутриентов Минсельхоза США: тысячи продуктов с точным составом на 100 г |
| Воркер (worker) | Отдельный фоновый процесс, который выполняет задачи не в момент запроса пользователя (например, шлёт напоминания по расписанию, обрабатывает голосовые в очереди) |
| Очередь (queue) | Механизм "отложенных задач" — например, чтобы обработка голосового не блокировала бота и не терялась при сбое |
| Миграция БД | Скрипт, который версионирует изменения структуры базы данных |
| Webhook | Способ, которым Telegram сам стучится к вашему серверу при новом сообщении (вместо того чтобы сервер сам постоянно спрашивал Telegram) |

## 3. Пользовательские сценарии (User Flows)

### 3.1 Первый запуск / подписка

1. `/start` → приветствие, короткое объяснение, чем полезен бот.
2. Показ тарифов: месяц / год (с ценами и лимитом голосовых в месяц).
3. Оплата (см. §7).
4. После успешной оплаты → онбординг анкеты.

### 3.2 Онбординг (сбор данных о пользователе)

Обязательные поля:
- Пол (муж/жен) — нужен для формулы BMR.
- Возраст.
- Рост (см).
- Текущий вес (кг).
- Уровень активности (5 стандартных градаций, см. §6.2).
- Цель:
  - Снижение веса
  - Набор веса
  - Поддержание / биохакинг (акцент на качестве нутриентов, не на смене веса)
- Если цель — набор/снижение веса: желаемый темп (по умолчанию и максимум —
  **1 кг в месяц**, ограничено сверху этим значением намеренно, см. §6.3).

Каждое поле собирается по одному, через inline-кнопки там, где возможно
(пол, активность, цель), текстовый ввод — для чисел (возраст/рост/вес).
После заполнения — экран подтверждения с расчётной целью КБЖУ (§6) и кнопкой
"всё верно / изменить".

### 3.3 Основной цикл: голосовое → дневник

1. Пользователь шлёт voice message.
2. Бот отвечает "Секунду, разбираю 🎧" (мгновенный feedback, т.к. обработка
   занимает несколько секунд).
3. STT → текст.
4. LLM раскладывает текст на список `{ингредиент, граммовка_оценка}`.
5. Для каждого ингредиента: перевод названия на английский (если нужно) →
   embedding → vector search по USDA FDC → топ-3 кандидата.
6. Бот присылает пользователю карточку с распознанным блюдом:
   ```
   Я услышал: "лазанья"
   Разложил на:
   • Листы пасты — 80 г   [Pasta, dry, unenriched ▾]
   • Фарш говяжий — 120 г [Beef, ground, 85% lean ▾]
   • Соус томатный — 60 г [Tomato sauce, canned ▾]
   • Моцарелла — 40 г     [Cheese, mozzarella, whole milk ▾]

   [✅ Всё верно]  [✏️ Исправить]
   ```
   `▾` = inline-кнопка, открывающая выбор среди 3 кандидатов FDC для этого
   ингредиента (см. §5.6 — механика коррекции).
7. Пользователь подтверждает → бот считает финальные КБЖУ+сахар математически
   (§5.7) и пишет итог + сохраняет запись в дневник дня.
8. Если пользователь жмёт "Исправить" → см. §5.6.

### 3.4 Напоминания и мотивация

- Ежедневное напоминание "занести приёмы пищи", если за N часов не было
  голосовых (настраиваемое окно, например бот молчит, если пользователь уже
  всё внёс).
- Периодическая сводка (например, раз в день вечером) — сколько КБЖУ съедено
  vs цель.
- Мотивационные сообщения — регулярность и тон настраиваются (не спам).
- Это отдельный **фоновый планировщик** (см. §8), не часть обработки запроса.

### 3.5 Лимиты и апсейл

- Каждому пользователю на тарифе — лимит голосовых сообщений в месяц
  (число — открытый вопрос экономики, см. §9).
- При достижении лимита — бот сообщает об этом и предлагает раньше продлить
  тариф/перейти на старший тариф (если появится), но **не блокирует** доступ
  к уже накопленному дневнику и ручному вводу (если он будет поддержан).

## 4. Архитектура (высокоуровнево)

```
Telegram ──(webhook)──> API-сервер (Bot Handler)
                              │
                              ├─> Auth/Subscription service ──> Payment provider
                              │
                              ├─> Postgres (пользователи, дневник, подписки)
                              │
                              ├─> Job Queue (обработка голосовых, тяжёлые задачи)
                              │        │
                              │        ▼
                              │   Voice Processing Worker
                              │        ├─> STT API
                              │        ├─> LLM API (декомпозиция блюда)
                              │        ├─> Embedding API
                              │        ├─> Vector DB (проиндексированный USDA FDC)
                              │        └─> Postgres (сохранение черновика записи)
                              │
                              └─> Scheduler / Notification Worker (cron)
                                       └─> Postgres (кому и когда слать)
```

**Почему очередь, а не обработка "в моменте" запроса:**
STT + LLM + embeddings + vector search — это несколько секунд и несколько
внешних API-вызовов подряд. Если один из них зависнет или упадёт, что-то
должно ретраить задачу и не терять голосовое сообщение пользователя. Прямая
обработка "внутри" ответа на webhook Telegram (без очереди) технически
возможна для MVP при низкой нагрузке, но не оставляет запаса для retry/масштаб.
**Рекомендация:** на MVP можно без отдельной очереди (простой async-обработчик
с retry на уровне кода), но код должен быть написан так, чтобы очередь можно
было добавить, не переписывая бизнес-логику.

## 5. Обработка голосового сообщения — детали

### 5.1 STT (речь → текст)
- Вариант по умолчанию: **Whisper API** (OpenAI) — хорошо работает с русским.
  Альтернатива — Google Speech-to-Text, Yandex SpeechKit (может быть точнее
  на казахском/русском с акцентом СНГ — стоит сравнить перед финальным
  выбором на этапе разработки, не блокирует архитектуру).

### 5.2 Декомпозиция блюда LLM
- Промпт LLM должен вернуть **строго структурированный JSON**, например:
  ```json
  {
    "items": [
      {"component": "листы пасты", "component_en": "pasta sheets", "grams": 80},
      {"component": "фарш говяжий", "component_en": "ground beef", "grams": 120}
    ]
  }
  ```
- Требование: LLM обязана декомпозировать составные блюда (лазанья, плов,
  бургер) до ингредиентов, а не отдавать общее название. Для простых
  однокомпонентных блюд ("банан") — один элемент.
- Оценка граммовки — по умолчанию LLM оценивает исходя из типичной порции;
  если пользователь называет вес явно ("200 г риса") — использовать его.

### 5.3 Валидация LLM-вывода
- JSON должен проходить строгую схемную валидацию перед дальнейшей
  обработкой (например, через structured output / function calling режим
  используемой модели, не просто "попросили JSON в промпте").
- Если LLM вернула невалидный JSON или пустой список — retry с более строгим
  промптом, при повторном провале — сообщить пользователю "не смог разобрать,
  опиши иначе".

### 5.4 Перевод + Embedding
- `component_en` (см. 5.2) — LLM сама переводит название компонента на
  английский в том же вызове (дешевле и надёжнее отдельного шага перевода).
- Embedding-модель: `gemini-embedding-001` (или аналог — `text-embedding-3-small`
  от OpenAI дешевле и достаточно для этой задачи; финальный выбор — вопрос
  цены/качества, не архитектуры).

### 5.5 Индексация USDA FDC (делается один раз, не на каждый запрос)
- Скачать датасет USDA FDC (Foundation Foods + SR Legacy — приоритет; Branded
  Foods — опционально, база в 100+ раз больше и менее чистая, для MVP не
  нужна).
- Для каждой записи построить embedding по названию (+ описанию) и сохранить
  в vector DB вместе с нутриентами на 100 г (калории, белки, жиры, углеводы,
  сахар, и опционально клетчатка/натрий).
- Это отдельный офлайн-пайплайн (скрипт), не часть runtime-бота. Перезапуск —
  раз в несколько месяцев при обновлении датасета USDA.
- Vector DB — рекомендация: **pgvector** (расширение Postgres) — не нужен
  отдельный сервис, всё в одной базе, чего достаточно для объёма Foundation +
  SR Legacy (~10-13 тыс. записей). Если позже подключат Branded Foods
  (~2 млн записей) — тогда пересмотреть в сторону Qdrant/Pinecone.

### 5.6 Механика коррекции (UX-решение, требует утверждения)

Это открытый вопрос, который явно обозначен в задаче как нерешённый.
Рекомендуемый подход (баланс простоты для пользователя и объёма работы):

**Уровень 1 — выбор кандидата.** У каждого ингредиента изначально стоит
первый (наиболее релевантный) из 3 кандидатов FDC. Кнопка `▾` открывает
inline-меню с 3 вариантами → пользователь просто выбирает другой, если
первый не подходит. Это закрывает 80% случаев "не тот сорт/вид продукта" без
свободного ввода.

**Уровень 2 — правка граммовки.** Кнопки `-10г / +10г` (или `-50/+50`) под
каждым компонентом, либо ввод числа текстом.

**Уровень 3 — правка состава.** Если ингредиента вообще нет в списке или
он не нужен — кнопка "убрать компонент"; если чего-то не хватает —
"добавить компонент" → пользователь пишет текстом название, и для него
заново прогоняется поиск по FDC (шаг 5.4-5.5) с показом тех же 3 кандидатов.

Это стоит зафиксировать с заказчиком отдельно на этапе `/gsd-discuss-phase`
для соответствующей фазы — здесь только предложение, не финальное решение.

### 5.7 Финальный расчёт (математика, не LLM)

Для каждого подтверждённого компонента:
```
калории_компонента = (граммы / 100) × ккал_на_100г_из_FDC
белки_компонента    = (граммы / 100) × белки_на_100г_из_FDC
... (аналогично жиры, углеводы, сахар)
```
Итог блюда = сумма по всем компонентам. Итог дня = сумма по всем блюдам дня.
**Ни одно из этих чисел не проходит через LLM.** LLM использована только на
этапе разбора речи и декомпозиции — не в подсчёте.

### 5.8 Сахар — важная оговорка
Не все записи USDA FDC содержат поле сахара (особенно Foundation Foods по
сырым продуктам). Технически честная реализация — показывать сахар "по
возможности" и явно писать "нет данных", если поле пустое в FDC, **а не**
подставлять 0 или выдумывать значение. Это стоит явно сообщить пользователям
в описании функционала бота, чтобы не создавать ложных ожиданий точности.

## 6. Расчёт целевых КБЖУ

### 6.1 Базовый обмен (BMR) — формула Миффлина-Сан Жеора
```
Мужчины: BMR = 10×вес(кг) + 6.25×рост(см) − 5×возраст + 5
Женщины: BMR = 10×вес(кг) + 6.25×рост(см) − 5×возраст − 161
```

### 6.2 Суточный расход (TDEE) — коэффициент активности
| Уровень | Коэффициент | Описание |
|---|---|---|
| Минимальный | 1.2 | сидячий образ жизни, без тренировок |
| Низкий | 1.375 | лёгкая активность 1-3 раза/нед |
| Средний | 1.55 | умеренная активность 3-5 раз/нед |
| Высокий | 1.725 | интенсивные тренировки 6-7 раз/нед |
| Очень высокий | 1.9 | физический труд + тренировки |

`TDEE = BMR × коэффициент`

### 6.3 Целевые калории под цель
- Изменение веса на 1 кг жировой массы ≈ 7700 ккал.
- **Максимальный темп — 1 кг/месяц** (ограничение явно задано в задаче) →
  максимальное суточное отклонение от TDEE:
  ```
  7700 / 30 ≈ 257 ккал/день
  ```
- Набор веса: `цель_ккал = TDEE + 257` (не больше).
- Снижение веса: `цель_ккал = TDEE − 257` (не больше), но не ниже безопасного
  минимума (обычно ориентир — не опускать ниже ~1200 ккал/жен, ~1500 ккал/муж
  без консультации врача — **это должно быть жёстко закодировано как нижняя
  граница**, а не оставлено пользователю на откуп).
- Поддержание/биохакинг: `цель_ккал = TDEE`, акцент интерфейса смещается на
  баланс БЖУ и микронутриенты, а не на дефицит/профицит.

### 6.4 Целевые БЖУ (граммы)
Пример пресета (нужно зафиксировать финально с заказчиком, это не медицинская
рекомендация, а разумный дефолт):
- Белки: 1.6–2.0 г/кг веса тела (выше при снижении веса, чтобы сохранить
  мышечную массу).
- Жиры: 0.8–1.0 г/кг веса тела, не менее 20% от суточных калорий.
- Углеводы: остаток калорий после белков и жиров.

### 6.5 Важная юридическая оговорка
Бот не является медицинским устройством и не заменяет консультацию врача
или диетолога — это должно быть явно написано в приветствии/условиях
использования, особенно раз есть сценарий "снижение/набор веса".

## 7. Подписка и платежи

### 7.1 Тарифы (входные данные от заказчика, зафиксировать в конфиге, не в коде)
- Месяц: ~1600 ₸
- Год: ~12000 ₸ (эквивалент ~1000 ₸/мес — скидка ~37% к месячному тарифу)

### 7.2 ⚠️ Открытый и потенциально блокирующий вопрос: способ оплаты
Telegram Payments API из коробки требует провайдера платежей (Stripe и
аналоги), которые **не всегда поддерживают приём тенге / карты казахстанских
банков** без юрлица и договора с локальным эквайером. Варианты, которые нужно
проверить ДО начала разработки платного функционала (иначе есть риск
спроектировать всё под API, который не заработает в проде):

1. **Локальный эквайер/платёжный агрегатор** (например, интеграция через
   Kaspi Pay/аналоги или банк-эквайер) с собственной страницей оплаты вне
   Telegram (бот даёт ссылку → пользователь оплачивает на внешней странице →
   вебхук от платёжки подтверждает боту оплату).
2. **Telegram Stars** — встроенная валюта Telegram, которая работает без
   локального эквайера, но требует конвертации ₸ → Stars и имеет свою комиссию
   Telegram — надо посчитать экономику при цене ~1600 ₸/мес.
3. Зарубежный провайдер (Stripe) — просто может не принимать карты РК
   напрямую в тенге, требует уточнения.

**Это должно быть решено в первую очередь**, до проектирования БД подписок
— модель данных зависит от того, вебхук-подтверждение или прямой callback от
Telegram Payments.

### 7.3 Модель данных подписки (независимо от выбора провайдера)
- `subscription(user_id, plan, status, current_period_end, provider,
  provider_ref, voice_messages_used_this_period)`
- Ежедневная/ежечасная джоба проверяет истекшие подписки → переводит в
  `expired`, шлёт уведомление о продлении.

## 8. Уведомления и планировщик

- Отдельный background worker (cron-подобный), который раз в N минут
  проверяет: кому пора напомнить, у кого истекает подписка, кому отправить
  дневную сводку.
- Хранить время последнего взаимодействия пользователя и часовой пояс
  (важно спросить его на онбординге, иначе напоминания будут приходить в
  неудобное время — например, ночью).
- Частоту и тон мотивационных сообщений — вынести в конфиг/пресеты, не
  зашивать в код жёстко (упростит A/B и правки текста без релиза).

## 9. Лимиты голосовых сообщений — экономика (для заказчика)

Каждое голосовое сообщение стоит денег на внешних API: STT + LLM (декомпозиция)
+ embeddings (по одному на каждый ингредиент блюда, обычно 3-6 шт.). Это
нужно прикинуть **до** финальной установки лимита и цены тарифа, чтобы
подписка не была планово убыточной при активном использовании. Разработчик
должен на этапе реализации посчитать фактическую стоимость одного голосового
(после выбора конкретных провайдеров STT/LLM/embeddings) и предложить лимит,
который держит unit-экономику в плюсе с запасом. Не фиксируем число здесь —
это должно считаться от реальных цен API, а не угадываться.

## 10. Данные и приватность

- Голосовые сообщения содержат биометрические данные (голос) и данные о
  здоровье (питание, вес) — это чувствительная категория данных.
- Хранить исходные аудиофайлы дольше, чем нужно для обработки, **не нужно** —
  удалять после успешной транскрипции (хранить только текстовую расшифровку и
  итоговый разбор, если это устраивает продуктовые требования).
- Токен Telegram-бота, ключи STT/LLM/embedding провайдеров, ключи платёжного
  провайдера — только в переменных окружения / секрет-менеджере, никогда в
  коде или в git.

## 11. Открытые вопросы и риски (нужно закрыть до/во время разработки)

1. **Платёжный провайдер под тенге** (§7.2) — блокирует проектирование
   платного функционала, решить в первую очередь.
2. **Механика коррекции ингредиентов** (§5.6) — предложен вариант, нужно
   подтверждение или альтернатива от заказчика.
3. **STT-провайдер** — Whisper vs Yandex SpeechKit vs Google — сравнить
   качество на реальных голосовых на русском/казахском перед фиксацией.
4. **Embedding-провайдер** — gemini-embedding-001 vs OpenAI text-embedding-3 —
   вопрос цены и качества поиска по FDC, не архитектуры.
5. **Лимит голосовых на тариф** — зависит от реальной unit-экономики (§9),
   посчитать после выбора провайдеров.
6. **Хранение аудио** — политика удаления, согласовать при необходимости с
   требованиями конфиденциальности.
7. **Юридическая оговорка про "не мед. изделие"** — нужно решить, кто пишет
   финальный текст (не техническая, а юридическая/продуктовая задача).

## 12. Рекомендуемый стек (не жёсткое требование, ориентир для планирования)

- Backend: Node.js/TypeScript либо Python — оба одинаково хорошо ложатся на
  задачу; выбор стоит делать по тому, на чём быстрее найдёте/будете сами
  поддерживать код (учитывая, что заказчик — React/TS-разработчик, **TypeScript
  на бэкенде снижает порог входа для него читать и участвовать в код-ревью**).
- База данных: PostgreSQL (+ расширение `pgvector` для векторного поиска —
  не нужен отдельный сервис).
- Очередь/джобы (если решим не ограничиваться MVP-подходом из §4): BullMQ
  (если Node) или Celery (если Python) поверх Redis.
- Telegram Bot фреймворк: `grammY` или `Telegraf` (Node/TS) — хорошо
  документированы, большое сообщество.
- Деплой: любой обычный VPS/контейнер (Docker) + Postgres — не требует
  экзотической инфраструктуры на старте.
